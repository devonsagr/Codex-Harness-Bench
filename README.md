## 📖 项目背景：为什么需要它？

在日常使用 AI 辅助编程的过程中，很多开发者都会陷入一种“调配置玄学”与“跑分幻觉”的困扰。Codex Harness Bench（CHB）诞生的初衷，正是为了给这套混乱的系统建立一个**透明、可控变量、贴近实际业务**的评测切口。

更具体的起因，是那些“看起来很努力，用起来却很累”的时刻：你问怎么解决，它绕着术语解释半天；你已经纠正了方向，它下一轮又回到原路；你要一个小功能，它搭出多层架构；你让它改善页面，它却把开发要求当成文案摆到页面上。修一个问题，加一条规则、一个脚本、一层审批，最终流程越来越完整，用户的问题却没有真正解决。

**我们要测的是：同一个模型，加了你的 Harness 后，是否更能听懂、说清、做对，而且少让你操心。** 模型的基础能力在同条件实验中相对固定，个人规则能改变多少，需要通过对照看出来。即使改不了，也应指出哪里跑偏、你重复提醒了几次、增加了哪些无用工作，而不是只给产物一个九十多分。

因此，“人机沟通”必须看实际对话：有没有答到点、能否理解纠正、该问时是否问清、不该打断时是否推进。写了交接文档不等于会沟通，回答很长不等于专业，回答很短也不等于有用。这些问题与过度工程化、产品文案混入开发指令，一起构成本项目要验证的日常使用体验。

### 1. 🧩 真实生产力是「模型 + Harness」的化学反应
市面上的排行榜回答的是各自协议下的能力问题：HumanEval 侧重函数补全，SWE-bench、Terminal-Bench 等 Agent 评测则已经包含工具、执行环境和 Harness。它们很有参考价值，但并没有测过**你本机这一套配置**。\
但现实工作中，开发者实际应用最多的场景，永远是 **模型 ＋ 宿主底座 ＋ 你本机的个性化 Harness（配置与规则）** 共同作用的结果。\
离开具体的 Harness 单谈模型能力，在实际工程中往往会严重失真。

### 2. 🌪️ 五花八门的私有配置：失控的 AGENTS.md 与 Skills 冗余
每个开发者的本地配置都千差万别：
- 全局 `AGENTS.md` 提示词微调了一两句、
- 随手添加的局部项目规则、
- 逐渐陈旧过时、甚至相互冲突的各类 Skills / MCP 插件、
- 不同的思考档位（Thinking budget）与模型交互约定……

很多时候，仅仅是提示词里多写了一句约束，模型的代码习惯就可能发生剧烈变化——或者产生令人头疼的**过度工程化（Over-engineering）倾向**（比如擅自封装好几层无用抽象、创建冗余空类与临时文件），或者工具调用失控。\
过去大家全凭“体感”和“手感”盲改配置，没有统一的基准参考。**我们面对这种客制化场景，设计了这套能够控制变量的打分切口。**

### 3. 🖥️ 固定 Codex 桌面端基座，专注评测外延客制化层
评测需要确定的边界。本项目不做脱离实际的自嗨，而是明确把基准**固定并锚定在大家最常用的 Codex 桌面端**（固定的宿主底座、原生沙箱与上下文链路）。\
我们不去重复造一个臃肿的 Agent 框架，**而是专门评测在此基础之上，每个人所做的“外延部分”**——你的全局规则微调、Skills 插件增删、推理档位选择，究竟是在给开发提效，还是在引入隐形负优化与算力浪费？

```text
       ┌──────────────────────────────────────────────┐
       │             Codex 桌面端原生宿主基座            │
       └──────────────────────┬───────────────────────┘
                              ▼
       ┌──────────────────────────────────────────────┐
       │   测试变量：外延客制化层 (AGENTS / Skills / 档位)  │
       └──────────────────────┬───────────────────────┘
                              ▼
                 同一任务与冻结起点的可编辑副本
                              ▼
           实际工程交付 → 机器程序验证 → 独立 AI 裁判取证
                              ▼
           按需人工复核 (体验与可用性把关)
                              ▼
                 有条件、可追溯、跨版本横向对比
```

### 4. 🥊 拒绝“刷题家”幻象：从零做项目的真实落地挑战
厂商发模型时个个都有漂亮的官方 Benchmark 雷达图，但很多模型在现实落地中本质上是**“高分做题家”**。\
你可能遇到过这种落差：榜单上的高分，换成自己的需求后，却变成了多余的抽象、超出范围的改动，甚至无法运行的项目。这个落差值得测，但不能凭模型名字预判谁好谁坏，更不能为了符合预期给某个模型压分。

现实业务中，最典型的场景往往是：**产品经理提了一个构想或业务需求，需要 AI 独立从零构建出一个完整可用、体验良好的项目。**\
这类全栈落地（Spec-to-Ship）任务天然具有主观性与多样性，仅凭几个单元测试的“退出码”根本不可能衡量真实交付品质。因此我们引入了：**程序验收事实 + 独立 AI 按题型取证 + 按需人工复核**。

### 5. ⚖️ 坦诚叠甲与技术挑战：微调控制变量与长周期评测难题
做这个项目，我们必须坦白承认当前面临的核心技术挑战与评测边界：
- **微调控制变量极难，单次分差微弱**：开发者对 Harness 的改动往往非常细微（比如微调几句 Prompt），在 LLM 天然具有温度采样随机性的前提下，单次分差可能来自执行或裁判的波动，当前还没有实测的统一误差范围。如何做出具备统计学意义的细微区分度？这要求我们**必须坚持相同环境、相同起点、多题目、多次重复测试**来看宏观趋势，切忌因单次高分就盲目断定某条规则有效。
- **长周期模糊项目难以自动化监控与评分**：面对开放式、长流程、多步骤的完整项目演进，长周期的上下文推演在纯自动化测试中极难做到全链路监控与精准打分。这也是为什么本工作台坚决保留了**人工复核、独立副本试运行与快照审计**通道，绝不用单一的虚假分数粉饰结果。

## 📐 两种评测轨道，分别解释

| 评测轨道 | 主要依据 | 核心定位与看分方式 |
|---|---|---|
| **基准题验证** | 固定题目、源码起点、指定环境与原题验收器 | **事实优先**：单元测试通过/失败与官方基准协议最优先；AI 质量评价仅作辅助参考。 |
| **真实项目交付** | 产品意图 Spec、全栈交付物、运行时交互与界面体验 | **体验与可用性**：程序基础事实 + AI 按题型量表取证 + 人工复核，允许多种合理技术选型，承认主观性。 |

> [!NOTE]
> 这不是非黑即白的二分法。基准题里也包含复杂工程扩展，真实项目交付也离不开基础测试。所有评分均用于特定变量下的前后对比参考，不代表模型的绝对全能，也不会把单一维度的体验分混充为官方通用学术跑分。

## ✨ 能做什么

- 🎛️ **私有配置版本管理**：一键保存、导入、复制和对比你的 AGENTS 规则、真实 Skills 插件组合与推理档位；支持回收站与历史快照版本溯源。
- 🛡️ **宿主配置保护与显式应用**：点击应用后才写入设置，先备份并校验 `config.toml`、`AGENTS.md` 和 `AGENTS.override.md`；提供显式恢复入口，遇到后续修改冲突会提示核对。
- 🧪 **独立 Git 工作区**：每次评测从冻结起点复制可编辑工程，修改不写回基线。目录独立不等于系统隔离，桌面执行仍会继承宿主的全局规则、技能与插件。
- 🤖 **独立 CLI 机器裁判取证**：基于官方独立 Codex CLI 进程调起裁判模型，按照严谨量表主动读取产物、运行可用检查并提取带行号的证据链。
- 👁️ **人工体验复核**：查看产物和截图、创建独立审查副本并在本地试运行，记录实际体验和按项修正；机器原分、人工修正与体验意见分别保留。
- 📈 **用量与效率记录**：从匹配工作区的原生日志提取 Token、缓存与活动时间；活动时间不是完整墙钟耗时或纯推理时间，缺失数据留空。
- ⚖️ **同模型 Harness 对照**：冻结同题、同模型、档位、速度与预算，交错执行 A/B，比较程序验收、失败和资源开销。可以一键创建精简配置副本，验证额外规则是否值得保留。

## 🚀 快速启动

需要 **Python 3.12+**、**uv**、**Node.js** 和 **pnpm**；正式执行需要本机已安装并登录 Codex 桌面端。

```powershell
# 1. 准备 Python 虚拟环境与依赖
uv venv --python 3.13
uv sync --frozen

# 2. 安装前端依赖并构建
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend build

# 3. 启动本地工作台
.venv\Scripts\python.exe -X utf8 -m chb.cli ui
```

> [!TIP]
> **Windows 用户快捷方式**：可直接双击根目录下的 **`launch-ui.cmd`**。\
> 缺少虚拟环境时执行 `uv sync`；缺少前端构建时安装依赖并构建。更新源码后请重新执行上面的构建命令。\
> 默认服务地址为：**`http://127.0.0.1:8765`**（仅监听本地，安全私密）。

*目前正式桌面流程以 Windows 实机验证为准。Python/Web 部分可在其他平台尝试，但不能仅替换路径就视为桌面集成已兼容。Docker 仅在运行外部容器化题包或 Harbor 裁判时需要，日常桌面评测与本机裁判不需要 Docker。*

## 🔄 一次评测的标准工作流

```text
[1. 保存配置] ──> [2. 选择任务] ──> [3. 准备并执行] ──> [4. 回收与评分] ──> [5. 存档与对比]
```

1. **保存配置**：在配置库中定义要测试的配置方案（选择模型、推理档位、标准/Fast 模式、规则文件与 Skills 组合）。点击“应用到 Codex”同步至本地。
2. **选择任务**：在题库中选择从零开发题（完整需求）或已有工程修复/重构题（绑定冻结源码起点）。
3. **准备并执行**：系统自动创建独立的评测工作目录。在 Codex 桌面端打开该目录，确认配置与标准 Prompt 后启动生成。
4. **回收与评分**：待 Codex 生成完成后，在工作台点击“回收产物”，随后启动自动检查与独立机器裁判。查看程序事实与 AI 引用证据，必要时人工按项修正。
5. **存档与对比**：回收时保存快照，交付结束后保留完整记录。要验证 Harness 收益，可在配置步骤开启同模型对照，由系统准备 A/B 配对题组，逐题执行并核对实际条件。

### ⚖️ 想知道“这套规则是不是太重”，怎么测？

把当前配置作为 A，选同模型、同档位、同速度的 B，或一键创建去掉额外规则与 Skills 的精简副本。写清要验证的改动，冻结题集、活动时间 / Token 预算与重复次数；系统按 A/B、B/A 交错创建独立工作区。**这只准备执行队列，不会自动替你发送桌面任务。**

结果先看预算内的程序验收成功、失败、未完成，再看包含失败尝试的资源开销。AI 质量意见单列，只有烟检和 AI 高分的网页作品不会被冒充成完整交付成功。实际模型、速度或宿主条件缺失 / 不一致时，报告保留观测结果，但不把差异归因给 Harness。

这是一套已接通的对照流程，**还不是已经验证有效的配置排行榜**。当前没有完成的真实 A/B 校准样本；前端审美、裁判偏差和提示词敏感性仍需盲样、重复审查和人工锚点验证。最高模型的作品可以作为参考样本，不能自动当成满分答案。详见[测量合同](docs/architecture/MEASUREMENT_AND_COMPARISON.md)与[方法研究](docs/research/harness-evaluation-20260929.md)。

### 💬 怎样量化“更好合作”，而不再拍一个总分？

先记具体事件，再比较同模型、同任务下的变化。新回收会封存本题绑定会话的可见文本；现有独立裁判可逐回合检查切题、纠正后的回答和不必要打断，显示符合、偏离、未知与不适用次数，并附双方原话。**这条证据链已经接通，但尚未用独立样本校准语义判定。** 完整目标还包括：

|使用中的痛点|要看的证据与结果|
|---|---|
|说东说西、没有答到点|用户请求与随后回答：首次回应解决核心问题的比例，附未命中原句|
|嘴上接受纠正，行为没有改|纠正前后的对话和改动：落实比例、同一意图额外重复提醒次数|
|不讲人话、理解起来费劲|指定读者下匿名比较哪份回答更清楚有用，保留平局与分歧；不按字数直接奖罚|
|无谓追问、把工作推回用户|不必要打断次数；必要澄清和真实权限确认分别记录|
|过度工程化、补丁越打越乱|对照目标审查改动与依赖，记录越界扩张、缺陷复发及重复无效流程；不能只数代码行|
|把开发指令写进产品|核对可见页面和文案，定位哪些内部要求误成了用户内容|

目前对话观察最多40回合、24000字符，每方每回合最多6000字符；截断、缺图、未回复和无效引用保留未知，未纳入回合明确列出。常见密钥遮盖后仍须自行核对敏感内容，下一次主动启动裁判会读取这份副本，回收不会启动模型。文本中的“已修好”不能证明代码真的修好；范围扩张、复发、视觉文案泄露与匿名表达偏好仍未接通自动判定。每项都要有分母、回合或改动引用。缺材料就写未测，不能拿交付说明代替对话。修 Harness 时一次验证一个改动，也检查它有没有让必要解释、必要设计或澄清变差；没帮助的规则应删掉，而不是每出一个问题再叠一条禁令。

开源项目提供了可借鉴的部件：Harbor 让任务验收器定义 reward；τ-bench 同时检查终态和必要告知；MT-Bench 评多轮回答；AlpacaEval 做成对偏好并研究长度偏差；AgentRx 从轨迹定位失败。它们各有适用范围，没有一个能直接替我们证明中文开发协作“好不好用”。具体算法、来源、校准步骤和未实现项见[人机沟通与过度工程化测量研究](docs/research/harness-interaction-evaluation-20260930.md)。

## 💾 数据存储与快照机制

为保证每一次评测的可重复性与审计追溯，所有数据均持久化在本地 `.local/arena/` 目录下（绝不自动上传任何个人规则与代码）：

| 本地目录路径 | 职责与存储内容 |
|---|---|
| `.local/arena/arena.sqlite3` | 配置库、题目版本、评测历史索引与评分记录主数据库 |
| `.local/arena/public-sources/`, `baselines/` | 固定版本的公开题包缓存与源码基线；复制到工作区后编辑，不写回基线 |
| `.local/arena/runs/<run>/<trial>/workspace` | 本次试次专属的独立 Git 工作区（Codex 桌面实际写入此目录） |
| `.local/arena/runs/<run>/<trial>/captures/` | 交付就绪后抓取的冻结产物快照 |
| `.local/arena/runs/<run>/<trial>/reviews/` | 独立机器裁判的原始日志、证据与报告；评分及修正另存数据库 |
| `.local/arena/runs/<run>/<trial>/human-inspections/` | 按需创建的人工审查副本 |
| `.local/arena/reviewer-runtime/` | 临时裁判运行目录；异常中断可能留下文件 |
| `.local/arena/public-sources/downloads/` | 持久下载缓存，供后续准备复用 |
| `.local/arena/trash/` | 安全删除缓冲池，误删的工作区可在确认彻底清理前无损恢复 |

## 📊 评分体系与量表细节

综合评价遵循**“程序验证提供事实，独立 AI 评价开放质量，人工复核保障体验”**的三位一体架构：

- **程序验收先给事实**：编译、原题测试、独立行为检查分别报告。变更行数与文件数用于观察改动规模，不能单凭“代码多”就判定过度工程化。
- **AI 按冻结量表取证**：新审查按覆盖、质量、韧性等细项给 0–4 等级，由程序计算分数，不再任意追加 extra。原题需求逐条核对，未验证项留空；最高等级需要可核对的反例检查证据。引用有效仅证明材料存在，不保证裁判理解正确。
- **题型决定评分卡**：开放项目默认“目标与范围 60% / 实际使用与可靠性 25% / 交付与可维护性 15%”；具体细项随题型变化。DeepSWE 的本地参考分为目标语义组 70%、回归 20%、维护性 10%，与原题通过结果分开。自定义方案和历史版本按各自冻结权重解释。
- **有分不等于已校准**：适用项和必要检查齐全即可显示单题参考分，未结束交付标“暂定”；缺证据不补零。六轴是证据归类视图，不是额外的综合分。AI 参考均值不能替代预算内交付成功率，旧分数不因新协议被悄悄重写。
- **体验复核保留出口**：前端必须看实际截图和交互状态，不能只读源码就断言好看好用。可以在独立副本运行产物，记录人工意见；机器原分与修正分别留存。当前尚无跨题库的视觉校准数据，不承诺一个统一小数分能准确区分所有作品。

## ❓ 常见问题 FAQ

### 一、 核心背景与评测原理

**Q: 市面上有那么多模型 Benchmark，为什么还要做这个项目？**\
A: SWE-bench 等 Agent Benchmark 本身也包含 Harness，但榜单测的是它所声明的组合，不是你的个人配置。本项目关注**同模型下，你增加的规则、Skills 与约定带来了多少交付收益，又多花了多少资源**。公开题目和原题验收器可以复用，评测问题与对照条件需要重新定义。

**Q: 为什么基准必须严格固定在 Codex 桌面端？**\
A: 变量控制需要固定的锚点。Codex 桌面端提供了成熟的执行流、原生沙箱与上下文协议，也是广大开发者最高频使用的环境。我们不去重复开发一个臃肿的 Agent 框架，而是把基座固定下来，专门测量并对比**外延的客制化层**。

**Q: 为什么说有些跑分霸榜的模型是“刷题家”？**\
A: “刷题家”描述的是跑分与使用体验可能存在的落差，不是对某个模型的预设结论。基准高分有其意义，但不能覆盖你的业务、界面审美和维护成本。需要让同一模型、不同 Harness 做相同项目，用验收事实、质量证据与资源记录回答，而不是按模型档次反推它应该得几分。

**Q: Harness 微调改动往往很小，单次分差微弱，如何避免随机性误差？**\
A: 没有实测就不能承诺“±几分”的误差。我们冻结配置指纹、题目版本、抽题种子与预算，采用**同条件、同题目、配对重复**，保存全部尝试。抽题种子只复现题集，不控制模型采样；一次高分不能证明一条规则有效。

**Q: 面对模糊长线需求，自动化测试有什么局限？**\
A: 长周期、多步骤的项目演进在自动化监控与打分中是业界公认的难题。任何宣称能 100% 自动给开放性长项目打出绝对公正分数的系统都是不诚实的。因此本工作台从不隐瞒局限性，提供了产物快照、独立审查副本以及按项人工复核入口，让人类工程师对实际交付物做最终裁决。

### 二、 裁判执行与数据管理

**Q: CLI 机器裁判究竟是怎么执行的？**\
A: 机器裁判每次均启动独立的 Codex CLI 进程，使用临时 Codex home 与产物副本，不恢复解题旧会话，也不使用当前开发对话代评。默认裁判为 GPT-6-Luna / max，实际可用条件以本机模型目录和运行回执为准。本机沙箱不等于虚拟机隔离。裁判模型会读取本题需求、量表规则以及待检查源码，通过工具主动探查、运行可用命令并收集证据链，逐项生成带具体代码行号引用的评分报告。“评分过程”面板会实时打印其执行的实际指令与输出。

**Q: 插件与 MCP 列表是固定的吗？**\
A: 不是。工作台在打开时会动态读取当前本机 `config.toml` 中已配置生效的 MCP 与插件 ID。工作台绝不会私自联网安装或更改你的系统插件。

**Q: AI 评分若格式校验失败，需要重新消耗模型额度吗？**\
A: 已保存完整报告且快照未变时，可先点“重新校验已保存报告”，只在本地解析与校验证据，不调用模型。缺失内容或证据不能靠解析补造；如果要重新启动裁判，则会再次消耗额度。

**Q: 如何进行前端界面的人工实际体验？**\
A: 在“评测 → 评分 → 查看产物与复核”页面中，点击“创建独立审查副本”，系统会克隆当前交付快照并显示运行说明与 `package.json` scripts。你可以在副本目录中启动服务，直接在浏览器中体验真实交互，随后在工作台中登记你的体验量表得分与评语。

**Q: 首次启用工作台时，我的最初配置会丢失吗？**\
A: 首次保护会备份 `config.toml`、`AGENTS.md` 和 `AGENTS.override.md` 的原文件及校验信息，不包含认证文件。配置库提供恢复入口；恢复需要明确操作，出现后续修改冲突时先核对，不能把“有备份”理解为任意状态下都能无损覆盖。

**Q: 如何彻底清理历史记录与磁盘缓存？**\
A: 进入工作台导航栏的“数据与存储”页面。系统明确区分了“清理工作目录（释放大量源码占用，保留评分、快照与统计记录）”和“永久删除整次评测”两类操作。确认页列明影响范围；关联会话按该入口的选择处理，不自动删除无关会话和已导出的 ZIP。删除工作区前会先移入回收站，永久删除不能撤销。
