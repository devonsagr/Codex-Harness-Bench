## 📖 项目背景：为什么需要它？

在日常使用 AI 辅助编程的过程中，很多开发者都会陷入一种“调配置玄学”与“跑分幻觉”的困扰。Codex Harness Bench（CHB）诞生的初衷，正是为了给这套混乱的系统建立一个**透明、可控变量、贴近实际业务**的评测切口。

### 1. 🧩 真实生产力是「模型 + Harness」的化学反应
市面上铺天盖地的模型排行榜（如 SWE-bench、HumanEval），测试的都是无菌实验室环境下的“纯裸模型”代码能力。  
但现实工作中，开发者实际应用最多的场景，永远是 **模型 ＋ 宿主底座 ＋ 你本机的个性化 Harness（配置与规则）** 共同作用的结果。  
离开具体的 Harness 单谈模型能力，在实际工程中往往会严重失真。

### 2. 🌪️ 五花八门的私有配置：失控的 AGENTS.md 与 Skills 冗余
每个开发者的本地配置都千差万别：
- 全局 `AGENTS.md` 提示词微调了一两句、
- 随手添加的局部项目规则、
- 逐渐陈旧过时、甚至相互冲突的各类 Skills / MCP 插件、
- 不同的思考档位（Thinking budget）与模型交互约定……

很多时候，仅仅是提示词里多写了一句约束，模型的代码习惯就可能发生剧烈变化——或者产生令人头疼的**过度工程化（Over-engineering）倾向**（比如擅自封装好几层无用抽象、创建冗余空类与临时文件），或者工具调用失控。  
过去大家全凭“体感”和“手感”盲改配置，没有统一的基准参考。**我们面对这种客制化场景，设计了这套能够控制变量的打分切口。**

### 3. 🖥️ 固定 Codex 桌面端基座，专注评测外延客制化层
评测需要确定的边界。本项目不做脱离实际的自嗨，而是明确把基准**固定并锚定在大家最常用的 Codex 桌面端**（固定的宿主底座、原生沙箱与上下文链路）。  
我们不去重复造一个臃肿的 Agent 框架，**而是专门评测在此基础之上，每个人所做的“外延部分”**——你的全局规则微调、Skills 插件增删、推理档位选择，究竟是在给开发提效，还是在引入隐形负优化与算力浪费？

```text
       ┌──────────────────────────────────────────────┐
       │             Codex 桌面端原生宿主基座            │
       └──────────────────────┬───────────────────────┘
                              ▼
       ┌──────────────────────────────────────────────┐
       │   测试变量：外延客制化层 (AGENTS / Skills / 档位)  │
       └──────────────────────┬───────────────────────┘
                              ▼
                 同一基准任务与只读源码起点
                              ▼
           实际工程交付 → 机器程序验证 → 独立 AI 裁判取证
                              ▼
           人工 5 维工程量表复核 (体验与可用性把关)
                              ▼
                 有条件、可追溯、跨版本横向对比
```

### 4. 🥊 拒绝“刷题家”幻象：从零做项目的真实落地挑战
厂商发模型时个个都有漂亮的官方 Benchmark 雷达图，但很多模型在现实落地中本质上是**“高分做题家”**。  
例如某些官方榜单霸榜的模型（如 opus5），在标准化测试集上跑分极高，但在真实场景接一个复杂需求时，却常常过度设计、擅自造轮子、甚至跑不通；反倒是像 fable5 等更接地气的模型，在实际从零交付项目时表现得更稳健高效。

现实业务中，最典型的场景往往是：**产品经理提了一个构想或业务需求，需要 AI 独立从零构建出一个完整可用、体验良好的项目。**  
这类全栈落地（Spec-to-Ship）任务天然具有主观性与多样性，仅凭几个单元测试的“退出码”根本不可能衡量真实交付品质。因此我们引入了：**程序确定性硬事实 + 独立 AI 裁判全维度取证 + 5 维人工工程量表**。

### 5. ⚖️ 坦诚叠甲与技术挑战：微调控制变量与长周期评测难题
做这个项目，我们必须坦白承认当前面临的核心技术挑战与评测边界：
- **微调控制变量极难，单次分差微弱**：开发者对 Harness 的改动往往非常细微（比如微调几句 Prompt），在 LLM 天然具有温度采样随机性的前提下，单次运行的分差可能只有微弱的 1~2 分。如何做出具备统计学意义的细微区分度？这要求我们**必须坚持相同环境、相同起点、多题目、多次重复测试**来看宏观趋势，切忌因单次高分就盲目断定某条规则有效。
- **长周期模糊项目难以自动化监控与评分**：面对开放式、长流程、多步骤的完整项目演进，长周期的上下文推演在纯自动化测试中极难做到全链路监控与精准打分。这也是为什么本工作台坚决保留了**人工复核、独立副本试运行与快照审计**通道，绝不用单一的虚假分数粉饰结果。

## 📐 两种评测轨道，分别解释

| 评测轨道 | 主要依据 | 核心定位与看分方式 |
|---|---|---|
| **基准题验证** | 固定题目、源码起点、隔离环境与原题隐藏测试器 | **事实优先**：单元测试通过/失败与官方基准协议最优先；AI 质量评价仅作辅助参考。 |
| **真实项目交付** | 产品意图 Spec、全栈交付物、运行时交互与界面体验 | **体验与可用性**：程序基础事实 + AI 5维量表取证 + 人工复核，允许多种合理技术选型，承认主观性。 |

> [!NOTE]
> 这不是非黑即白的二分法。基准题里也包含复杂工程扩展，真实项目交付也离不开基础测试。所有评分均用于特定变量下的前后对比参考，不代表模型的绝对全能，也不会把单一维度的体验分混充为官方通用学术跑分。

## ✨ 能做什么

- 🎛️ **私有配置版本管理**：一键保存、导入、复制和对比你的 AGENTS 规则、真实 Skills 插件组合与推理档位；支持回收站与历史快照版本溯源。
- 🛡️ **宿主安全保护与无损应用**：应用配置到本地 Codex 时自动备份原有的 `config.toml` 与 `AGENTS.md`，支持随时一键完全回滚。
- 🧪 **隔离 Git 沙箱工作区**：每次评测自动生成独立隔离的 Git 工作区，预置绑定的只读源码与测试，防止污染个人开发目录。
- 🤖 **独立 CLI 机器裁判取证**：基于官方独立 Codex CLI 进程调起裁判模型，按照严谨量表主动读取产物、运行可用检查并提取带行号的证据链。
- 👁️ **人工工程 5 维复核**：支持产物与截图快照查看、一键克隆独立审查副本并在本地试运行，从“需求切中、代码规范、健壮度、交互可用、维护性”五个维度打分，独立记录。
- 📈 **用量与效率精准遥测**：自动从匹配工作区的原生会话日志中提取 Token 用量、Prompt 缓存命中数与实际耗时，拒绝伪造。

## 🚀 快速启动

需要 **Python 3.12+**、**uv**、**Node.js** 和 **pnpm**；正式执行需要本机已安装并登录 Codex 桌面端。

```powershell
# 1. 准备 Python 虚拟环境与依赖
uv venv --python 3.13
uv sync --frozen

# 2. 安装前端依赖并构建
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend build

# 3. 启动本地工作台
.venv\Scripts\python.exe -X utf8 -m chb.cli ui
```

> [!TIP]
> **Windows 用户快捷方式**：可直接双击根目录下的 **`launch-ui.cmd`**。  
> 首次运行会自动检查环境并执行 `uv sync` 与前端构建。  
> 默认服务地址为：**`http://127.0.0.1:8765`**（仅监听本地，安全私密）。

*注：Linux / macOS 用户只需将 Python 路径换为 `.venv/bin/python` 即可。目前实机验证以 Windows 为主。Docker 仅在运行外部容器化题包或 Harbor 裁判时需要，日常桌面评测与本机裁判不需要 Docker。*

## 🔄 一次评测的标准工作流

```text
[1. 保存配置] ──> [2. 选择任务] ──> [3. 准备并执行] ──> [4. 回收与评分] ──> [5. 存档与对比]
```

1. **保存配置**：在配置库中定义要测试的配置方案（选择模型、推理档位、标准/Fast 模式、规则文件与 Skills 组合）。点击“应用到 Codex”同步至本地。
2. **选择任务**：在题库中选择从零开发题（完整需求）或已有工程修复/重构题（绑定只读源码起点）。
3. **准备并执行**：系统自动创建独立的评测工作目录。在 Codex 桌面端打开该目录，确认配置与标准 Prompt 后启动生成。
4. **回收与评分**：待 Codex 生成完成后，在工作台点击“回收产物”，随后启动自动检查与独立机器裁判。查看程序事实与 AI 引用证据，必要时人工按项修正。
5. **存档与对比**：标记交付结束，生成本次评测完整快照。更换另一组配置，在完全相同的题目与初始条件下重复执行，获得可追溯的对比结论。

## 💾 数据存储与快照机制

为保证每一次评测的可重复性与审计追溯，所有数据均持久化在本地 `.local/arena/` 目录下（绝不自动上传任何个人规则与代码）：

| 本地目录路径 | 职责与存储内容 |
|---|---|
| `.local/arena/arena.sqlite3` | 配置库、题目版本、评测历史索引与评分记录主数据库 |
| `.local/arena/public-sources/`, `baselines/` | 固化的公开题包缓存与只读源码起点，严格与工作区写权限隔离 |
| `.local/arena/runs/<run>/<trial>/workspace` | 本次试次专属的独立 Git 工作区（Codex 桌面实际写入此目录） |
| `.local/arena/runs/<run>/<trial>/captures/` | 交付就绪后抓取的冻结产物快照 |
| `.local/arena/runs/<run>/<trial>/reviews/` | 独立机器裁判与人工复核的原始日志、证据与打分结果 |
| `.local/arena/reviewer-runtime/`, `downloads/` | 临时审查运行沙箱与暂存目录，正常执行完毕自动清理 |
| `.local/arena/trash/` | 安全删除缓冲池，误删的工作区可在确认彻底清理前无损恢复 |

## 📊 评分体系与量表细节

综合评价遵循**“程序验证提供事实，独立 AI 评价开放质量，人工复核保障体验”**的三位一体架构：

- **自动化事实硬指标**：编译是否报错、已有测试集是否通过、Git 变更增删行数与纯净度（识别中间层与多余膨胀文件）。
- **独立 AI 裁判 5 维取证量表**：
  1. 🎯 **需求切中度 (50%)**：是否精准实现所有显式与隐式需求，是否存在减配或无谓的功能堆砌。
  2. 🛡️ **边界健壮度 (20%)**：异常捕获、错误处理、类型防护与竞态条件。
  3. 🎨 **交互与视觉 (15%)**：界面布局质量、交互逻辑与操作反馈（非界面题自动剔除该维度并重平衡）。
  4. 📦 **工程交付完整度 (10%)**：目录组织、构建脚本、依赖配置规范性。
  5. 🧹 **可维护性与代码品味 (5%)**：命名规范、分层清晰度、是否避免过度工程化。
- **人工工程复核**：可随时创建隔离副本实际启动前端应用，填写真实体验评分与改进建议。机器原分与人工修正记录严格分存。

## ❓ 常见问题 FAQ

### 一、 核心背景与评测原理

**Q: 市面上有那么多模型 Benchmark，为什么还要做这个项目？**  
A: 因为通用 Benchmark（如 SWE-bench）测试的是无菌环境下的“纯裸模型”。但现实中开发者天天在用的，是**「模型 + 桌面宿主 + 你本人的客制化 Harness」**。Harness 中的提示词微调、Skills 插件乃至思考档位，对代码产出有着决定性影响。脱离 Harness 谈模型生产力如同纸上谈兵。

**Q: 为什么基准必须严格固定在 Codex 桌面端？**  
A: 变量控制需要固定的锚点。Codex 桌面端提供了成熟的执行流、原生沙箱与上下文协议，也是广大开发者最高频使用的环境。我们不去重复开发一个臃肿的 Agent 框架，而是把基座固定下来，专门测量并对比**外延的客制化层**。

**Q: 为什么说有些跑分霸榜的模型是“刷题家”？**  
A: 很多模型在官方基准题（如闭卷单点 Bug 修复）中表现惊艳（比如 opus5），但一放到实际真实业务场景——面对产品经理一个需要从零构建的模糊需求时，就容易暴露严重的“过度工程化”通病：疯狂封装抽象、建立无用层级，甚至无法正常编译运行；反倒是 fable5 等在实际交付中更加接地气。真实交付是开放的、主观的，所以我们坚决采用“硬测试 + AI 多维取证 + 人工复核”的三轨评测。

**Q: Harness 微调改动往往很小，单次分差微弱，如何避免随机性误差？**  
A: 大语言模型天然具有温度采样随机性（±2~3 分正常波动）。单次运行的高分或低分绝不能证明一条规则的好坏。必须采用**“控制变量、同环境、同题目、多轮次统计”**的方法。本项目把每次评测的配置指纹、随机种子与日志完整归档，正是为了支持长期科学的统计学对比。

**Q: 面对模糊长线需求，自动化测试有什么局限？**  
A: 长周期、多步骤的项目演进在自动化监控与打分中是业界公认的难题。任何宣称能 100% 自动给开放性长项目打出绝对公正分数的系统都是不诚实的。因此本工作台从不隐瞒局限性，提供了完善的产物快照、独立克隆副本以及人工 5 维量表把关机制，让人类工程师对实际交付物做最终裁决。

### 二、 裁判执行、Fast 模式与运行排查

**Q: CLI 机器裁判究竟是怎么执行的？**  
A: 机器裁判每次均启动独立的 Codex CLI 进程，使用临时独立的 Codex home 与隔离工作区副本，不继承任何旧会话。裁判模型会读取本题需求、量表规则以及待检查源码，通过工具主动探查、运行可用命令并收集证据链，逐项生成带具体代码行号引用的评分报告。“评分过程”面板会实时打印其执行的实际指令与输出。

**Q: Fast 模式是真实的开关吗？**  
A: 是的。配置中开启 Fast 时，系统会写入 Codex 的原生参数 `service_tier="fast"` 和 `features.fast_mode=true`；独立 CLI 裁判也会透传该参数。只有当前模型目录声明支持 Fast 的模型才会开放此选项。根据官方说明，Fast 通常可提供约 1.5 倍的生成速度，ChatGPT 账户或 API Key 会产生对应的额外额度开销。

**Q: 插件与 MCP 列表是固定的吗？**  
A: 不是。工作台在打开时会动态读取当前本机 `config.toml` 中已配置生效的 MCP 与插件 ID。工作台绝不会私自联网安装或更改你的系统插件。

**Q: AI 评分若格式校验失败，需要重新消耗模型额度吗？**  
A: 不需要。当裁判原始输出保存完好但前端解析异常时，快照未变的情况下可直接点击“重新校验已保存报告”，系统仅在本地重新运行正则与 JSON 校验，不发起新的模型调用。

**Q: 审查任务为什么会超时？**  
A: 早期版本默认超时为 8 分钟，当前版本已升级为默认 1 小时（支持在 15 分钟至 8 小时之间灵活配置）。超时记录为“未完成”，不会盲目判定为产物 0 分。若遇到 Windows 沙箱下的权限报错（如 `spawn EPERM`），属于系统级环境阻断，需检查对应目录权限而非单纯增加等待时间。

**Q: 如何进行前端界面的人工实际体验？**  
A: 在“评测 → 评分 → 查看产物与复核”页面中，点击“创建独立审查副本”，系统会克隆当前交付快照并显示运行说明与 `package.json` scripts。你可以在副本目录中启动服务，直接在浏览器中体验真实交互，随后在工作台中登记你的体验量表得分与评语。

**Q: 首次启用工作台时，我的最初配置会丢失吗？**  
A: 绝对不会。在首次启用并尝试应用配置时，系统会自动将当前的 `config.toml`、`AGENTS.md` 和 `AGENTS.override.md` 完整备份并计算哈希校验值存入配置库。你随时可以从配置列表中将“最初配置”一键无损恢复。

**Q: 如何彻底清理历史记录与磁盘缓存？**  
A: 进入工作台导航栏的“数据与存储”页面。系统明确区分了“清理工作目录（释放大量源码占用，保留评分、快照与统计记录）”和“彻底删除整次评测（彻底抹除一切文件与数据库条目）”两类操作，操作前均需二次明确确认，且绝不会误伤宿主 Codex 本身的全局会话与用户手动导出的 ZIP 包。
