# 桌面执行、阶段与证据回收

负责 D15-08/15/17/18、U08。主要工作包 B04/B05；接口见 [数据与 API](DATA_AND_API.md)。本文把“怎么运行”写成可实际操作的过程。配置来源与 Skills 选择见[配置合同](CONFIGURATION.md)。

## 1. 三种执行语境

|语境|执行者|输入/输出|成绩归属|
|---|---|---|---|
|正式项目评测|用户在 Codex 桌面启动任务|本题独立工作区、完整需求或显式分步需求；项目产物与桌面日志|desktop|
|客观验收|本机后端启动 Docker 检查|冻结快照副本、固定验收镜像；退出码/输出/时间|该快照的检查证据|
|机器裁判 / 旧辅助复审|固定本机原生沙箱或 Harbor 管理的 Codex CLI|冻结需求、产物副本、已有检查；实际命令与引用式评分|cli-review-only；为桌面交付评分，裁判用量独立记录|

旧 CLI 跑题实验在 runs/ 单独保留。不能把它与桌面正式评测互换，也不能把“启动复审”说成“桌面自动运行了项目”。

## 2. 一次单题执行的详细顺序

|步骤|用户在界面做什么|系统实际做什么|完成后看什么|
|---|---|---|---|
|1 选择|工作台选题、选已有配置并预览，按需调整本次Skills；配置导入集中在配置管理|核对来源 revision；临时技能调整只进入本次Run|规则/技能、项目需求、阶段与证据要求|
|2 准备|点击应用到新工作区并创建|自动创建目录，冻结输入与策略，复制起点、生成规则和技能、初始化 Git、保存 baseline|精确目录路径与本次编号；还没有模型用量|
|3 打开|点击新建Codex对话并预填|第一轮通过官方深链打开工作目录与冻结提示词草稿；仍需用户信任目录并发送|不保证侧栏分组，不据此推断已发送|
|4 核对|在桌面核对模型和推理档位|工作台只记录用户确认|实际模型/档位；后续可用日志核对|
|5 发送|一键复制本轮提示词，在桌面任务中手动粘贴发送|服务端已冻结提示词；工作台不代发；按精确目录匹配原生会话|第一轮新任务；后续仍是同一个任务|
|6 等待|在桌面观察执行/回答必要问题|页面轮询同步原生状态、累计用量与活动时间，不自动代替下一轮确认|该轮交付说明、请求确认或异常|
|7 回收|桌面停止写入后点击回收|检查路径、冻结全部允许文件，记录新增/删除/修改及哈希|回收编号、所属阶段、排除清单和差异|
|8 验收|回收后点击自动检查并评分，按需人工修正|本机模式直接独立AI检查副本；Docker模式先执行已有脚本；评分与修正追加保存|机器原分、覆盖率、逐项证据、最终分；无脚本也可评分|
|9 继续或结束|已完成整题则结束交付；需要修改时继续原对话并再次回收|切换阶段但仍等待用户开始；结束不自动判通过|历史记录、证据覆盖和分数|

工作区在第2步已自动建好；“复制路径”仅复制已存在目录的地址，无需用户再次建文件夹。打开桌面、复制提示词和记录开始各自独立；保留当前人工发送流程，不把自动打开等同于发送。桌面自动发送并非原则上不能做，但当前没有实现，也没有验证过适用入口。

新Run执行提示词版本为user-requirements-v3，默认含inputPrompt和去重后的全部步骤需求，不添加阶段次数；显式staged才附当前步骤；内部projectSpec/criteria留作独立评分材料，不再整段注入。裁判只看截至目标快照阶段的已发提示词，不用后续轮要求扣分。内部条目没有公开需求依据时标未验证，不能追加隐藏需求；旧Run保留原来文本。

## 3. 到底检查哪个文件夹

现有目录由工具拥有：`.local/arena/runs/<run>/<trial>/workspace/`。题目可显式选择一个源目录作为起点；导入时复制为 baseline，原目录不被修改。不同试次使用不同目录。

用户在桌面编辑 workspace；回收复制到 `captures/<capture>/files/`；Docker 检查只读挂载后者，再复制到容器 `/app` 执行。AI 同样读封存材料。继续修改 workspace 不改变已经回收的证据。

**当前不支持把任意现有文件夹直接指定为原地运行和验收目录**，也没有任意路径文件浏览 API。用户原文“选择某个文件夹”包含两种可能：选择起点，或选择已经做好的项目验收。U08 已明确独立工作区主线；后者作为待审扩展，不能谎称“导入起点”已经完全满足。

目标的准备页应清楚写“从哪个起点复制”和“实际去哪个目录做题”；这两个路径不得用一个“工作区”输入框混淆。

## 4. 多轮、确认和回归

U24默认single-delivery：一次给完整需求，不预设实际对话次数。是否规划、等待确认或一次完成由被测Harness与实际问题决定。Capture是产物版本，不是模型回复次数；可随时回收、继续原对话、再次回收。只有用户主动选staged才按题库步骤提供分步提示词。

新Run保留authoredStages/authoredChecks来源，执行副本折为完整交付；仅保留最终阶段检查及runOnFinal回归，不把中间状态检查强套到成品。原题和旧Run不改写。旧机器评测也可在任意回收后complete；finalCaptureId指向该版本，必须新做final范围评分，旧阶段分只留历史。未发送的后续步骤提示词不伪装为已发送；原始完整需求仍为整题依据。旧v1/v2脚本计分继续保留阶段规则。

用户要求按阶段等确认时，流程为：发送本轮 → 执行/澄清 → 停止写入 → 回收 → 查看验收证据 → 用户确认进入下一轮 → 在原桌面任务发送下一轮。确认通过是流程动作，不自动构成质量通过。

显式分阶段的系统允许已回收后继续，不强制所有检查通过；进入下一步时正文展示完整提示词及复制按钮。这支持阶段尚不完整但有意继续的真实使用；目标 B04 要记录“带着哪些未解决项继续”的理由。不能后台自动把不通过项当作通过，也不应把每次检查失败都变成无法继续开发。

重复回收生成新Capture，清除当前交付结束标记，旧评分不迁移。旧版多个阶段总分使用各阶段最新回收的适用检查；人工总分使用最新回收的人工复审。早期检查可在准备前显式声明runOnFinal；用户检查最终快照时会同时运行这些回归项。未声明的检查不自动扩展范围。计分按阶段×检查要求完整，不把早期通过当最终通过，见T-AC5。

已经进入下一阶段后，可以对上一阶段的封存版本补做检查。它解决漏验旧产物，不证明新产物没退化。

## 5. 现有状态与动作

|状态|含义|主要允许动作/退出条件|
|---|---|---|
|prepared|准备完成，尚未发现本轮执行|打开/复制、核对后 start；API 允许补回收外部已完成产物|
|working|匹配会话已开始，或用户后备声明|capture 或 interrupt；不证明桌面进程实时存活|
|captured|已冻结当前轮产物|重复回收、验收、complete；显式分步可continue|
|waiting_confirmation|已选择进入下一轮，尚未记录开始|核对、复制和 start；仍不自动发消息|
|checking / judging|工具拥有的后台工作|等待或 stop；不能改变阶段/回收覆盖目标|
|completed|用户标记当前产物为整题交付（不等于通过）|查看/复审/导出；再次回收会回到 captured，总分需重新结束|
|interrupted|用户记录外部中断|查看原因、保留证据、可回收已有部分；不是桌面停止命令|

具体服务端约束以 mutate/start_job 实现为准。当前 UI 禁用忙时编辑，但服务端动作互斥需要 B05 再逐项对齐，不能把 UI 禁用当完整接口保护。当前 interrupted 没有专用“恢复该轮并记录重启”动作；用户可在桌面继续后回收，恢复路径的清晰引导仍需补全。

## 6. 回收和证据完整性

- 每次快照记录阶段、时间、文件清单、内容哈希、差异、回复或执行说明。
- 依赖目录、Git 元数据和凭据类文件排除；单文件8 MB、总50 MB、最多5000文件，链接/目录联接和回收期间变化报错。
- 当前差异相对于初始 baseline，不是相对于上一轮；界面必须写清比较基点。逐轮差异切换是目标能力。
- 产物清单和路径提供只读浏览，不能从浏览器读任意宿主文件。
- 检查、AI 和导出前核对快照哈希。哈希用于意外修改检测，不等于防恶意篡改的公证。
- 原型的文件变化数量有实际证据时可以展示，但不能直接兑换“纯净度”成绩。

目标证据关系为：需求/验收条目 → Capture → 文件片段/测试记录/人工操作证据 → Review。版本2已通过criteria稳定ID绑定人工操作说明、文件hash和检查回执。U20机器评分已校验文件行级引用和真实命令输出；截图附件浏览和完整自动操作回执仍未实现。

## 7. 检查与 AI 的生命周期

检查启动绑定 captureId，固定镜像内容 ID，保存 job 与容器拥有信息。容器关闭网络，只挂冻结材料；不挂工程根、个人 home 或 Docker socket。记录 passed/failed/error/timeout/cancelled，不能把所有非成功都折成零分。

本机裁判支持无需Docker的副本检查，生命周期与边界见评分合同。AI审查显式点击才使用模型额度；新机器裁判单次Agent超时480秒，旧辅助审查180秒，环境准备和清理另计。新镜像提供Python、Node及Playwright Chromium，Harbor上传本次冻结candidate副本；具体网络、证据校验与未验证边界见EVALUATION。不自动重试、换模型或增加评审人数。输出必须有结构化意见和引用验证；详见评分合同。

正常停止只处理本工具拥有的后台任务，不停止桌面 Codex。服务重启保留快照和错误，并按精确拥有信息处理检查容器；强制结束进程后，不保证 Harbor 审查环境都已清理。需要可读的恢复信息，不能以名称前缀清理全局容器。

## 8. 异常与恢复目标

|异常|保留什么|下一动作|
|---|---|---|
|桌面额度/限流/上下文问题|当前轮、已回收材料、错误来源与时间|在桌面处理；记录恢复，不能自动买额度或换条件|
|打开桌面失败|已准备工作区和配置|复制路径手动打开，不新建重复 Run|
|复制提示词失败|完整可选中文本|手动复制，不能显示“已发送”|
|回收期间仍在写文件|旧快照不变，错误提示|停止写入后重试；不留半份有效快照|
|检查环境故障|容器信息、输出、已完成检查、目标 Capture|恢复环境后重试同一快照，留存旧尝试|
|原生日志不属于本题|拒绝原因|重新选择日志；不污染已绑定会话|
|浏览器刷新/后端重启|数据库与冻结文件|重新加载记录；不要以清空数据作为修复按钮|

当前不具备原型文案宣称的“所有异常一键自愈”。B05 按明确状态逐项补齐。

## 9. 验收案例

- **E-AC1**：准备之后没有模型调用；打开桌面失败仍可用同一目录继续，不重复建实验。
- **E-AC2**：两轮同一会话，第一轮和第二轮产物可分别查看；回收后改工作区不改旧快照。
- **E-AC3**：需要确认的配置在阶段边界等待；工作台不自动确认；用户等待不产生负面质量分。
- **E-AC4**：检查绑定的快照始终可见；前轮补验与最终回归有不同记录，不混淆。
- **E-AC5**：中断、后端重启、重复请求后，能从历史定位同一试次并继续；没有丢失已成功封存的材料。

## U15 应用回执

准备工作区同时生成.codex/config.toml；用户可在开始前一键将本题冻结配置应用到Codex全局。应用的文件回执、旧全局指纹、应用后预期指纹分别保留；只允许prepared状态更新预期，不追溯改变旧回收。文件写入、新任务加载和实际遵守分别核对；没有模型执行记录不能宣称全部生效。现有桌面发送/阶段确认步骤继续有效。


### U19：桌面对话草稿入口

单题准备后可自动用Codex官方深链打开新对话草稿，path是本试次绝对工作目录，prompt为本轮冻结文本。首次进入不受信任目录时由桌面要求用户确认；发送、模型/档位核对和记录开始仍显式进行。后续轮次保持原对话，不自动开新会话。路径匹配不保证侧栏已有项目分组归属；不通过改写Codex数据库伪造会话。协议调用成功只记“已请求”，不推断任务/模型已经运行。参考：[官方Commands深链规范](https://learn.chatgpt.com/docs/reference/commands)。


### U29 工作区清理边界

已回收并标记结束后，可在“数据与存储”按评测清理workspace，包括其Git和依赖。先确认桌面停止写入，后端核对当前可收集文件与最新capture一致，再移入trash/workspaces；可恢复到原路径，原路径已占用则拒绝。永久删除另行文字确认，先记录deleting以便失败重试。保留captures、reviews、冻结配置、评分和数据库历史；不能以归档代替释放空间。清理前检查全目录链接/联接，禁止借此跨出拥有目录。正常异常路径会回滚可逆移动，强制结束和磁盘故障仍可能需要人工核对。

本机AI裁判的工作副本与临时凭据目录改在.local/arena/reviewer-runtime，正常结束删除；长期复查结果仍在本试次reviews。下载中间目录在.local/arena/downloads，均不进入Git。
