# 产品模型：固定桌面场景中的个人 Harness 评测

依据：[requirements](../requirements.md) 的U27当前定位及此前仍有效需求。本文是目标合同；实现进度由 [主架构路线](../PROJECT_SPEC.md#8-唯一实施路线与完成标准)维护。

## 1. 背景与目标

用户在真实项目中遇到的问题，是模型、全局规则、技能和交互习惯一起作用时，交付是否切中需求、是否出现无用扩展、旧方案是否正确迭代，以及整个过程是否可控。只知道某个模型的通用榜单成绩，不能直接回答自己的规则组合是否更适合自己。

因此本项目是一个本地评测工作台：把一次真实需求、当时的配置、实际产物、用量和验收依据保存成可以回看的记录，让用户改动个人 Harness 后能够做有条件的比较。

它的首要成功标准是：用户能在同一Codex桌面场景下，评测不同个人配置对交付和资源使用的影响，并追溯差异来自哪些条件。许多编码榜单本来就使用指定Harness；本项目的区别是把用户日常桌面的可配置层作为主要变量。

## 2. “直击有效”的操作定义

|要判断的事|可用证据|不能用作替代的指标|
|---|---|---|
|理解需求|需求条目与交付行为对应；澄清记录；用户验收说明|回答短、语气自信、步骤少|
|完成交付|核心用户故事能走完；适用测试；持久化和异常行为|文件存在、编译通过、截图漂亮|
|适当的实现范围|新增结构能解释其对要求的作用；旧实现正确迭代|单纯以代码行数少、文件少判优|
|遵守个人流程|该次启用的约束逐条核验；阶段确认记录|所有用户共用“不要技能”“不许等确认”的偏好|
|资源使用|实际日志中的用量、可确认的活动时长、人工介入说明|用墙钟时长惩罚合理等待，用估算冒充账单|

复杂需求可能需要更多代码、更多轮次、更多澄清。不能因为它用了技能或多建了模块，就自动认定过度工程化。问题在于它们是否服务于已约定的目标。

## 3. 固定场景、变量和观察条件

- 固定场景：Codex 桌面。它本身已有执行、工具、上下文和宿主设置，是评测底座。
- 主要研究变量：用户选择的 AGENTS 文本、实际技能内容、个人约束、交互约定。
- 可同时记录的设置：模型与推理档位；如果也改变它们，结果属于组合比较，不能只归因于规则修改。
- 尚不能完全固定的条件：桌面版本、全局技能和插件、全局规则继承、服务端行为、随机性及人工介入。
- 当前装载方式：独立工作区叠加规则。它不等于把用户的全局环境完全替换成选定配置。

本限制必须出现在准备和结果语境中，不能只埋在问答页。更多平台、Deepseek 全局插件场景、通用 Agent 调度不是本轮范围。

## 4. 核心对象

|对象|含义|与相邻对象的区别|
|---|---|---|
|配置 Config|一份命名的个人规则组合，有 revision|不是一份模型的能力成绩；同名新版本不能覆盖旧实验|
|题目 Task|要交付的需求、阶段与验收合同|不是模型运行；也不是一条 npm 命令|
|项目契约 ProjectSpec|用户故事、接口、数据、验收与技术边界|需求契约不等于强制唯一实现答案|
|运行 Run|一次冻结选择，含配置、题目、策略与条件|一次 Run 可准备多个工作区，但不自动执行多题|
|试次 Trial|一个配置版本 × 一个题目版本的独立工作区|一个多轮项目仍是一个 Trial|
|阶段 Stage|同一项目的预定需求推进步骤|不是一题，也不是独立重复样本|
|回收 Capture|一次停止写入后封存的文件版本|不是完成/通过声明；同阶段可回收多次|
|复审 Review|针对某一回收的机器评价或人工修正|不同作者和证据类型不能互相覆盖|
|比较 Comparison|有条件的结果集合与差异解释|不是所有任务、所有策略混成的总榜|

## 5. 三条用户路径

### 路径 A：先测自己的配置

保存一套配置 → 选一道项目题或写自己的需求 → 看清验收方式 → 准备独立目录 → 在桌面执行 → 回来回收和验收 → 查看历史。

不要求先找另一套配置，不要求先跑五题，不要求新建账户。没有自动测试的新题也应能通过通用机器量表和逐条需求验收开始；结果明确标记证据类别。

### 路径 B：改一条规则后比较

复制已有配置 → 显示具体差异 → 选择同一题目版本和策略 → 分别在独立工作区执行 → 比较交付、用量、约束遵守和证据不足处。

恢复旧配置应形成新副本，不能直接改宿主设置或旧记录。若要判断微小收益，应进入重复评测方案；本轮不会把单次差异解释为可靠提高。

### 路径 C：完整项目分阶段推进

例如：需求澄清与 Spec → 前端 → 后端及持久化 → 联调交付。每个阶段有提示词、预期产物、验收方式和确认点。第一阶段产出的 Spec 是候选产物，不能自动改写评测者最初的需求与标准。

阶段结束先回收，在同一桌面任务确认继续；下一阶段应验证此前仍有效的要求。当前实现已支持阶段推进和前轮补验，但尚未实现结构化的需求演进与回归关联。

## 6. 当前产品的依据

Gemini只提供了前端起点，不规定题库、评分或后端。产品范围由用户当前目标决定：桌面底座保持一致，模型条件可记录/对照，个人可配置层是主要变量。界面延续已有有效入口，功能与评测方法独立实现。

公开题库用于覆盖代表性需求。接入时必须保留源码、依赖和验收语义，展示是否适配/可运行/已校验，不能用题面数量替代任务覆盖。来源索引可供选型，但尚不能用于桌面执行。个人业务需求可使用开放式机器评分，与公开题原生指标分别报告。

历史来源对齐文档仅用于追溯已有字段，不再承担产品要求和实施优先级。产品页围绕当前使用场景解释，而非让用户阅读开发过程。

## 8. 产品验收边界

用户能说明“本次用了什么配置，做了什么，哪个版本被检查，哪些要求满足，分数为什么这样，哪些数据不知道”，才是完整闭环。41 项测试通过仅是工程证据，不能替代这个判断。

完整的验收脚本在 [后端完成合同](BACKEND_DELIVERY.md)。只有功能接通、故障保留、历史可复核及正式桌面项目验收都满足，才使用“产品功能闭环完成”的表述。
