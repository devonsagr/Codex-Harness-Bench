# 后端功能完成合同与实施切片

本文定义后端“做全”需要交付的行为、模块边界和验收方法。**唯一顺序与工作包状态在 [总架构第8节](../PROJECT_SPEC.md#8-唯一实施路线与完成标准)**；本文不另建第二套进度表。

## 1. 从基础链路到产品闭环

现有Python后端能保存版本、准备独立工作区、回收文件、运行检查、启动独立AI复审、保存人工分和历史。这些是可复用基础，不需要推翻重做。

但是“填功能”还必须把 Gemini 的业务合同接通：结构化需求进入执行和验收，逐题细则进入评价，配置差异能读懂，历史能复用，异常能恢复。数据库能写一个JSON不等于完成这些模块。

每项功能按一条完整纵向切片交付：输入/校验 → 持久化与版本 → 执行或派生 → 页面展示/操作 → 历史与失败路径 → 验收。禁止后端返回占位字段，前端画上勾就算完成。

## 2. 模块责任与依赖

|能力|现有落点|补全职责|依赖|
|---|---|---|---|
|项目契约与题目导入|contracts/task_import、service、catalog、Contracts/Editors|结构版本、条目ID、预览、准备度、提示词编排|先于逐项验收和项目样题|
|配置与对照|save_config/import_files/restore_config|模型能力来源、装载预览、内容差异、版本浏览|不依赖题目评分|
|阶段与快照|prepare/mutate/files|冻结提示词、回归关联、确认理由、恢复信息|题目与验收条目|
|评分与验收|scoring、review、Runner|量表+逐题条目、证据、必要项结论、复审版本|稳定条目ID和快照|
|后台检查|jobs.run_checks|类型/条目关联、尝试历史、最终回归与恢复|复用现有Docker边界|
|AI意见|review_packet/run_judge/validate_judge|材料覆盖、引用定位、人工处理与争议|复用Harbor，不另造runner|
|用量与比较|telemetry、Records.Comparison|协议诊断、细类异常、分项比较、后端统一分组|冻结条件与评分语义|
|历史与导出|Database、api.export、Records|版本时间线、新评测复用、完整契约/证据导出|贯穿所有新实体|
|本机交互|webapp、App、api|稳定错误分类、服务端动作约束、草稿与恢复|所有切片共同边界|

已新增contracts/task_import分离契约与导入逻辑；comparison等后续按需拆分；继续使用SQLite和单进程本机服务，不引入无必要的云队列、账户系统或多平台抽象。

## 3. 切片一：项目契约从头到尾不丢

输入：Gemini已有projectSpec/fullstackScope/evaluationRubric/customChecklist和用户自定义题。输出：有版本的规范化契约、兼容旧字段的保存、结构化编辑/预览、冻结提示词、历史中的原始合同。

先处理字段保真，再处理界面。用7份已有Spec做迁移样本；没有Spec的题保持真实准备状态，不凭空生成默认API或数据库。目标需求探索模式要保存“原始需求—候选Spec—用户确认”的关系，不能让候选自行更改标准。

完成证据：T-AC1/2/3/4、F-AC1/2、D-AC1/3。检查内容进入了实际复制给桌面的提示词和运行记录，不能只在catalog查字符串。

## 4. 切片二：逐项验收与统一计分

输入：冻结验收条目、适用量表、当前capture。输出：每条达成状态和证据、人工复审新版本、必要项结论、通用分数解释，AI仍独立保存。

“部分满足”不是默认50分；先保存语义与理由。逐题条目与通用维度关联但不重复计分。改条目/改策略不得污染旧Run。必要条目失败不能被高视觉分抵销成“通过”。

完成证据：S-AC1/2/3/4/6、F-AC3，旧arena-review-v1结果回放不变。只有现有公式通过测试，不代表逐项验收完成。

## 5. 切片三：配置复用与控制变量

输入：两份配置revision和实际技能快照。输出：字段矩阵、正文/内容差异、原始与生成规则说明、旧版恢复副本、直接进入评测的明确选择。

完成证据：C-AC1至C-AC5、F-AC4、D-AC5。不能因原型技能是字符串而退回只存技能名字；不能把全局规则哈希当完整隔离证明。

## 6. 切片四：多轮执行和材料复审

输入：阶段合同、预定检查、候选产物、AI报告。输出：用户确认、阶段回收、后续回归、需求和文件引用、意见处理、带入下一轮的问题说明。

完成证据：T-AC5、E-AC2/3/4、S-AC5。提示词仍手动在同一桌面任务发送；不能偷偷切CLI自动跑来完成桌面验收。

## 7. 切片五：失败、恢复、历史和用量

输入：真实或构造异常、旧版记录、重复累计日志。输出：保留证据的中断/恢复、可读错误、同请求重试、旧历史不变、可解释比较和未知指标。

完成证据：E-AC1/5、D-AC2/4/5、M-AC1至M-AC5、F-AC5。没有异常分支的“能点通”不足以交付。

## 8. 完整项目样题与实际验收

新增一套原创前后端项目题，包含用户交互、API或明确数据层、持久化、异常反馈、多轮扩展和最终回归。可采用任务看板；题源不得与原型未核实第三方仓库混淆。

同时验两件事：被评测Agent交付是否合格；工作台是否完整保存和解释评测。测试生成draft.txt/final.txt只验证回收，不是完整项目样题。

|阶段|执行内容|通过条件|
|---|---|---|
|题包自检|错误起点、参考解、环境缺失|区分功能失败/通过/环境异常，答案不交给候选|
|软件链路|创建契约→准备→文件变化→回收→逐项复审→历史|数据/操作和错误分支正确，不产生正式模型成绩|
|正式桌面|真实完成整题与多轮确认|桌面会话/目录、实际产物、验收和不完整项记录|
|历史复用|创建配置/评测新副本|原记录hash和分数不变，新目录/ID明确|
|产品审查|用户能看懂过程、证据、分数和限制|裁决进入需求记录，不用测试数替代认可|

正式桌面需要用户手动核对/发送，这是U08选择的方式，不能用工具写示例文件来冒充。本轮固定契约软件验收使用隔离测试目录，不启动桌面模型，也不把测试文件当正式整题交付。

## 9. 测试层次与证据

|层次|针对什么|不能证明什么|
|---|---|---|
|单元/合同|迁移、评分、状态、版本冲突、用量|界面直观或模型能力|
|API集成|存储、快照、回收、后台尝试、错误|桌面任务真的执行|
|浏览器操作|输入、跳转、选中语境、错误、历史恢复|未操作场景全部正确|
|容器题包|负例拒绝、参考解通过、超时/停止|测试覆盖全部需求|
|AI调用|真实结构输出、引用检查与归档|意见无误、视觉已验收|
|正式桌面|真实场景中的完整记录与验收|微量变化已有统计可靠收益|

现有基准：50项测试（含新增9项契约测试）、TypeScript/Vite/compileall/uv build；此前3套原创题容器负例/参考解与一次AI辅助复审；本轮增加JSON导入到历史的浏览器软件样例。保留这些回归，新增针对业务风险的检查，不写只镜像实现的测试。

## 10. 兼容与回滚

1. 新字段有明确schema/迁移；旧分数按原策略解释。
2. 不批量改旧Run来“补上”原本没采集的条目和用量。
3. 新算法用新版本；历史重分析写派生记录及源hash，不替换原结论。
4. 文件写入与DB登记有可恢复流程；残留明确标记，不递归清理用户目录。
5. 使用Git revert回退代码，保留.local/与runs/；旧程序不支持新数据时只读或明确拒绝，不降级覆盖。

## 11. 怎样报告完成

每个工作包给出：需求编号、Gemini对应点、完整业务路径、验证回执、尚未验证部分和版本。只有测试通过时写“合同测试通过”，不是“产品完成”。

不采用无依据的“完成80%”；以总架构的工作包和退出条件说明。一轮工作完成有意义的交付范围，不把小改动后等用户说继续当作固定节奏。
