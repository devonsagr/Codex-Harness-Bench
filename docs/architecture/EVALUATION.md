# 验收、评分与 AI 误判处理

负责 D15-03/06/07/10/14/18/19。工作包 B02/B04/B08；本合同是评分语义依据，当前公式代码在 `src/chb/arena/scoring.py`。

## 1. 先验收要求，再解释分数

四种信息分别回答四个问题：客观检查证明哪些行为被测过；人工复审判断交付是否切中需求且可用；AI 帮助发现可能遗漏；个人约束记录该用户的特有要求是否满足。

测试绿、AI 无意见、人工高分和项目符合要求不是同一句话。界面首先展示验收覆盖和未核实事项，其次展示有依据的分数。

## 2. 通用量表与逐题标准

|层|内容|计分关系|
|---|---|---|
|通用人工维度|需求完成与切中度、可维护性、边界健壮性、适用时的交互视觉|按冻结权重形成可解释人工分|
|逐题验收条目|例如新增、撤销、刷新恢复、异常反馈|说明上述维度在本题如何观察；不再加一份重复总分|
|个人约束|例如特定文档同步、阶段等确认|单列达成状态与证据，初期不并入公共总分|
|客观检查|功能、构建/类型、明确规则等|实际退出状态与预定权重；关联验收条目|
|AI 意见|带文件/行引用的疑点、遗漏或建议|不自动写人工分，不把意见数换成扣分|

这样既不用每新增一道题都重做评分引擎，也不会只拿通用四个数字忽略具体需求。原型中的 customChecklist/evaluationRubric 应迁移成可追溯的逐题条目；原型 rubrics 类型并不代表31题都已有完整量表。

## 3. 人工验收应该怎么做

1. 选择要验收的回收版本，显示题目和策略的冻结版本。
2. 阅读本题需求，按用户故事实际操作产物。检查文件、输出、接口或浏览器效果；没有做过的操作保持未核实。
3. 对每条要求记录满足/部分满足/不满足/未核实/不适用；部分满足写出剩余行为，不适用写理由。
4. 每条可引用文件片段、检查结果或人工操作说明。原型点击“测接口”只切布尔值的行为不得保留为真实测试。
5. 为适用通用维度填写0–100分，支持小数，并解释依据；选择交付可用程度。没有初始85分，也不预勾全部通过。
6. 保存一份新复审。后续修正留下旧版和修改理由；重新回收后不自动把旧分迁到新产物。

当前只实现第1/5/6步的基础数据、文件/检查浏览和个人约束状态。逐题验收明细、逐条证据、接口实际操作回执与评分争议记录未完成。

### 通用分值锚点

|范围|解释|所需说明|
|---|---|---|
|0–39|核心目标不能完成|主要失败场景或缺失交付|
|40–59|明显缺项，主要流程仍受阻|具体缺项与影响|
|60–79|基本可用，需要较明显修正|哪些部分成立、哪些需要返工|
|80–94|要求较完整，存在局部问题|真实验收范围与剩余问题|
|95–100|有充分证据满足本次要求|实际核验覆盖；不能仅由“没发现问题”推出满分|

这是校准人工判断的产品量表，不是行业认证。四个数值维度加一个交付等级，不再把原型“5维”文字误说成五个独立数值。非 UI 题的 UX 不适用；UX 权重在适用维度间重新归一化。

## 4. 现有公式与空值

设预定检查权重为 w，所有预定检查必须都有 passed 或 failed 结论：

`O = 100 × 已通过检查权重之和 / 全部预定检查权重之和`

`H = Σ(适用维度分 × 维度权重) / Σ适用维度权重`

`S = O × objectiveWeight / 100 + H × humanWeight / 100`

默认主权重50/50，人工维度30/25/25/20；准备前可改并冻结。该比例来自现有产品约定，不声称科学唯一或已经用户专项确认。策略没有相同版本的结果不能直接混排。

- 没有检查时 O=null，不是100；有超时、环境错误、取消或漏执行时也保持未知。
- 某分支权重为0时不要求该分支有分。无脚本项目可在准备前明确选纯人工策略；结果注明“纯人工”。
- 所要求证据缺失、或者 Trial 未标记 completed 时 S=null。0是已知低分，null是没有足够依据。
- 多轮检查目前使用各阶段最新回收；人工使用最新回收的最近一次 human review。新回收会使旧版分数不再适用于当前结果。

### 算例（演算，不是实验成绩）

检查权重2和1，前者通过、后者失败，则 O=66.67。人工分80/70/60/90时 H=74.5，50/50总分70.59。若第二项超时，则 O和默认策略下总分未知，人工74.5仍可显示。

非 UI 题人工80.5/70/60，按30/25/25归一化为70.81。这只是算式说明；视觉不适用不能偷偷补一个高分。

### 需要补齐的判定信息

当前总分并没有逐题必要条目门控：客观部分有失败也可能出现数值总分，个人约束未满足也不会阻止计算。目标增加“验收结论/必要项状态”，与连续分数并列；不能把70分自动翻译成项目通过。必要条目是否全部满足是合同判定，不能用视觉高分抵销关键数据丢失。

## 5. 为什么调整 Gemini 的评分方案

原型同时存在客观50/人工50和项目 E2E40/AI30/人工30两套口径；后者还会将模拟分反填人工维度。两套不能在同一成绩中隐式混合。本期采用明确的客观+人工公式，保留 AI 为独立意见；作为待审设计说明，不伪称是用户指定的唯一算法。

原型 gitPurityScore、技能多自动扣分、单轮自动奖励和固定误差缺少有效依据，且与用户对“切中需求”的纠正冲突。文件数、行数、轮数只是事实；只有明确的需求/约束被违反，才进入对应人工或规则验收。

## 6. AI 审查的真实能力

现有审查输入为冻结题目对象、文件文本、差异和已经执行的检查。单文件最多30k字符，总文本100k字符；遗漏文件列出。Harbor 的 CLI 审查返回 summary 和 findings(path,line,quote,comment)，代码核对引用是否存在，不成立的引用过滤。

这只能减少无依据引用，不能消除以下错误：引用是真的但理解错；重要文件被截断；发现了风格差异却当功能缺失；静态源码无法证明运行行为；没有视觉材料却猜测界面好坏。

当前没有 AST/DOM 事实采集链、参考实现相对评分、双裁判盲审、分歧熔断，也没有估计过误判率。原型规范页宣称这几项“内建”属于演示承诺；本项目不沿用其已完成语气。成功调用一次审查接口仅验证链路，不证明裁判可靠。

目标 B04 先补意见处理：用户可标记接受/驳回/待核实，填写原因和证据，保留原意见及处理历史。意见引用能跳到对应冻结文件；AI 与人工冲突不静默覆盖任一方。

双裁判等后续方法只有在具体问题和成本值得时再评估，绝不为了看起来完整而每次自动调用多个模型。

## 7. 人工证据与运行预览

源码阅读不等于实际体验。目标复审入口允许登记产物运行地址、截图或手动操作记录，并标注环境和时间。展示用户明确提供的地址不等于让后端自动执行任意宿主命令；启动候选应用仍需已声明的安全执行方案。

本期先保证文件、检查和人工记录完整连通；自动浏览器验收与可复用 Web 检查模板按 B07 验证，不把未实现的实时预览写成现有功能。

## 8. 验收案例

- **S-AC1**：无检查的新题用纯人工策略完成；总分注明策略和证据，不出现默认测试通过。
- **S-AC2**：未评分、真正0分、部分满足和不适用在存储与界面中明确不同。
- **S-AC3**：每条需求可追到文件/测试/操作依据，恢复旧历史仍保留条目和当时评分。
- **S-AC4**：必要的刷新持久化失败，界面不会仅凭高视觉分显示“验收通过”。
- **S-AC5**：AI 引用伪造被过滤；引用真实但结论错误可被人工驳回，原意见仍可查。
- **S-AC6**：修改评分策略需新实验或单独派生分析；原始成绩及证据不改写。
