# 验收、机器评分与人工修正

本合同负责 B02/B04/B08 的评分语义。当前新方案为 `arena-machine-v1`，实现位于 `arena/machine.py`、`jobs.py`、`scoring.py`。旧 `arena-review-v1/v2` 只按原规则回放。实施状态统一见 PROJECT_SPEC 第8节。

## 1. 默认流程

准备时冻结题面、项目契约、逐条需求和评分维度。回收后点击“自动检查并评分”，后台先运行当前阶段已有脚本，再启动独立 Harbor/Codex 裁判读取产物副本、尝试构建/测试/交互并逐项评分。无需另开桌面对话，不要求每题先写验收脚本。

机器评分产生之后，用户可按需修正单项；没有人工参与也可以形成完整成绩。人工不是固定50%的计分分支。被测执行仍为 Codex 桌面，裁判执行标记 `cli-review-only`，裁判时间与额度不能冒充被测任务用量。

## 2. 通用方法与题目差异

|层|依据|本项目处理|
|---|---|---|
|通用维度|需求完成、可靠性、交互、交付、维护等|按题选用，冻结权重，不以所有维度等权作为行业标准|
|逐题要求|原始题面、projectSpec、criteria|裁判逐条对照；原有契约转换保留来源，不编造新的要求|
|程序检查|预先声明的命令及实际退出状态|先运行，独立保存结果，提供给裁判；不重复加一份总分|
|主动取证|裁判读取文件、尝试构建、运行测试与浏览器操作|复用工具能力，不要求用户逐题提供脚本；不能运行的内容留为未验证|
|人工修正|实际复核及理由|替换有效分项，保留机器原分，不修改程序通过状态|
|过程与效率|真实日志、指纹、资源记录|单独展示，不用少Token抵消功能失败|

新方案默认需求50%、健壮性20%、交互15%、交付10%、维护5%；这是可调整的产品起点，不是经校准的行业标准。非界面题排除ux，其余适用权重归一。权重使用滑条联动，合计100%；真实成绩是独立0–100，不联动。

当前直接使用已有结构化条目与完整题面。**导入时用AI自动拆解需求、供用户确认后冻结的功能尚未实现**；没有criteria仍可按完整题面评维度，但必要项覆盖显示“未配置”，不能宣称已逐条完整验收。

## 3. 分数与未知

设适用维度权重为w，机器项分为m，人工有效修正为h：

- 机器原分 M = Σ(w×m) / Σ已评分项权重。缺项时明确标“暂定”。
- 机器覆盖率 = 已有机器分的权重 / 全部适用权重；它不是测试覆盖率或需求通过率。
- 有人工修正时，该项有效分取h；其余取m。
- 所有适用项有有效分且交付标记completed后，最终分 S = Σ(w×有效分) / Σw；否则S=null。
- 人工可以为机器未验证的项补充复核分，但不会抬高机器覆盖率。
- 真正0分参与计算，null表示未知。超时、额度不足、环境错误不变成0分。
- 重评失败时保留仍适用的旧机器报告并显示本次错误；不伪造新的评分成功。

分档锚点：0–39核心失败；40–59重大缺口；60–79主流程成立但有明显问题；80–94主要要求和关键边界有验证；95–100完整且有可复现证据。高分不自动等于所有必要项通过。引用正确也不能证明AI判断一定正确。

## 4. 裁判输入、执行和引用

裁判镜像 `chb-reviewer:machine-v1` 包含 Codex CLI、Node、Python、pnpm、Playwright Chromium。用 `scripts/prepare_arena_review.py` 显式构建。已有Harbor负责环境、执行和清理，未另建通用Agent runner；本轮没有安装独立Rewardkit包。

完整冻结快照经Harbor预构建镜像的environment上传能力复制到容器 `/app/candidate`。不挂载项目根、宿主home或Docker socket；宿主快照执行前后核对hash。裁判可在容器临时副本安装依赖和运行，指令禁止修改实现以帮助通过。提示词和产物中的AGENTS/技能/说明仅作不可信材料，不能改变评分目标。该约束和引用检查不构成已验证的抗提示注入保证。

裁判上限480秒、2 CPU/2GB；Harbor准备/清理另计，不自动重试、换模型或升级权限。Agent阶段网络限定模型服务及npm/PyPI依赖源；特殊外部服务和技术栈不保证可运行。脚本检查仍是独立无网络容器。专用脚本镜像缺失时可继续裁判取证，必要脚本的缺失仍记未知；未清理的容器或快照异常不忽略。

返回 `summary/findings/ratings/criteria`。每个计分维度必须有score、method、reason、evidence；score为0–100有限数或null。method为static/runtime/unverified。非空分必须有引用，UX/性能必须有runtime记录。逐条需求覆盖冻结ID，状态为met/partial/unmet/unverified；已判定项必须有引用。

引用可为快照文件path/line/quote、已有checkId/output quote、裁判实际命令及输出quote。命令来自Codex事件日志，不能由返回JSON自行伪造执行记录。引用无法匹配则拒绝这份评分，原始日志保留。程序只能核实出处，不能确认命令是否真的测到了需求；runtime不等于客观正确，仍须查看命令语义。

截图可由裁判留在Harbor artifacts，但本轮未提供截图浏览/引用验证的完整界面。浏览器工具已配置进镜像定义，**容器与真实裁判链路尚未实跑通过**，不将DOM/视觉覆盖宣传为已验收能力。

## 5. 人工修正和版本

`machineCorrections` 是追加记录，绑定capture、reviewId和包含检查结果的evidenceKey。修改单项必须填写理由与复核证据；score=null表示撤回该项修正，恢复机器原分。修正不能改写ratings、criteria或脚本结果。

新回收、新机器报告或本快照检查证据变化后旧修正不再适用；全部历史继续保存。后台检查期间拒绝修正，过期提交拒绝。新方案最终分包含当前有效修正；同条件自动比较暂排除人工改分项，要求完整机器覆盖及相同裁判模型/档位/镜像/CLI版本，避免人工结果混入自动排名。

必要项结论沿用冻结契约：关联脚本失败或条目partial/unmet→not_met；条目未核实或必要检查缺失→unverified；全部met且相关检查通过、交付完成→met。没有必要条目→not_configured。此结论与数值分数独立。

## 6. 旧记录兼容

旧v1/v2仍是 `S = O×objectiveWeight/100 + H×humanWeight/100`。O是完整预定脚本集合中的通过权重比例；H是适用人工维度加权分。旧AI仅辅助意见；旧objectiveReviews的人工裁定单列，不改原分。旧记录不自动迁移，不将既有AI意见重新解释成机器评分。页面说明新建评测已改用机器方案。

旧人工复审的criteria/个人约束/dimensionEvidence/readiness/revisionReason与文件、检查引用校验继续保留。旧缺检查且客观权重大于0的百分比方案仍按原规则拒绝创建；新机器方案不受此限制。

## 7. 来源与尚未解决的问题

通用评分器和逐题成功标准必须区分。研究依据见 [开源调查](../research/landscape.md)：Harbor Rewardkit复用程序/模型/Agent评分，Promptfoo Agent Rubric主动查产物，Agent-as-a-Judge按需求取证；SWE-bench/Terminal-Bench提供更严格但更依赖任务测试的结果验证。

本轮复用既有Harbor执行接口，先打通机器结构化评分、出处校验、原分/修正分及界面。没有完成：裁判可靠性校准、双裁判争议复核、自动生成并确认逐题量表、参考实现相对评分、截图证据界面、完整过程指标和重复可靠性统计。不能以单测或一次模型调用证明评分科学有效。
