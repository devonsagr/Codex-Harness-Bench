# 验收、机器评分与人工修正

本合同负责 B02/B04/B08 的评分语义。当前新方案为 `arena-machine-v1`，实现位于 `arena/machine.py`、`jobs.py`、`scoring.py`。旧 `arena-review-v1/v2` 只按原规则回放。实施状态统一见 PROJECT_SPEC 第8节。

## 1. 默认流程

准备时冻结题面、项目契约、逐条需求和评分维度。回收后点击“自动检查并评分”，后台根据所选环境启动独立 Codex 裁判（本机原生沙箱或 Harbor 容器）；容器模式先运行当前阶段已有脚本，裁判读取产物副本、尝试构建/测试/交互并逐项评分。无需另开桌面对话，不要求每题先写验收脚本。

机器评分产生之后，用户可按需修正单项；没有人工参与也可以形成完整成绩。人工不是固定50%的计分分支。被测执行仍为 Codex 桌面，裁判执行标记 `cli-review-only`，裁判时间与额度不能冒充被测任务用量。

## 2. 通用方法与题目差异

|层|依据|本项目处理|
|---|---|---|
|通用维度|需求完成、可靠性、交互、交付、维护等|按题选用，冻结权重，不以所有维度等权作为行业标准|
|逐题要求|原始题面、projectSpec、criteria|裁判逐条对照；原有契约转换保留来源，不编造新的要求|
|程序检查|预先声明的命令及实际退出状态|先运行，独立保存结果，提供给裁判；不重复加一份总分|
|主动取证|裁判读取文件、尝试构建、运行测试与浏览器操作|复用工具能力，不要求用户逐题提供脚本；不能运行的内容留为未验证|
|人工修正|实际复核及理由|替换有效分项，保留机器原分，不修改程序通过状态|
|过程与效率|真实日志、指纹、资源记录|单独展示，不用少Token抵消功能失败|

U47–U51 的既有 `arena-machine-v1` 固定七项方案是历史冻结协议：需求完成35%、验证与回归20%、边界与健壮性15%、规则与范围遵守10%、交互与视觉10%、交付与可复现性5%、可维护性5%。这套权重仍用于回放旧评测；U52 新建评测同属 `arena-machine-v1`，但默认标记 `taskTypeAuto`，按题选用下文的评分卡与权重。缺项时总分为空，非界面题不要求交互分。这些本地方案均不是经校准的行业标准。历史 `arena-review-v1/v2` 与旧运行按冻结规则读取，不用新卡改写文件。

当前直接使用已有结构化条目与完整题面。**导入时用AI自动拆解需求、供用户确认后冻结的功能尚未实现**；没有criteria仍可按完整题面评维度，但必要项覆盖显示“未配置”，不能宣称已逐条完整验收。

## 3. 分数与未知

设适用维度权重为w，机器项分为m，人工有效修正为h：

- 机器原分 M = Σ(w×m) / Σ已评分项权重。缺项时明确标“暂定”。
- 机器覆盖率 = 已有机器分的权重 / 全部适用权重；它不是测试覆盖率或需求通过率。
- 有人工修正时，该项有效分取h；其余取m。
- 所有适用项及必要程序检查有有效结果后，单题分 S = Σ(w×有效分) / Σw；交付未结束时标为暂定，中间阶段不作为整题分。配置汇总另要求交付结束和下述证据资格。
- 人工可以为机器未验证的项补充复核分，但不会抬高机器覆盖率。
- 真正0分参与计算，null表示未知。超时、额度不足、环境错误不变成0分。
- 重评失败时保留仍适用的旧机器报告并显示本次错误；不伪造新的评分成功。

分档锚点：0–39核心失败；40–59重大缺口；60–79主流程成立但有明显问题；80–94主要要求和关键边界有验证；95–100完整且有可复现证据。高分不自动等于所有必要项通过。引用正确也不能证明AI判断一定正确。

### U62：单题参考分与配置对比资格

`machine.py` 派生 `score.assurance`，不修改冻结报告或旧分。公开题只有对应快照的原生验收及已核对本地卡均有效，才标 `native`；项目内五套经过正/负例核对的专属 verifier，仅在题目仍为导入时的第 1 版、只有一个阶段、检查器与该题匹配、**最新快照**的全部配置检查有结果且通过时才标 `task-check-pass`。多阶段题当前未在最终快照重跑全部回归，不能据早期阶段通过取得资格。专属检查失败标 `task-check-fail`。共享创意网页烟检、无独立程序验收、未知或缺失结果标 `ai-reference`。即便有多个 `runtime` 引用，也不能把通用命令输出自动升级为任务语义验收。

评分项齐全仍显示原始单题 AI 参考数值，失败与未知保持各自状态。配置成绩只对整组均具 `native` 或 `task-check-pass` 的完整题集发布可对照的本地综合分；其他完整题集仅显示 **AI 参考均值**，跨配置比较入口拒绝宣称胜负。这是防止通用烟检支持的 90+ 分被当成验证通过的最低门槛，**不是分数校准**：即使有专属脚本，本地综合分仍含 AI 质量判断；任务脚本只覆盖写明的行为，主观视觉、范围切中、沟通和维护性仍须用已知好/坏样本、匿名人工审查和同条件独立重复校验。旧版缺资格标记的记录保留原数值，资格按当前只读规则解释；不把未知强制写成失败或零分。

### 评分可信度的验收路线（未完成的校准工作）

验收单位是**冻结题目版本 × 冻结作品快照 × 检查器版本 × 裁判模型/提示词版本**，不能拿不同条件的两次数值直接当作配置改进。每题先列核心任务、可观察行为、必须失败的边界、未知项和可接受的替代实现；公开题优先固定原生验收，开放网页题需逐题加入真实用户流程、状态变化、错误恢复、窄屏/键盘/可访问性检查。共享烟检只守住页面能运行的底线，不能替代逐题语义。每个专属验收都用至少一份应通过、若干份针对关键缺陷应失败的**隔离夹具**检验；夹具与参考解不得进入被测工作区或裁判输入。多阶段题须在最终快照执行回归，不能拼接过去阶段的通过状态。

AI 只评程序难以判定的质量：冻结短而具体的量表、分档锚点、取证范围与缺证弃评规则；保留原始报告及逐项引用，程序校验引用是否存在，人工抽查引用是否真的支持结论。网页视觉要基于实际浏览器截图及交互轨迹，同一产物由不知道配置身份的评审独立标注，再与 AI 逐项对照。先建立高、中、低和核心失败的锚样本；让不同配置、不同题型都覆盖这些等级，避免只拿完成品校准高分。正式比较前预登记高分误判、关键缺陷漏检、排序逆转、弃评、重复方差和人工评审一致性指标及放行阈值，不在看完结果后倒调门槛。

对同一冻结快照重复审查，并随机打乱任务顺序、改变无关表述，测量模型和提示词的敏感度；将同题同条件的两个配置做成配对试次，显示逐题差和分布，不用单次 0.1 分差决定胜负。核心需求失败或必要程序验收失败时，任何 AI 高分都只能列为**待复核/未通过**，不能被其他维度的高分抵消。裁判超时、环境错误、无法看图和无证据应为 null，绝不能当作品 0 分；人工修正需保留机器原分和理由。校准集覆盖并通过之前，连续分始终称本地参考值，雷达和效率数据只是诊断视图。

## 4. 裁判输入、执行和引用

本机模式不依赖Docker，固定执行Codex CLI。CLI不是仓库内置文件：按系统 `PATH` 查找 `codex`，也可用 `CHB_CODEX_BIN` 指定非标准安装路径；使用前必须由运行者自行安装并登录。工作台不会复制作者机器的绝对路径、自动安装 CLI 或自动登录。开启workspace-write原生沙箱，使用临时CODEX_HOME及凭据副本，不加载用户配置/规则，凭据目录与产物目录分离。Windows使用受限令牌并绑定本次进程树，停止/超时只结束自己启动的程序。裁判在临时项目副本工作，原始快照不开放写入；网络允许下载依赖。既有容器检查在本机模式跳过，其必要证据仍保持未知，不能伪造通过。本机CLI合成题已实跑；环境指纹尚不完整，本机结果暂不进入严格同条件比较。

机器评分页面当前默认 gpt-6-luna、推理档位 max；模型目录列出不等于当前账号有调用权限，实际是否成功应以裁判作业回执为准。页面允许改选其他账户可用模型，报告保留实际模型与档位。裁判额度属于执行本机 CLI 的登录账户；ChatGPT 登录和 API Key 登录的额度/计费由各自账户渠道决定，不能把仓库或桌面评测记录当作独立额度来源。每次点击评分都会创建新的 `codex exec` 进程，不调用 `resume`，使用 `--ephemeral` 和新的临时 CODEX_HOME；不读取上一次裁判的会话、提示词、评分或内存。Docker/Harbor 同样为每次新 Job 创建新环境并在结束后删除。报告保存 `model`、`reasoningEffort`、`judgePromptVersion`、`codexVersion`、`reviewEnvironment`、`judgeIsolation` 和 `jobPath`，可追溯到完整提示词和事件日志。本站 AI 质量提示词由本项目制定并标记版本，不是 DeepSWE 官方程序验证器的判分提示词。

Docker裁判镜像 `chb-reviewer:machine-v1` 包含 Codex CLI、Node、Python、pnpm、Playwright Chromium 与 Noto CJK 字体。用 `scripts/prepare_arena_review.py` 显式构建；基础层在 `reviewer/Dockerfile.base`，裁判 CLI 层在 `reviewer/Dockerfile`。已有Harbor负责环境、执行和清理，未另建通用Agent runner；本轮没有安装独立Rewardkit包。字体只保证浏览器能渲染中文，不代表视觉构图自动判定准确；使用缺字镜像生成的旧截图不会因镜像升级自动变好，需新审查才能取得新的视觉证据。

完整冻结快照经Harbor预构建镜像的environment上传能力复制到容器 `/app/candidate`。不挂载项目根、宿主home或Docker socket；宿主快照执行前后核对hash。裁判可在容器临时副本安装依赖和运行，指令禁止修改实现以帮助通过。提示词和产物中的AGENTS/技能/说明仅作不可信材料，不能改变评分目标。该约束和引用检查不构成已验证的抗提示注入保证。

裁判预算默认3600秒、可选至28800秒；Docker路径限制2 CPU/2GB，本机尚无等价资源配额。Harbor准备/清理另计，不自动重试、换模型或升级权限。Docker Agent阶段网络限定模型服务及npm/PyPI依赖源，本机网络尚无同等域名白名单；特殊外部服务和技术栈不保证可运行。脚本检查仍是独立无网络容器。专用脚本镜像缺失时可继续裁判取证，必要脚本的缺失仍记未知；未清理的容器或快照异常不忽略。模型裁判不是确定性证明：相同快照、模型和提示词仍可能因模型采样、依赖安装、外部服务和工具时序产生不同结果；当前不自动平均、重试或以单次结果宣称可靠提升，比较时必须保留条件和重复结果。

返回 `summary/findings/ratings/criteria`。每个计分维度必须有score、method、reason、evidence；score为0–100有限数或null。method为static/runtime/unverified。非空分必须有引用，UX/性能必须有runtime记录。逐条需求覆盖冻结ID，状态为met/partial/unmet/unverified；已判定项必须有引用。

引用可为快照文件path/line/quote、已有checkId/output quote、裁判实际命令及输出quote。命令来自Codex事件日志，不能由返回JSON自行伪造执行记录。文件行号不匹配时，仅在同一冻结文件内有唯一逐字匹配的行才重新定位，并保存reportedLine和定位方式；不存在或歧义的引用不采纳。某项引用无效则该评分项置null/需求项置unverified，并记录validationWarnings；其他有效项保留。字段结构、维度集合、非法数值仍拒绝整份报告。原始日志和回答不改写。程序只能核实出处，不能确认命令是否真的测到了需求；runtime不等于客观正确，仍须查看命令语义。

截图可留在各自审查目录的artifacts，但未提供截图浏览/引用验证的完整界面。已有主题题历史报告包含Chromium交互证据；当前Windows本机裁判运行Edge发生受限令牌IPC权限拒绝和崩溃，尚未接通无Docker浏览器取证。裁判指令不再要求在该环境启动浏览器，UX/浏览器性能保持未验证；这不是已完成自动视觉评分。npm用户/全局配置已拆成两个独立空文件，避免double-loading错误和意外继承个人代理；不允许裁判清空这些变量绕回个人配置。

裁判输入的evaluationScope明确stage/final、目标阶段及总阶段数；中途仅检查当前及此前阶段，不以总体目标中的后续功能扣分。源码行号由冻结source-lines.json提供，不能靠模型猜测。引用按本节逐项核实和降级；结构错误仍显示具体失败原因并保存validation-error.json。早期回收被用户指定为整题交付时scope为final，但不追加未发送的后续提示词；旧stage报告不能转成最终分。

前端评分应分清五层：① 固定脚本检查可打开、控制响应、常见视口溢出和运行错误；② 题目专用的功能行为以可复现操作核对；③ 浏览器截图、交互前后与键盘/窄屏体验由实际页面观察；④ AI 按冻结评分卡写逐项理由和来源；⑤ 人工对抽象视觉、空间关系和争议项独立复核。当前创意题仅有第一层共享烟检及可选单次 AI/人工审查，尚无逐题视觉金标准、双评审一致性或跨模型盲评校准。单个 AI 适合辅助发现遗漏、整理证据和给**参考**连续分，但它的视觉偏好和推断错误都可能进入结果；机器分不是已证实的客观真值。实际浏览器运行证据是 UX 分的最低门槛，不等于审美结论已被截图验证。新报告的视觉构图/原创表达项还要求裁判保存真正的光栅截图，否则这两项保持未评；本机 API 只读提供本题裁判保存的 PNG/JPEG/WebP 给人工查看，排除 SVG 和非本题目录。截图存在仍不能证明 AI 实际看过图像，须在人工复核或独立图像裁判中校准视觉结论。

失败的五次使用 `arena-judge-2026-09-24`：已保存的家庭能源题示例共7404个字符，其中固定审查指令1492字，其余5912字是冻结题面、评分方案与记录。U57 将给裁判的材料收紧到原始需求、已发送阶段、适用维度与评分标准，去掉内部元数据和不适用维度的重复描述，并升为 `arena-judge-2026-09-27`；同题新版实际指令为4628字符（旧版7404），其他题长度以每次保存的指令为准。长度本身不是五次失败原因：旧容器 CLI 连模型元数据都未识别，调用随后被拒绝。但写法、条目顺序、示例和裁判模型确实会影响主观分。更改指令必须升版本；同题比较固定题面/评分卡/提示词版本、裁判模型与档位、环境和运行预算。争议项宜隐藏被测配置标签后人工盲评，必要时用独立第二评审和正反例校准；不能事后挑最高分或报不存在的误差范围。原提示词及事件日志可在“评分过程”查看。

[DeepSWE 官方任务格式与评分说明](https://github.com/datacurve-ai/deep-swe)明确将题目说明交给被测 Agent，另用隔离的程序 verifier 产出 binary reward 与测试通过比例；它没有可直接套用到本站自由网页审美的官方 AI 质量判分提示词。本站的 AI 提示词只评本地质量维度，不得冒充 DeepSWE 上游 reward。模型裁判的偏差并非推测，原始研究如[位置偏差系统研究](https://arxiv.org/abs/2406.07791)说明评价协议也须纳入控制变量。新短时三维题沿用 `interactive` 基础烟检；旋转是否真的保持立体结构，仍需看实际视角变化和人工复核，不能因按钮能点就给空间项高分。

### U58：独立会话、盲化边界及提示词校准准则

独立审查定义为每次新 Codex CLI 进程、独立临时 CODEX_HOME/Harbor 环境、不续接被测或上次裁判会话，只提供原始题面、冻结已发送需求、适用评分卡、当前产物及客观检查。**“独立”不自动等于“盲”或“客观”。** U57 五份有效报告虽满足会话独立，却把被测 `.codex/config.toml`、AGENTS 文件放进裁判副本；这些文件可能暴露模型/档位并施加指令影响。因此该五分是未盲化的本地参考评分，不能作为“完全未知被测配置的 AI 裁判”证据。新版 `arena-judge-2026-09-27-blind-v2` 从文件副本、提示材料、行号映射和引用核验中排除任一目录的 `.codex` 与 AGENTS 指令，保留原快照；报告 `judgeBlinding` 与提示词版本/SHA 区分协议。旧报告重校验按当年实际可见文件核验，不套新协议重写旧历史。被测文件名、代码注释、页面内容或工具输出仍可能透露身份，项目文本也可能提示注入，故不得声称绝对盲评。

本站 AI 提示词不是公开 SWE 题的官方 verifier。提示词中的评分区间锚点、检查顺序、是否要求浏览器证据、示例及字数都会同时改变**得分分布**和**运行用量**；已有五题集中约90分，只能提出“可能压缩高分段”的待检假设，不能由不同题/不同镜像的一次结果证明。每次修改量表或提示词须更换版本与 SHA；旧分只读。校准的最小流程：先冻结评价目的、锚题与正/负/边界样本、评分卡/通过标准、候选提示词、模型、思考档位、镜像、浏览器/字体和时限；隐去配置标签，在相同产物上交错顺序评 A/B，各至少重复以记录波动；人工不见 AI 分数独立评判视觉/需求；报告逐项分差、未评比例、引用错误、人工一致或分歧、错误样本、Token 和耗时，不能只比较总体均分。若成本不足，只做小规模发现性核对并标“未校准”，不要发布精细领先结论。网页视觉项需保存且确证裁判实际观察光栅画面；单有截图文件不足以证明这一点。该完整实验本轮**尚未执行**，所以现有 AI 分仍是参考分。

额度审计按每个作业最后一条 CLI 累计 usage 计，不把多条进度事件相加；中断无最终完成事件时读取 rollout 最后的累计计数。输入中的缓存读取、输出中的推理 Token 为子集；作业 token 不等于订阅额度扣除或美元账单，失败/重试分别计。U57 的五次成功作业合计 1,840,076 输入、38,825 输出，另一次超时作业底层记录 278,480 输入、6,685 输出，完整来源和旧模型失败链见[当前交接](../当前交接.md#u58裁判隔离真实额度审计与提示词影响现行)。每次评分页面与后端要求单次 `usageAcknowledged=true`；无同意不启动模型。可选时间预算只限制墙钟时间，不承诺 Token 硬上限，用户需要依据用量、任务复杂度与剩余额度自行决定是否再评。**缩短首条提示词并未解决重复工具调用带来的上下文成本。**

### U60：启动包、自动卡 v3 与网页证据边界

新裁判的终端指令只给 `/app/judge-packet.json`（原生沙箱为 `environment/judge-packet.json`）路径；任务环境中保存冻结题面、当前阶段、适用 rubric、维度列表及候选文件名，源代码仍在独立候选目录与行号映射。候选中的浏览器 profile 缓存文件被排除，避免把数百条非交付路径送给裁判。协议同时记录指令 SHA、材料 SHA、快照 ID、模型/档位、镜像与 `arena-judge-2026-09-28-packet-v3` 版本；新旧提示词协议不得混成同题可比结果。Windows `WinError 206` 可从 Harbor result 的异常读成启动失败，若模型未返回报告则不产生评分；已失败的旧作业保留原样，再发起新 CLI 仍须单次额度确认。

`project-tasktype-v3` 对此前工程/网页等自动卡目标组加入 5% 逻辑取舍，并从意图项扣除相同权重，保持 60/25/15。此项必须引用用户看得到的设计、澄清、验证或产物决策，不要求/臆测模型私有思维。旧卡缺少该项时，雷达推理轴仍为空，绝不通过新映射从旧高分倒填；对比按题目、评分卡版本、裁判提示词和模型协议隔离。

网页通用 Chromium 检查增加可见页面变化、键盘操作、表单可访问名称、SVG 响应结构、320/390/768/1280 宽度、运行异常与离线依赖；输出逐项 PASS/失败。检查器升级只对尚未冻结镜像摘要的内置创意题自动准备；既有冻结试次仍用当时的镜像。共用烟检不能识别地标像不像、数据值是否真实、游戏状态是否满足题意或审美好坏。新评分卡、更多检查项和附引文的单个 AI 仍未完成同快照重复/人工盲评校准，历史 93.6 仍只作参考分。

## 5. 人工修正和版本

`machineCorrections` 是追加记录，绑定capture、reviewId和包含检查结果的evidenceKey。修改单项必须填写理由与复核证据；score=null表示撤回该项修正，恢复机器原分。修正不能改写ratings、criteria或脚本结果。

新回收或新机器报告后旧修正不再适用；同快照仅复查程序时，按U74保留原报告及对应修正，最新程序事实另列。全部历史继续保存。后台检查期间拒绝修正，过期提交拒绝。新方案最终分包含当前有效修正；同条件自动比较暂排除人工改分项，要求完整机器覆盖及相同裁判模型/档位/镜像/CLI版本，避免人工结果混入自动排名。

必要项结论沿用冻结契约：关联脚本失败或条目partial/unmet→not_met；条目未核实或必要检查缺失→unverified；全部met且相关检查通过、交付完成→met。没有必要条目→not_configured。此结论与数值分数独立。

## 6. 旧记录兼容

旧v1/v2仍是 `S = O×objectiveWeight/100 + H×humanWeight/100`。O是完整预定脚本集合中的通过权重比例；H是适用人工维度加权分。旧AI仅辅助意见；旧objectiveReviews的人工裁定单列，不改原分。旧记录不自动迁移，不将既有AI意见重新解释成机器评分。页面说明新建评测已改用机器方案。

旧人工复审的criteria/个人约束/dimensionEvidence/readiness/revisionReason与文件、检查引用校验继续保留。旧缺检查且客观权重大于0的百分比方案仍按原规则拒绝创建；新机器方案不受此限制。

### U25 裁判默认、独立上下文与监控

评分页面默认 gpt-6-luna / max。模型在本机目录不可用或档位不受支持时阻止启动；账号实际不可调用若在启动后才获知，则作业标记未完成并显示失败原因，不静默切成 Sol/medium。请求携带 reasoningEffort，后台再查本机已知模型能力；报告保留实际模型/档位/CLI版本/环境。跨次质量参考分按裁判模型、档位、提示词版本与评分方案核对，不同协议不可直接合算。

裁判引用校验先匹配原始命令输出；完整 JSON 输出中，允许引用同一对象里原顺序连续的键值片段，以适配美化缩进与单行引用，但不接受跨对象拼接、改值或换序。报告末尾恰好多一个 `}` 时可窄范围解析，原始报告仍保留并标注修复方式；其他截断或多余文本继续失败。引用无效只使对应项未验证，不能为了形成总分补造证据。旧报告可在同一冻结快照上离线追加重校验，无须再调用裁判模型。引用通过只证明证据存在，不证明主观评分准确；视觉和交互仍需独立核对与人工校准。

本机每次创建新的 codex exec --ephemeral 进程、临时 CODEX_HOME 和独立产物副本，只临时复制登录凭据；不 resume、不继承宿主规则/用户配置或旧评分会话。原快照保持不变。它是 CLI 独立审查，正式被测执行仍在桌面。这里隔离的是会话/配置/副本，不是全新操作系统：宿主工具、网络、依赖和模型本身仍影响结果；不承诺完全免疫产物中的提示注入。

评分页“评分过程”展开后轮询只读接口，显示准备/执行/完成/失败/取消/中断、job目录及真实 command_execution 命令、输出、退出码。不展示模型内部思考事件，不把尚未输出当卡死；截断只影响页面，原始日志留在本机。通用凭据模式脱敏，不向公网发送。失败任务也能看日志；开始新任务时不混入旧任务命令。

准确性仍待校准：冻结量表、引用和真实命令校验能约束证据，不能证明分数正确或消除随机性。机器先评、人工修正另存；不自动择优选分或捏造误差范围。U72新增同次预算内一次缺项反馈，与另行发起独立复评不同，具体合同见下文。后续可靠性验证需固定样本多次评分并对照人工标签，当前未完成。依据：[OpenAI评测最佳实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，建议用人工判断校准自动评测并考虑模型输出波动。Windows 本机浏览器取证仍未接通，不以本轮监控功能宣称视觉评分已解决。

## U33–U34 裁判控制与两类判分

裁判请求增加reasoningEffort（空串=不强制）和timeoutSeconds（60..28800整数，默认3600）。明确能力的模型仅允许支持的档位；当前Harbor不支持ultra和自定义提供商。每次独立进程、临时home、无会话恢复，实际提示词与公开命令/消息可查；新会话不能消除模型训练偏差，也不等同VM隔离。预算耗尽状态budget_exhausted，无新分数，保存证据；环境异常与程序不通过分开。

基准验证主要展示原题程序/公开协议结果；AI分为补充质量参考。真实项目使用需求与质量量表。当前展示依据publicSource或checks推断，不改写历史policy；不是按Bug/构建推断。缺原验收器明确未接通。所有分数附参考性说明。八项榜单与开源框架依据见../research/benchmark-scoring-20260923.md。

人工复核不依赖AI报告：humanAssessments按captureId+captureHash绑定，只接受适用维度、0..100分和非空观察依据；覆盖率=已评分维度权重/适用权重，参考分按已评权重归一化。UX项必须声明实际界面体验。此结果独立于机器原分、machineCorrections和程序结果，不进入旧综合分或官方通过率。审查途径包括校验快照文本/惰性图片、独立副本、用户明确启动及本机预览地址。尚无自动浏览器、盲评配对、多裁判或可靠性校准。

## U35 Fast 裁判与旧报告重校验

本机 CLI 裁判支持显式标准/Fast 选择；Fast 只在模型目录声明能力且环境为本机时允许，固定命令参数包含 `service_tier="fast"`、`features.fast_mode=true`。标准模式显式传 `service_tier="default"`，这是 Codex 用于拒绝模型目录默认 Fast 的原生值。Harbor 适配未验证透传，拒绝 Fast 而非显示虚假的勾选。报告记录请求档位，不把请求值说成服务端实际测速；费用比较仍按已记录的API标准价等值，不把ChatGPT订阅扣额换成美元。

裁判提示词限制每个维度/需求优先引用不超过20条；校验器能逐条验证至50条。超过50条仅降级对应项，其他有效项保留。对已保存的本机或 Docker 校验失败报告，可在同一 run/trial 的最新冻结快照与原回答、原始命令日志上重新校验；本机读取 `answer.json` / `events.jsonl`，Docker 读取保存的 Harbor `agent/codex.txt` 最终消息与命令记录。要求原校验错误记录与 captureId 匹配，旧原文不改写，不启动新模型。单条引用无原文或不能定位时剔除该引用并显示警告；同一评分项仍有经核对的运行/文件引用时保留其分数，全部引用失效才让此项保持未评。此操作只校验引用存在，不判断余下引用是否足以证明审美结论。成功追加新评分版本和来源 `revalidatedFrom`，保留原运行结束时间，复核时间单独记录；结构错误、原报告缺失、新回收已出现、快照变化、运行中/归档/删除中均拒绝复用。

## U46：连续单题分与配置分（已批准；v1 已接入，校准仍在进行）

用户已批准按题连续分、多题配置分及多类型题方向。现有公开题 reward 与本地任务分、配置分分开：reward 是上游原题通过/失败的事实，本地分评价此题交付完成程度，配置分评价当前完整题集下同一配置 revision。原题失败允许本地任务分大于零，但不能把本地分写成“DeepSWE 官方得分”。以下目标合同中已实现部分与尚待校准/扩展部分分别说明；不能把设计条款一概称为已交付。

### A. 评分卡与单题公式

1. 每题从**原题面与用户已声明的目标**形成稳定 ID 的验收项：目标、验收锚点、必要程度、权重、可接受证据、来源、是否允许人工修正、不适用条件。总权重 100 分。一个需求可以有多条测试；一千条回归测试不因数量是一条目标测试的一千倍而自动分走一千倍权重。题目、起点、量表、检查器与成本预算在新试次执行前冻结。
2. 每项完成系数 `r_i` 在 0 至 1：0 表示确证没有实现，1 表示该项全部必要行为有证据，中间值必须对应评分卡预先写明的可区分部分目标或质量锚点。原题脚本、独立追加测试、实际运行、浏览器交互、文件及截图、有效 AI 引用、人类操作观察各按适用性取证；“有代码”“模型自述”“用例数量多”都不自动给分。
3. `S_task = round(Σ(w_i × r_i), 1)`，`Σw_i = 100`，`w_i` 单位为分。必要证据未知时最终分为空，保留已取得的分项、缺失原因、自动安全重试和补验入口；不能把局部分按已评权重归一成整题总分。实际验收失败是已知未达标，不得伪装为环境未知。不适用项应在冻结时移除并重配权重，不能看过结果才排除败项。
4. **已批准的本地 v1 起点**：SWE 工程题用“本题目标 70 / 旧功能与边界回归 20 / 工程质量 10”；开放项目用“用户目标 60 / 实际使用与可靠性 25 / 交付可维护性 15”。这些是本产品本地量表，不是官方标准。前端项目把实际浏览器/UX 纳入体验项；无网页题不填视觉。必要目标不能因好看、测试数量或便宜而被掩盖。
5. 既有五题只读上游题面、测试和冻结快照进行**统一版本的追溯重评分**；由于执行已发生，须标明追溯，不能宣称预注册。不得看到某配置得失后专门改某题权重。以后修订量表另起版本，并对全部可比试次同版本重算，原报告、原页面分和上游 reward 永久留存。

Anko 说明此规则为何必要：当前 F2P 1/2、P2P 119/119，原题 reward=0；`120/121=99.17%` 只是原始用例通过比例。题面要求默认参数语法、缺参赋值、调用时从左到右求值、非法声明报错及不依赖外部生成器。失败的 `TestDefaultArgumentsVisible` 必须让对应语义目标失分；119 项旧功能回归只能证明它们覆盖的旧行为，不可冲淡核心失败。具体新分在条目映射和工程质量证据核对前不能凭这两个分子猜出。

### B. 按题适用的能力指标，而非固定四项滑条

|能力/指标|何时适用、主要证据|计分和人工权限|
|---|---|---|
|需求切中、目标完成|所有题；逐条目标、可运行主路径、文件/脚本验收|主权重；可复核需求解释，硬测试结果只读|
|程序正确性、回归与边界|仓库/软件题；原题 F2P/P2P、独立测试、构建和异常路径|按语义组计权；脚本假阴性应复验，不用滑条改写|
|模糊需求澄清与范围控制|需求探索、项目经理式任务；澄清记录、目标决策、是否无授权扩张|有锚点的主观项可由人复核|
|逻辑推理与工程判断|规划、复杂数据/算法/架构题；前提、论证、反例、可执行设计|以证据和同题盲评补充，不用数学问答分代替项目结果|
|前端功能、视觉、无障碍|网页/交互题；浏览器操作、窄屏、键盘、截图、实际体验|程序交互和人的视觉判断分存；纯静态读代码不足|
|工程质量、维护与交付|代码/长期项目；结构、接口、测试、说明、接手复现|主观项可修，必须引用具体文件和观察|
|安全、持久化与健壮性|题目或使用风险确有要求；反例、权限、数据恢复、异常|必要禁令不可被视觉分冲抵|
|跨阶段连续性与返工|多轮长期项目；版本、里程碑、旧需求回归和返工记录|同一项目各阶段只是一个试次的轨迹，不算多个独立样本|
|对话体感与人情味|真实协作过程；是否直答、解释清楚、恰当澄清、尊重用户决策|人类按锚点观察并可调整；不以客套词数量打分|
|稳定性|同题同条件重复，记录成功率与分布、故障原因|配置层跨试次指标，不凭一次结果给“稳定”分|
|成本和速度|被测执行的真实 Token、缓存、时间及价格假设|默认并列效率轴，不拿低成本抵消功能失败；原生日志只读|

这些是指标库，不是每题必须填写 11 项。外部截图中的 Academic、Health、Vision、Agentic Coding 多数是题集或能力域，不是 SWE 每题评分栏；不同榜单的百分比、Elo、rating、成本不能直接平均。完整来源、专业指标与适用性见 [榜单研究](../research/benchmark-scoring-20260923.md)。

### C. 人工、复验、缺项与长任务

- 原题 reward、测试结果、实际 Token/时长、快照哈希、命令退出状态保持只读。人工调整只在需求解释、视觉、交互、对话体验、工程判断等主观项给新分；必须绑定快照、列出观察和理由。最终数值由条目重算，机器原分、原始报告与每次调整留档。程序疑似误判走同一版本的独立复验/申诉，不由用户把硬结果拖成通过。
- 多阶段项目在准备时冻结最终目标、已知约束和“允许澄清”的边界。每一阶段留下要求变更、决策、文件版本、可操作里程碑、检查和人工介入；阶段结束可给诊断性进度，但项目最终分只针对最终快照、全程必要项和最终回归。用户后来改变需求形成新契约版本；不能拿后来的要求追罚旧阶段，也不能让被测模型自行重写原始评分标准。一次长项目仍是一道题，五个阶段不是五次独立样本。
- 预检在消耗被测额度前检查固定源码、镜像/运行时、验收器、浏览器取证能力和评分依赖；软件失败自动安全重试并在本机留下原因/日志。可从已回收快照补验收，不要求模型重新做题。无法取得必要证据时不发布最终分，明确“系统待修复/待补验”，并在工作台提供继续入口。用户不应逐题手动配置 Docker 或逐个建 113 个文件夹；开源文档给出自动准备、故障诊断及可复制的低成本辅助配置提示词，但提示词不能代替依赖锁定与实际运行验证。

### D. 配置分、比较和结果页

- 当前批次只在计划的全部题有有效单题分时显示批次均值。配置历史将同一 `configId+revision` 下、同一题目版本和评分协议的重复先求均值，再对具名题集中的**不同题等权**。若题集版本在执行前声明题权 `a_t`，则 `S_config=round(Σ[a_t × mean_repeat(S_task,t)] / Σa_t, 1)`；默认各 `a_t=1`。页面展示题集版本、全部题/有效题数、逐题权与分、排除理由及截止时间。有新题正在跑时保留“上次完整题集分”和日期，不能把已评分的少数题冒充新全集分；不能事后按输赢调权。
- 不同题目的 0–100 使用各自冻结的“目标满足程度”刻度，跨题均值是**该用户题集的决策摘要**，不是经过等难度校准的模型能力尺度；简单题高分和困难题高分不能据此宣称等量能力。按领域展示子分与覆盖，并允许用户在运行前明确更重视哪类题。若任务评分卡未校准或题集组成不同，保留逐题证据而不拿两个配置分直接排行。
- 跨配置比较必须共享题目、起点、模型、思考档位、速度、预算、评分卡、原题验收器和已知宿主条件；有多变量改变时标组合比较。逐题配对差值、两配置汇总差、重复分布、失败/中断与人工介入同屏。不同领域可以构成用户自选题集，但必须同时展示项目/前端/SWE 等子领域画像，不称官方通用模型排名。
- 成本与速度在结果主卡可见：被测桌面输入/输出/缓存 Token、活动区间、总历时及可识别等待；裁判调用单独记账。若只有价格表推算，就标“API 等值估算、日期与假设”，不能称 ChatGPT 订阅实际账单；缺字段留空。可画质量—成本/速度 Pareto，默认不把花费折成质量分。成功但贵、便宜但失败应由用户看清取舍。
- 单题页面直接显示一个本地综合分、逐项权重与贡献、必要项结论、原题验收状态、人工修正和证据链接。配置成绩页显示一个当前具名题集配置分、逐题分、领域分、覆盖、成本/时间与稳定性。可保留 1 位小数便于核对计算，但 0.1 分不是已验证的分辨能力。具体 UI 目标见 [前端合同](../FRONTEND_SPEC.md)。

### E. 差异很小时的可信边界与实施验收

比较以同题**配对差值**为主，而不是比较两个碰巧抽到不同题的平均分。固定锚题和预算；探索用低成本少量题，确认集的题目与决定扩大的条件事先写明，不能只挑某配置有利的题发布。关键题允许独立重复和同题匿名成对偏好判断；记录评审者、顺序、所有失败及中断。需要区间时先写清题目/独立试次作为抽样单位、缺失处理和假设；样本不足或区间跨零时写“尚不能判断”，不捏造固定误差带或宣布 0.3 分胜出。流程细则见 [用量与比较](MEASUREMENT_AND_COMPARISON.md)。

**已实现的 v1**：`src/chb/arena/task_scorecards.py` 为五道已实际验收的 DeepSWE 题固定目标语义组，70 分按组是否全部通过计，不按 F2P 用例数简单均分；P2P 整组占 20 分；已有、引用已校验的独立 AI 可维护性维度占 10 分，人工只可对这个主观维度留下理由和新值，不能改原题 reward 或 F2P/P2P。当前五份冻结快照**追溯**得分为 Adaptix 98.8、Anko 61.8、AioMonitor 98.3、Actionlint 98.7、ABS 98.3；同一批不同题等权得 91.2/100。Anko 的“默认参数加载”35/35、“语法与调用可见性”0/35、“回归”20/20、“工程可维护性”6.8/10，原题 reward 仍为 0。AioMonitor 的旧通用 AI 维度覆盖 17.65% 并未被重归一成总分；本地卡用已跑完的目标/回归测试和有效的可维护性证据计分。五题未重新调用被测模型；运行记录有无 `localScorecardVersion` 区分预注册与追溯。未来上游测试清单变动或少测试明细时不猜分。

对 **U47–U50 期间创建的开放项目**，本地评分卡将有效 AI 取证映射到固定 60/25/15：目标为 intent 50+instruction 10；无界面题的可靠性为 verification 10+robustness 15，有界面题为 verification 10+robustness 5+ux 10；交付为 maintainability 10+handoff 5。配置的程序检查失败把 verification 子项置 0，未运行或环境错误使该项未知。旧开放项目历史算法不追溯改写；该映射是本地 v1 工程方案，尚未完成人类盲评校准。

**U51 新建开放项目**使用 `project-policy-v1`：创建评测时把已选标准评分项 ID、说明与权重一起冻结；对本题适用的正权重项归一为 100 分，单题分为逐项得分乘归一权重之和。无界面题排除 `ux`、`visual`、`originality`、`responsive`、`accessibility`；配置的程序检查失败把 `verification` 限为 0，尚未完成的检查让该项未知。任一适用项没有有效引用，整题分为空，绝不按已测项重新放大。机器原分和人工修正留痕；雷达从同一冻结评分卡读取逐项 **原始 0–100 分**，不再乘权重，程序检查限制后的验证分在雷达和单题卡一致。旧开放项目仍按固定卡计算；公开 DeepSWE 继续使用原题 reward＋独立 70/20/10 本地卡，不受网页/协作 AI 量表权重改变。评分方案可选通用、工程、网页、业务数据和长期协作预设，也可增减独立标准项；选项只是取证要求，不代表已经测得能力，网页需实际界面证据，长期协作需过程记录。配置对比按冻结协议隔离不同方案。

前端单题卡展示权重、贡献和证据；配置卡优先显示最近完整批次的等权分。旧批次的原题 reward、AI 原始七维和人工修正保留。宿主指纹变化不抹掉单题/批次分，但跨配置控制变量比较受限。**尚未完成**：其余 108 道公开题的语义评分卡及全部上游环境、持久化具名题集版本/自定义题权、同题跨批重复汇总、AI 裁判与人工盲评校准、完整长期项目过程评分和小差异统计推断。缺必要证据保持空值，不以已知项放大成总分。

### F. 细分分数怎样避免“看似精确，实则随意”

设计每道题的条目时，先从需求写**用户可观察的行为**，再定义互不重复的语义目标和必需/建议层级；每个目标给出 0、部分达成、完全达成的具体锚点。部分达成可用事先声明的子目标完成比例，或者同一个行为在代表场景中的分级表现；不能事后凭感觉给 73 分。脚本通过数仅作子目标证据，需审查是否多个用例都在重复测试同一行为。相反，一个致命失败应标必要项未通过，页面将“有一些分数”与“验收通过”分开。

以下只是**公式演示，不是任何真实试次结果**：一项开放网页任务预先定“主要流程40分、数据持久化20分、浏览器体验20分、交付维护20分”；相应证据系数若为1、0.5、0.75、0.5，则任务分为 `40×1+20×0.5+20×0.75+20×0.5=75.0`。每个系数背后仍必须能点开看到具体场景、文件或操作回执；若浏览器根本无法启动，那一项是**未知**，不能把另外80分按比例放大为93.75，也不能随意填0。SWE题采用同一计算机制，但锚点偏重本题语义目标与回归；网页和对话项不适用时在执行前不纳入其题评分卡。

**校准与分辨率**要在发布本地评分方案前实际检验：用故障起点、参考正确实现、故意只完成部分目标的多个候选和不同质量网页样本，确认评分次序符合预先锚点；对模糊题让至少两名独立评审在不看配置名称的情况下评分，记录分歧、仲裁及锚点调整。评分卡若不能稳定分辨明显好/坏产物就不能用来判断 1 分差；改锚点产生新版本，对全部可比候选统一重新评价，保留旧版。AI 裁判需用这些人工标签验证错误与漂移，必要时只做收集证据助手。没有复核样本就不得宣称已校准。

配置差异的 0.1 分显示来自算术，不是统计有效位数。若两配置的微差小于同配置独立重复、评分者分歧或环境漂移，报告“观察到差值，尚不能归因”；必要时追加预先设定的重复和盲评。可在结果中并列显示原题 reward、连续分、必要项结论、评审不一致和成本/时间，不再用单个数字掩盖这些不同性质的事实。

### U52：现行自动题型评分卡与六轴诊断图

呈现：专项失败具有独立失败状态，不能被多个通过项或AI高分平均掉；配置对比资格为 `task-check-fail`。专项全通过仍不自动升级为可比较，因为其未覆盖完整需求与审美；沿用U62的参考分限制。评分页先看功能证据，再看AI质量参考。原题reward、历史连续分、人工修正继续分存。

所有机器评分新增 `judgeReliability`：仅合并同快照、同模型/档位、同提示词hash、同冻结需求/评分方案/验收器、同环境/镜像/CLI/速度的独立job。新报告的judgeComparisonKey排除检查时间、耗时及通过/失败等观测值，保留输入条件；否则每次重新运行检查都会造成材料hash变化，复评永远无法比较。旧报告无此键时，保守要求完整材料hash和evidenceKey一致。重解析同一job、重复job不算新样本。协议字段不足为未测；两次及以上显示各维度有分样本的min/max/极差，不杜撰置信区间。重复一致不证明判断正确，`calibrated=false`。默认仍Luna/max；此模块不启动模型、不改变原分。

AI新提示词版本 `arena-judge-2026-09-28-behavior-v4` 读取专项结论与未覆盖范围，要求保存冲突而非以高分抵消失败。提示词变动本身不是准确性提升证据，旧v3报告不改标为v4。新旧提示词的人工锚点评测、遮蔽身份后的复评、位置/文风偏差、独立人工一致性尚未实测。研究依据：[MT-Bench裁判偏差研究](https://arxiv.org/abs/2306.05685)、[SWE-bench程序验收](https://www.swebench.com/SWE-bench/guides/evaluation/)；二者不能替代本产品校准。

验证入口：`.venv/Scripts/python.exe -X utf8 scripts/validate_frontend_behavior.py --build` 只使用Docker和合成测试替身，不调用模型。包含5个可通过正例、无效按钮、错误总量/环比/逐日值、无效绘制/撤销/清空、导出旧图、静态游戏、暂停失效、重开失效，以及定位歧义、自然动画、合法整数放大、图表标题干扰。测试替身不进入题目起点；日志在忽略的 `.local/qa/`。这些夹具验证检查器敏感性，不能宣传为生产作品准确率。

剩余正确性验收：扩展任务语义覆盖并设置独立保留负例；公开题继续原生测试，并以nop/oracle验证环境；AI主观项需要冻结标注集和独立复评，比较错误判高率/错杀率/逐项偏差及分歧，而不是追求更低均分。没有独立参考标签时，不认证裁判准确率、不宣布1–2分优势。

## U64：通用等级与原始需求协议

### 问题、目标与适用范围

原协议允许模型直接输出0–100，引用存在并不证明结论正确；仅有几条手工criteria会遗漏题面要求；五题专项脚本无法扩展到所有新题。新模块 `judge_protocol.py` 对所有新机器审查（包括自定义维度、公开题的补充质量评价）使用 `anchored-observations-v1`。原题程序reward、专项行为验收和人工修改继续分存。它降低随意计算与遗漏的空间，不把模型观察变成客观真值。

### 冻结输入与逐条检查

1. 裁判包只含当前审查范围的冻结题面、产物、检查记录与规则；模型身份、开发对话及参考解不作为评分输入。工作区继承关系及本机沙箱读取限制仍按执行合同说明，不能泛称完全隔离。
2. 从 `inputPrompt` 与当前 `stages.prompt` 按句号、分号和换行提取条款、去重，代码块整块保留；分阶段审查排除总体未来目标。多于48条时连续分组，不丢失文本。编号R001起；它们是原题原文，不由裁判自由重写需求。
3. 原有 `task.criteria`（WebGen包括UI操作及expected_result）另行完整检查。裁判对两组分别返回met/partial/unmet/unverified与具体证据；复合条款须全部成立才能met。没有依据不能因条款难测而删掉。
4. 合同内容与SHA-256存入packet和报告。历史报告不带此协议的仍按历史解析；保存报告复验不会静默套新公式。

### 等级与算式

每个适用维度均有三个等权观察：coverage需求覆盖、quality实现质量、resilience反例/遗漏检查。每项必须给预期、观察和缺口，等级只能整数0–4或null：0核心失败，1重大缺口，2部分成立且有实质缺陷，3要求成立但有次要问题，4完整成立且主动反例检查有直接依据。没有适用的动态边界时，检查本维度遗漏/不一致，不发明题外要求。null代表未验证，绝不等同0或100。

- 细项基础值为等级×25；维度为三个细项均值，缺一项则维度null。
- 等级4必须有通过引用校验的 `counterEvidence`，且至少一条与正例引用不同。重复引用、不存在命令或文件、缺少反例会留下明确原因并使该细项null。
- UI、性能、功能、验证、健壮性、运行交付需要运行记录。规划/协作文档的目标、交付和一致性可依据静态产物，不强制虚构运行命令。
- intent覆盖与质量受需求完成率上限约束。原criteria与原题条款各自算met=1、partial=.5、unmet=0的均值，取较低上限；任一组含unverified则这两项不能形成已验证分。分组取较低值避免大量容易条款稀释一个失败的明确验收项。
- 冻结单题评分卡再按维度权重聚合；维度和总分都没有extra/bonus。额外功能、代码长度和模型名称不加分。程序失败/必要项失败仍保留原有独立门槛，不能被漂亮界面平均掉。
- 细项等级是原始观察，受需求约束后的贡献可低于该等级基础值；UI同时显示constraint。三项平均并不代表百分之多少真实能力。

### 格式、故障与历史

结构错误拒绝报告；缺少单个细项保留其他合法细项并标未知，不丢整份证据、不补假分。旧直接score字段无法绕过新checks协议。已有解析/引用修复只修可证明的格式和定位问题，不能替模型补结论。模型未返回结果、环境失败、预算耗尽继续与作品失败区分。裁判默认仍Luna/max，本轮没有实际模型调用。

### 验证与未完成边界

用离线固定证据测试五档算式、无奖励、缺项、假/重复反例、静态冒充功能、未知需求、失败上限、长题面无丢失、自定义维度、规划静态依据和协议回放。模拟Harbor传输覆盖新协议解析。它们证明程序门槛及数据流，不证明Luna或其他裁判会正确观察真实网页。

可复现的同一错误判断仍可能产生高分；引用不同也不保证语义上真是反例。后续可信度验收必须用未参与开发的匿名正/负/边界交付、人工锚点与独立复评，测关键缺陷漏检、高分误判、顺序逆转、弃评率及实测波动；保持calibrated=false直到有这些数据。原有U63五题32项行为检查继续可用，但不能宣称其余题也有专属浏览器脚本。详见[方法研究](../research/unified-scoring-20260929.md)。

## U65：裁判传输一致性修复与交付结果分离

发现本机execute_local的--output-schema仍强制旧ratings.score格式，而v5提示词已要求ratings.checks和requirementChecks；这会使模型无法同时满足两份合同。现按冻结scoringContract.version生成同一结构：每个适用维度coverage/quality/resilience，每项level为0/1/2/3/4/null，method/reason/evidence/counterEvidence；原criteria及全部冻结条款是必填键。无scoringContract的历史材料继续旧结构，未知协议拒绝。此次未改变锚点版本或旧分数，没有切换Luna/max默认，也没有通过重复付费调用掩盖格式问题。

该修复针对本机结构约束，不能声称解释此前所有Docker失败。Docker仍由Harbor执行，输出经现有解析与同一validator；模型拒绝、预算耗尽、环境故障仍可能没有完整报告。原题程序验收已可在Harness对照报告独立形成交付事实，无需AI报告成功。AI分数依然是辅助诊断，通用烟检及截图文件存在不构成整体验收。

验证包含新/旧schema、必需原文条款、等级与反例字段及未知协议；程序验收通过无需AI、假高分不代替验收、缺失不补零、失败不从分母消失等回归。代码测试通过不能证明真实模型已稳定输出，也不能证明视觉评分已校准。

## U68：机器审查增加真实对话证据

## U69：固定程序事实不再等待AI分

fixed_suites.summary核对协议、题号、有效测试SHA、固定用例集合、镜像digest、argv和当前快照检查记录；截断、缺项、矛盾回执或预算耗尽保持未知。programAcceptance逐项展示，缺项不归零或减少分母。函数整套判定与社区核心比例不同，不跨题混为总质量分；AI不能覆盖失败。HumanEval+163题保留原扩展断言，32号有错误被排除；社区8题77用例只认证声明核心。具体正反例/缺陷与视觉缺口见U69研究；不能以验证器回归代替真实裁判校准。

## U71：单题、配置与雷达的显示来源

结果总览直接显示score.overall，贡献表读冻结taskScorecard.items；已评分项均值score.machine只是AI参考，缺项不重放大成单题总分。旧策略先按旧objective/human权重解释，不把旧分冒充新连续卡。公开原题的reward、F2P/P2P与跨试测通过率保持独立；五道已核对DeepSWE卡是语义组70、回归20、维护性10，其余公开题仍没有该连续卡。质量审查入口对公开题开放，但不能替代原验收。

六轴沿用capabilityProfiles的真实分项来源；原题卡只可能映射目标功能、可维护性与回归，不推导网页/推理/协作分。配置成绩同题、同版本、同协议重复先均值，再对不同题等权；不符合配置资格的记录保留逐题参考而不冒充可比成绩。对话观察是逐回合诊断，未额外加权；只有本来冻结的相关维度才可能影响该记录的分与轴。

## U72：同预算的裁判自动补查（review-feedback-v1）

新机器审查使用提示词arena-judge-2026-10-02-feedback-v7。本机和Harbor共用run_judge包装，最多两次取证，即首次检查加一次反馈；仍使用原来的0–4等级/需求约束和冻结公式。先要求裁判自查引用及最高等级反例，平台校验后把格式、无效引用、缺细项与可取证的原题遗漏反馈给裁判。合法零分/低分不反馈；环境、权限、额度或未提供材料不是让模型补猜的理由。

补查创建新的独立CLI副本，由裁判读取前次原报告/真实命令和有来源的截图，主动补取证、纠正引用或选择证据支持的等级，返回完整报告。原始报告/日志不改写；平台不替模型赋值，不修候选作品，不合并择优分数。保存最终有效报告与automaticRepair回执；若补查预算或环境失败，保留此前有效报告和部分观察，缺项继续为空。

时间截止点涵盖本次两次取证，不为补查另开完整预算，剩余不足60秒不启动。模型、档位、速度、快照和连接参数沿用；补查前核对凭据/提供商指纹，变化即止，不换号或切换模型。取消、快照变更及已知故障按既有保护处理。逐次jobId/原因/seconds/usage和累计judgeUsage留存；同一job去重，任一次用量未知则总用量未知。进度接口累计前次与当前实际作业。保存报告重新校验仍不调用模型，从原job重读前次命令并校验同capture，保留两次资源。

judgePromptSha256代表基础v7评分流程，judgeFinalInstructionSha256保留实际补查指令哈希；protocol保留previousReviewJobId和两者。反馈尝试不是独立可靠性样本，不用两次有依赖的取证声称重复稳定或已校准。默认Luna/max、旧报告、评分方案和原验收reward不变；旧记录不自动付费重评。此机制解决可补查遗漏无人处理，不保证任何环境都能验收，也不证明AI理解与视觉判断正确。

## U73：结果存在与评分完整性分开

原题有效reward=0为失败结果，不因质量报告缺失或无本地连续卡而消失。前端从nativeVerificationId及当前manifestHash绑定报告读F2P/P2P比例：各自passed/total，total必须正整数，passed须在范围内；未验收/失效报告保持未知。比例诊断进展，不能混合大量P2P稀释目标失败，也不改变原题reward。配置原题已验收计数包含失败，无需AI；对照交付统计仍使用既有程序结果，不改成质量分。

task_scorecards增加只读observations，保留三组内每个细项冻结权重与有效贡献。calculate_machine派生scoreProgress，不修改原overall/items.points、量表、报告或历史。knownPoints为已测贡献之和，unknownWeight为未测权重之和，范围按原评分卡的组内舍入/最终精度计算[已确认贡献,已确认贡献+未测权重]；未知不置0、不重新放大分母。自定义卡沿用其已归一冻结权重，合法零分属于已测。自动程序检查失败限制verification=0，未执行/环境问题保持null，均沿用旧公式。

范围是基于现有评分项的算术可能值，不是AI误差、统计置信区间或完整评分。已评分判断本身仍可能有误，引用有效不等于校准。界面解释真实缺项，区分旧快照、同快照验收记录改变后的evidenceKey不匹配、辅助意见与机器报告、程序未执行、反例引用缺失；补查入口不发起模型调用，实际启动仍由用户确认额度。没有程序验收器不等于不能收集AI/人工体验，但不能据此宣告程序通过。

## U74：复查只更新程序事实，保留原AI判断

此前evidence_key同时含capture id、manifest和当前checks，重跑时checks被清空并替换，导致AI报告和修正被误判过期。现使用同capture的checkAttempts.results重建原键，且始终使用当前manifest；匹配后选择最新有效机器报告。无法证明对应历史的键不接受，换capture或manifest也不接受。旧报告无需迁移、覆盖、重新调模型或改量表。

machineEvidenceKey为选中报告原键，人工修正仍绑定该键及reviewId；objectiveEvidenceKey继续对应最新程序检查，旧程序裁定仍失效。machineCheckEvidence为原报告审查时采用的检查，machineChecksChanged表示当前检查键不同。原AI分原样保留，当前检查仍按既有规则限制verification与配置资格，失败不会被AI质量分改成通过。

开放题的通用网页烟检只列基础运行事实，不展示为独立整题程序验收。此项显示调整不移除旧检查，不改变冻结verification权重、原题reward或所有null的含义。沟通比例是逐回合诊断，具体未知分母/查原话规则见前端合同U74。
