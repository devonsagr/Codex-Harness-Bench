# 用量、效率、误差与结果比较

负责 D15-02/03/05/06/15/19；主要工作包 B06/B08。

## 1. 为什么这些限制是产品前提

用户关心的是小幅 Harness 修改是否值得采用。在同一模型上，任务差异、运行随机性、上下文、全局环境及评分者判断，都可能大于规则修改本身的收益。因此结果页必须同时展示观测值、条件和未知项；不能只在 FAQ 留一句“存在误差”。

这个项目没有承诺100%正确，也没有测得固定±2或±3分的误差带。单次胜出、一次 AI 无意见、一个测试通过都不足以证明 Harness 更好。

## 2. 各指标的现有来源

|指标|现有读取规则|界面/验证边界|
|---|---|---|
|inputTokens|原生日志最终累计 input_tokens|含缓存输入，不再另加缓存|
|outputTokens|最终累计 output_tokens|与输入相加形成当前totalTokens|
|cacheReadTokens|cached_input_tokens|必须≤inputTokens；不自行推断计费折扣|
|cacheHitRate|缓存输入/输入×100|输入为0或未知时为null|
|reasoningTokens|若日志有 reasoning_output_tokens 则返回|当前后端可读，前端主指标未呈现；该字段校验/语义需补齐|
|totalTokens|input+output|不能再把 reasoning 或 cache 盲目加一次|
|activeSeconds|明确开始/完成事件配对的累计间隔|是日志活动区间，不是纯模型推理时间；工具和区间内等待可能包含其中|
|cost|后端真实账单字段当前为null；执行详情可按版本化公开价格表估算 API 等值区间|执行页已有估算，但配置成绩主卡未突出；估算不是 ChatGPT 订阅实际扣额，不能将其写进真实账单字段|
|检查耗时|后台检查实测单调时钟时长|包含检查生命周期开销，不等于模型执行耗时|
|AI复审用量|保留在本机或Harbor复审记录|与正式桌面用量分开，不冒充项目产出用量|

原型还设计 executionLatency、tokensPerSecond、varianceMargin。当前并未可靠采集完整吞吐/首响应/误差；不能补随机值或仅凭界面字段算出貌似精确的数字。

## 3. 日志绑定与重复导入

页面活动时服务最多每5秒只读查询Codex最新state_*.sqlite，按精确工作区cwd选取对应session日志，不遍历所有会话内容。Windows规范化长路径/大小写；日志路径必须在Codex sessions或archived_sessions内，元数据再次校验cwd/id。首次匹配多个会话时提示歧义，不合并；已绑定后只继续同一会话。仍保留用户手动选择本题JSONL入口。要求 session_meta 的 cwd 与准备工作区匹配、session ID 唯一；多轮继续导入同一会话。对输入、输出和缓存累计值校验非负、顺序不回退，保存最后累计值，不逐行相加。

手动导入保留原文私有副本、hash和摘要；自动读取持久化摘要/绑定信息，不反复复制完整日志。后导入的累计值不能比已保存更早或缺项。日志中的模型和档位与配置不一致/缺失时标为条件未确认，而不是修订历史配置来匹配它。

当前解析器支持已知结构，不是所有 Codex 版本的通用分析器。B06 要增加协议版本、reasoning字段校验和不完整事件诊断；遇到未知结构明确保留未知，不猜测用量。

自动读取不会因用户忘点开始漏掉此前累计Token。运行中的未闭合时间段保持未知，不以页面开启时间伪造执行时长。日志缺失、结构不支持或多会话歧义会给出原因。原生输入含缓存，图表将其拆为缓存/非缓存，不再次加总；缺少写缓存或费用字段仍为空。

## 4. 时间与人工介入

目标分开记录：准备时间、桌面活动区间、等待用户、用户操作/反馈次数、后台验收时间、总历时。当前只有部分时间戳和日志活动秒数，没有完整自动拆分。

例如某阶段10:00开始、10:05请求确认、用户14:00回应。不能直接把四小时解释为模型生成慢；如果日志无法可靠定位等待，显示总历时和“活动/等待尚未分离”。配置原本要求分阶段确认时，该等待也不是质量扣分理由。

用户补充澄清、修改要求、提供代码或手工修复，都可能改变条件。目标记录介入类型与内容摘要，区分计划阶段提示词、必要澄清和额外修补。不能只统计轮次少就奖励“直出”。

## 5. 比较前要核对什么

|条件|怎样使用|未知时怎么办|
|---|---|---|
|题目/契约/起点版本|同题比较必须相同输入|保留历史，标不同题或未知|
|配置内容|明确要比较的变量，技能比内容hash|展示变化，不因名称相同视作相同|
|模型/档位|对比请求值与日志观察值|无法归因于单一Harness变化|
|正式执行方式|desktop与CLI分开|不合并正式成绩|
|阶段与介入|确认点、需求变更、手工修复|提供说明，必要时分组|
|评分策略/验收者|相同维度权重、评分口径和版本|不同策略不直接混成总榜|
|环境|宿主已记录指纹、检查镜像内容ID、桌面版本等|列已知/未知，不标完全控制|

现有 Comparison 在 React 中按题目对象、执行方式、模型/档位、策略、宿主指纹和检查镜像分组；要求成绩齐、实际日志匹配、没有条件变化观察。U20机器策略另外要求机器覆盖率100%、没有有效人工修正，并按裁判模型、推理档位、镜像ID和CLI版本分组；元数据缺失的不入同条件组。它只展示综合分、输入Token和活动秒数，没有完整维度矩阵和差异解释。用户仍可在历史找到未进入分组的记录。

该筛选是实现中的保守规则，不是完整公平性证明。后续应为每条排除给出可读原因，并把公共分组计算移至可测试的后端服务，避免浏览器和导出各有口径。

## 6. 如何判断微小变化（目标方法，尚未实现）

1. 先定义问题，例如“去掉规则X后，完整项目交付与等待次数有什么变化”，不要事后从多个指标里挑最好看的。
2. 固定一组有代表性的项目和修复题，分别分析；在相同题目版本上做配对重复。
3. 记录执行顺序与人工介入；多轮是同题连续过程，不能当额外独立样本。
4. 保留未开始、失败、中断、未知的全部数量。不能只挑双方成功的结果证明质量收益；仅对可比较的时长作条件分析时，要说明筛选。
5. 展示每次结果与差值，报告样本量和分散程度。样本过少或条件不齐，结论为“尚无法判断”。
6. 若实现区间估计，必须在独立方法文档声明抽样单位、算法、缺失处理和假设，并用合成已知数据验证。当前不指定一个虚构的通用误差数。

重复执行不是本轮自动开启的任务；需要明确次数、预算和手动桌面安排。B08 先实现记录与解释，统计估计列为有条件的后续能力。

## 7. 异常不能污染成绩

当前桌面中断有人工原因；日志把额度、429及其他异常粗分类。尚未完整区分 context_overflow、网络、取消、超时、工具失败和环境崩溃，更不能自动自愈全部情况。

目标异常记录有来源、发生阶段、已完成产物、是否影响质量判断、恢复所需动作。额度耗尽保持“中断/未知”，不是代码0分；测试确认功能错误是 failed，不应借“环境问题”隐藏。无法判断原因则 unknown，并保留日志供核对。

## 8. 验收案例

- **M-AC1**：同一累计日志重复导入不增加总量；缓存和reasoning不重复相加；错误会话拒绝。
- **M-AC2**：含长时间用户等待的多轮记录，不把等待自动归为模型低效；缺可靠分段时明确未知。
- **M-AC3**：模型/策略/镜像或规则变化的记录仍在历史，分组页解释为何未纳入。
- **M-AC4**：同题两配置单次差2分，页面只展示差值与证据，不宣布可靠胜者或固定置信区间。
- **M-AC5**：额度中断、测试失败和未执行都保留各自状态与数量；不存在筛掉失败后假装100%成功。

开放项目的单题评分卡仅在当前有效裁判报告、全部适用项与必要程序检查均有结果时计算加权总分；不再以“交付结束”作为查看单题数字的前置条件。未交付结束的数字标为暂定，重新回收或人工修正后重新计算；中间阶段不得作为整题成绩。配置题集仍只纳入已结束交付且满足评分协议的题，缺项均值仍不能顶替总分。配置成绩页把当前题集、历史和待补记录分栏筛选、每页最多八项。高分核查直接列出 90+ 题数、重复题、人工评分记录和程序检查数量；次数和引用存在不能证明判断正确，也不构成分数校准。

## U46：精细比较设计与效率结果（待审目标，未实现）

### 被测量、比较单位与有意义的微小差异

1. 单题本地综合分衡量**该题交付证据**，不是模型能力本身。一次配置改动的比较单位是同一题目/版本/起点/模型/预算下的**配对试次**。同一项目的五个阶段仍是一份试次；把阶段当五个样本会虚增可信度。配置分是固定具名题集上的概括，不替代逐题配对差。
2. 先声明待比较的一个主要变化（例如一条 AGENTS 规则或一个 Skill 的内容哈希）、主结果（目标完成/单题分）、次结果（成本、时间、对话体验）与“值得采用”的最小实际收益。没有统一的 0.5/2/5 分门槛；规则带来的收益可能小于模型随机性、裁判波动和人类审查差异。
3. A/B 两配置用同一模型、推理档位、服务速度、题目、评分卡、起点和总预算；交错运行 A/B 顺序以减少时间/服务变动偏差。记录桌面版本、运行时间、全局规则/Skills/插件继承、模型服务端变化线索、人工澄清、外部依赖与异常。宿主条件不能完全冻结时，标明其影响；不得声称绝对控制变量。
4. 同一题重复运行是独立开始的新试次，不复用前次模型会话或看过的答案；每次保留失败、中断、额度耗尽与环境异常。开发者修复验收环境后对相同快照重评，属于**评分重算**，不是模型独立重复。确认集中的任务及纳入规则须在观察 A/B 差异前冻结，不能只挑赢的题。

### 预算层级与统计报告

|层级|建议用途|可以说什么|不能说什么|
|---|---|---|
|3–5 道低成本烟测|启动/环境/严重回归筛查；可含一题 SWE、一题开放需求、一题前端|发现明显故障，知道是否值得扩题|不能宣称微小改动优于基线|
|8–12 道固定跨类型核心集|同题 A/B 配对；涵盖工程、界面、模糊需求和沟通|报告逐题差、均值差、领域差及用量|若每题只跑一次，不能把小差异称稳定收益|
|少数重点独立重复与匿名审查|对成本允许且差异有争议的锚题，复核细微质量/人类体验|展示波动、偏好分布、评审者分歧|不能事后只重复候选赢的题或将主观 Elo 当绝对分|
|2 道左右长时项目案例|阶段记录、需求变更、返工、最终验收|解释能否持续推进和接手|样本少，不能凭案例宣称统计领先|
|113 道 DeepSWE 全库|充足预算研究/官方协议复刻条件下的大范围工程解决率|同协议下的题级覆盖与原题通过率|不是入门门槛；不能替代前端、业务目标与人情味|

主页面至少展示：`每道题 A/B 分数与差值`、有效/计划题数、独立重复次数、平均与中位差、失败与中断、已知条件差异；成本与速度同屏。小样本可直接展示原始配对点，避免给人造的置信区间。若未来报告 95% 区间，必须先固定重抽样单位（题目及其独立重复）、重复题的嵌套关系、配对顺序、缺失/失败处理和统计假设，并用已知合成数据测试；区间跨零或样本不足时结论为“尚无法判断”。显示一位小数只方便复算，不代表能检测 0.1 分真实提升。无可靠统计前不使用“领先”“提升显著”等表述。

### 成本与时间在结果页的完整口径

|结果指标|计算或来源|不得混淆|
|---|---|---|
|输入/输出/缓存 Token|精确绑定桌面 session 的最终累计；重复导入不累加|缓存读包含在输入里；reasoning 不重复加进输出|
|活动时间|完整的原生日志活动区间|不是模型纯推理时间，也可能包含工具时间|
|总历时与等待|准备、首次发送、澄清等待、回收、验收的时间戳；不足则未知|用户要求等待确认时不自动罚速度|
|API 等值区间|定价版本 × 各类有效 Token，用显示公式与假设计区间|不等于订阅余额、实际发票或所有工具费|
|复审开销|AI 裁判/容器/人工复核单独统计|不得塞进被测模型完成题目的成本|
|单位有效交付成本/时间|可核对完成题的总资源除以有效交付数，同时列失败尝试|不能只看成功子集的花费而隐去失败|
|质量—效率取舍|同题集、同预算下同时画分数与成本/时间；可标非劣解|默认不把廉价换成额外质量分|

U58 已从裁判 CLI 的每作业累计事件读取输入、缓存读取、输出和推理输出，在评分过程及新报告分别展示。中止作业可从保留的 rollout 读取最后可用计数；没有计数就显示未知，不能按0处理。缓存读取包含在输入内，推理输出包含在输出内；这些数不映射成 ChatGPT 订阅额度或实际账单。裁判重新评分、超时重试各有独立开销，不能只看成功报告。当前时间预算不是 Token 硬上限，初始提示词缩短也无法限定工具循环总用量。用户每次启动新 AI 裁判须单次确认额度提示；无模型的程序验收、引用重校验或人工查看不需要这项确认。

执行详情 `UsageChart` 展示累计 Token、活动时间与部分模型 API 等值估算；U50 起配置成绩六轴画像下也汇总当前有效题集的 Token、活动时长、API 等值区间及有重复题的最大分差。该金额是按已有定价和记录换算的等值估算，不是 Codex 订阅账单；缺失用量时显示未知，不外推。历史主列表、完整准备/等待耗时、裁判费用分账、定价版本留存及完整环境指纹仍未齐备；后续应让 API、前端与 ZIP 读取同一后端口径，不能浏览器各自补价或将新价格无说明地追用于旧记录。U54 的24题精选仅控制浏览，不能作为统计分母或借此宣称细小配置差异可检测。
