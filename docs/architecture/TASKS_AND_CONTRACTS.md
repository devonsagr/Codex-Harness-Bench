# 题库、项目契约与新题接入

负责 D15-04/09/12/13/14/17；关联 [前端](../FRONTEND_SPEC.md)、[评分](EVALUATION.md)。主要工作包 B01/B02/B07。

## 1. 两类题与三条分类轴

|轴|取值与含义|不可混用|
|---|---|---|
|taskParadigm|open-ended-project 项目构建；deterministic-bugfix 修复已有问题|项目题是主线，不能因已有修复题好测就只做修复|
|channel|应用与界面、功能与工程、架构与约束、协作与多轮|是题目方向，不是固定四个评分维度|
|difficulty|Easy / Medium / Hard / Nightmare|是作者标注，未经实测校准不能当成能力等级认证|

三个轴独立。一个 Hard 项目可同时主要考察多轮协作；多轮阶段数也不是难度的唯一依据。题库应支持三轴组合筛选，以及标题/描述/提示词搜索。当前题库与准备页共用三轴筛选及标题/描述/提示词搜索函数；题库“保存并用于评测”带入真实题目ID。

## 2. 什么是一道完整项目题

一道可交付的题由六部分组成：用户需求、项目契约、起点与环境、阶段推进、验收计划、来源与准备状态。它们必须能从选题页一路追到执行提示词、回收和历史，不能只存在于 JSON。

`projectSpec` 保存 userStories、apiEndpoints、dataModel、acceptanceCriteria、techStack；已有字段纳入类型、校验、编辑/阅读与独立评分材料，criteria连接逐项验收。字段是否存在不能证明题目完整：必须核对实际需求、源码、环境和验收依据。原型只提供前端起点，当前题库范围与功能合同由本项目维护；旧points不自动加到总分。

**数据保真和行为保真都必须验证。** 新Run分别冻结完整Spec/criteria与开发提示词；后者仅包含原始需求和当轮任务，并保留SHA-256。内部验收契约不再注入开发提示词；旧Run继续展示原来的文本编排，不追加原本没发送的要求。

## 3. 契约结构与长期细化目标

延续原字段并做显式版本迁移，不要求用户把旧题全部重写。

|部分|目标内容|用途|
|---|---|---|
|用户故事|稳定 ID、用户动作、期待结果、必要程度|把自然语言需求对应到可观察行为|
|接口契约|方法/路径、输入、输出、错误、是否固定|仅当需求需要跨层接口时约束；不强制每题 REST|
|数据模型|实体、关系、持久化约束、迁移或恢复要求|不默认把所有题变成 SQLite 题|
|验收条目|稳定 ID、说明、适用阶段、证据类型、关联用户故事|作为逐条验收的共同索引|
|技术边界|必须使用、禁止使用、可自主选择，分开记录|区分题目硬约束和参考建议|
|范围 fullstackScope|已有值保留；与实际需求核对|不以“有后端”标签自动证明真实后端存在|
|阶段|稳定 ID、提示词、预期产物、验收条目引用、确认点|前一阶段要求继续有效时建立回归关联|
|schemaVersion|导入格式与迁移版本|旧题只读解释，新保存产生新 revision|

原型数组字符串应逐条展示为可编辑条目；迁移生成稳定 ID 并保存来源。删掉条目需要新题版本，不可让历史评分失去对应对象。

### 当前schemaVersion=2的具体表示

- `projectSpec`保留原型五字段：四组字符串数组与techStack文本；`fullstackScope`保留原枚举。上述长期表格中的方法/输入/输出对象、适用阶段等细化目标仍未全部实现。
- `criteria[]`含id、label、description、required、dimension、source。id稳定，dimension是九种内置验收分类之一，不产生第二份条目加分。必要项由评测者明确指定。
- 缺criteria的旧输入从故事、验收标准、customChecklist、rubrics、evaluationRubric按文字去重转换；来源写入source，旧points保存为legacyPoints，默认required=false，不替用户发明必要程度。
- 当前题库展示可兼容转换，不写回旧数据；保存创建新revision，新Run冻结转换结果与sourceSchemaVersion。旧Run不迁移。
- 编辑Spec不会静默覆盖已经人工调整的criteria。编辑器提供“从用户故事与验收标准补充条目”，只添加尚无同名项；修改/删除要求后需明确核对条目。删条目会同时去掉草稿中的检查引用，旧Run保留完整定义。
- 新Run的promptSnapshots逐阶段保存text/stageId/sha256。旧Run使用legacy-text-only解释，不能声称旧桌面收到新版契约。

可导入示例：[原创人工题包](../../catalog/examples/contract-task.json)。这份题包没有自动化检查，也未做正式桌面验证；可用U20机器方案启动裁判，也兼容旧纯人工流程；不能把它标成B07已校验完整项目题。

## 4. 既测完整交付，也能测需求探索

### 固定交付契约

评测者预先写清用户故事、外部接口和可观察验收标准。Agent 自行选择内部实现；测试从外部行为判断。适合比较不同配置面对同样已知需求的表现。

### 需求探索项目（待审设计）

输入是问题、使用情境、约束和期望成果，第一阶段让 Agent 讨论并形成 Spec。评测者验收是否切中原始目标，再明确确认后继续前端、后端与交付。

必须保留三层：评测者原始需求、Agent 产出的候选 Spec、用户确认或修订后的阶段输入。Agent 写的“全部通过”不能变成评分标准。新要求导致合同改变时记录新版本和介入，不悄悄改旧题。

现有阶段模板能记录几轮提示词和文件，但没有结构化的候选 Spec 确认及版本关系。B01/B04 先完成固定契约闭环，探索模式的持久化作为后续明确切片，不以文本框存在宣称支持完整需求演进。

## 5. 新题不必先写专用测试脚本

|准备层级|必须提供|能得到什么|不能声称什么|
|---|---|---|---|
|需求草案|目标、提示词、题类、来源|可编辑和完善的题面|已可复现的基准|
|可人工验收|明确交付条目、通用量表适用性、阶段|项目交付与逐项人工评价，必要时纯人工策略|代码已经自动验证|
|可运行检查|明确起点/空目录、镜像、参数、适用范围|真实检查结果和对应证据|测试覆盖全部需求|
|已校验题包|环境固定、负例与参考解校验、验收覆盖说明|有边界的可复现实验输入|普遍难度标尺或零偏差评分|

这是目标准备度合同；当前已有题包校验预览、缺检查提示、来源和许可显示，但还没有统一的四级准备度状态模型。

U20新评测采用arena-machine-v1机器量表，**当前代码默认七项**：需求完成、验证与回归、健壮性、规则与范围遵守、交互与视觉、交付与可复现性、可维护性；可添加目录中的安全/性能等维度并调整权重，人工按项修正。旧v1/v2维持各自冻结的四维或人工量表。逐题条目提供具体证据要求，必要项不因维度被移除而免验收。通用裁判可主动运行项目，仍不能在不存在脚本时填一条npm test并标为已验证。U46 提议的按题指标库与这组旧默认维度分开，尚未成为运行算法。

## 6. 题目检查合同

现有检查字段：id（已有ID保留，新界面检查生成稳定ID；旧输入缺ID时兼容顺序编号）、label、image、argv、weight、timeout、可选 stageIndex。stageIndex 从0开始；省略时只在最终阶段适用。镜像需本机已准备；真实执行固定内容 ID。

已增加kind（functional/build/rule/other，build含类型检查）、criterionIds和runOnFinal。未分类保持other，条目引用必须存在。独立验收或候选自测来源尚未结构化，不能从类别标签推断测试可信度。

绑定某阶段意味着检查那一阶段的快照。当前“前轮补验”不等于“第二轮重新运行第一轮检查”；后者用runOnFinal显式声明；最终快照检查时纳入早期回归项。客观覆盖按“阶段×检查”计数，不把旧阶段通过结果当成最终产物仍通过。

检查定义和判定标准在准备前冻结。候选工作区中可含开发测试，但独立验收脚本/参考解不放进起点交给模型；验证镜像可以保存独立验收器。

题目编辑器支持复用已有题目的检查方案：复制镜像、命令、权重和时限，生成新检查ID，清空原题criterionIds，统一设为最终交付且runOnFinal=false。需核对本题目录、依赖、预期和需求关联再保存新版本；复制本身不运行命令，不修改来源题或旧Run。编辑器权重仍为明确标注的相对份数，准备页按阶段×检查集合展示归一后的客观百分比。

## 7. 导入与公开来源

已提供 JSON 文件导入预览：版本1/2 → 全包校验 → 显示来源/许可及契约 → 用户点击导入 → 事务创建新副本。支持单题、题目数组或{schemaVersion,tasks}；1–50题，900KB。任一题失败整个包不写入；同请求编号重试不会重复创建。仅导入题目定义，外部baselineId必须对应本机已有快照；此JSON接口不会下载仓库或执行题包命令。另有显式公开GitHub源码导入：固定完整commit SHA，通过codeload下载并校验路径/大小/文件数，拒绝链接与子模块；记录sourceUrl/sourceCommit和dependenciesReady=false。它不安装依赖，不证明外部服务可用。修复题没有本机baseline禁止准备；构建题可明确从空目录开始。

导入来源至少记录：来源类型、URL、源版本或哈希、许可声明、改编说明、验收来源和验证状态。链接只是引用，不自动下载陌生仓库。外部许可未核实时不得标为确认可再发布；公开题库优先项目原创且已声明来源的完整题。

当前31份 Gemini 题面中14份项目、17份修复。它们是原型输入，引用仓库和建议脚本未逐一核实，不能宣传31套可直接跑的标准测试。现有5套原创完整题：原有笔记搜索、存储演进、CSV 导入，以及 U47 新增的业务账务核对和离线业务指标网页。新增两题已有故障起点负例和参考解容器正例；它们扩展了业务逻辑与前端交互，但仍不足以代表完整前后端长期项目。

## 8. 具体贯通示例

题目：“做一个任务看板，支持新增、移动、删除，刷新后仍保留数据。”

- US-1 新增卡片：人工实际操作 + 可选浏览器检查；不能只看 POST 路由存在。
- US-2 跨列移动：UI 显示与服务数据一致；失败时有明确反馈。
- US-3 刷新恢复：关闭/重开后数据仍在；只有 localStorage 是否可接受取决于题目约定，不由工具一刀切。
- US-4 删除与空态：删除后刷新不会复活，空列表仍可添加。
- 视觉：按通用 UX 量表看可读性、操作反馈和键盘使用；不把阴影、倾斜动画当所有题通用要求。

这些条目通过criteria稳定ID连接选题预览、冻结需求、阶段提示词、验收和历史；项目Spec字符串数组维持原型可编辑形式。U20新机器方案允许AI提交有引用依据的条目结论，不能改写程序检查结果；缺证据保持未核实。旧策略AI仍只辅助，不代填人工通过。

## 9. 验收案例

- **T-AC1**：上述看板契约保存/重载/准备/回收/历史的条目一致，开发提示词只含公开需求，无字段静默丢失。
- **T-AC2**：导入一题仅带需求和人工验收条目，无检查脚本也可准备；机器与旧人工策略明确标注。
- **T-AC3**：题库三轴组合筛选、关键词搜索与工作台选题一致；点“用于评测”带入该题 ID。
- **T-AC4**：更新题目不会改旧 Run 的合同；旧验收条目仍能解释。
- **T-AC5**：阶段2破坏阶段1功能，最终回归检查能检出；仅阶段1旧快照通过不算最终通过。
- **T-AC6**：负例失败、参考解成功、环境失败分类正确，才能把新完整题包标为“已校验”。

### 内置题自动装载与实际起点（U26）

服务启动由builtin_tasks安装缺失的五个固定original-*题目；仅从仓库tasks/*/environment/fixture冻结源码。已有版本（含用户修改及归档）不覆盖、不复活。旧显式导入接口保留兼容，新界面不再要求用户导入内置题。

|内置题|类别|实际起点|
|---|---|---|
|笔记搜索修复|Bug修复|notes.py、text_utils.py、AGENTS.md、tests/test_existing.py|
|CSV目录导入修复|Bug修复|catalog.py、validation.py、README、AGENTS.md及已有测试|
|笔记存储演进|项目扩展|已有笔记工程和测试；默认完整需求，也可显式分阶段|
|业务账务核对|业务流程/数据逻辑|Python ledger 故障起点、可见 helper 与测试；独立验收收费、退款、重复、异常、Decimal|
|业务指标网页|前端/真实浏览器|离线 HTML/JS 数据起点；Chromium 验收筛选、漏斗、API、CSV、键盘和 390px 无溢出|

五题为本项目原创，不是从引用的第三方GitHub项目抽取的真实Issue。前三题与账务题使用 Python 标准库，网页题使用离线 HTML/JavaScript；故障起点保留未完成行为。创建评测复制冻结源码并校验哈希，叠加本次 Harness，不复制参考解或隐藏验收器。独立程序验收需要 Docker；工作台点击检查时仅对这五道仓库自带题自动构建固定 verifier 镜像，网页题首次还需构建项目 reviewer 基础镜像。开发和本机 AI 审查仍可不用 Docker；浏览器程序验收不能在 Docker 缺失时冒充通过。

题库与准备页默认“可开始”，缺源码的17份Gemini修复题面和1份项目类重构题面列于“待补全”，选用/开始受限；仍保存完整原文以便后续完善。从零构建题可从空目录实现，但这不代表依赖、数据库或外部服务已就绪。“项目起点”展示源码文件数、来源、快照与环境说明；environmentNote为可选文本，新增题包填入运行时和已有测试命令，旧记录不追写。

requiresBaseline明确声明修复、重构和已有工程扩展需源码；Bug修复始终要求起点。旧perf-01-props-to-signals记录只读兼容为需要源码，不改变旧Run，用户编辑新版可明确选择起点要求。前端准备度与后端prepare使用相同条件，不只根据类别判断。

## U27 公开题源与桌面适配

`catalog/public-task-sources.json` 是固定上游版本的来源索引，113项包含id/title/language/category/repositoryUrl/baseCommit及题面、环境、验收器链接。界面可搜索和查看来源，U31允许从索引选题，但只在创建时按需准备，索引数不代表环境已验证数量。元数据许可与变更见 `catalog/SOURCES.md`；不包含目标源码、参考解或隐藏测试。

正式接入仍属B07：按来源版本获取题包，冻结题目与目标工程base SHA，准备源码/依赖，验证原验收器，再发布可执行题目。已有公开GitHub起点导入仅能准备源码，不代表这一整条适配链已经完成。

开发工作区包含目标起点、允许的已有测试和原始任务说明；隐藏tests、参考解、裁判细则放独立验收材料。准备清单必须记录OS/运行时/依赖、原生或适配环境、校验结果；失败时留在待准备，不让修复题落入空目录。Windows本机无法等价复现的题不能静默变更条件。自动准备是产品能力，不能要求用户逐题手工拼装题包。

评分接入须保留原题reward和测试结果，与本项目质量维度分开。先验证一个代表题包的完整链路，再扩展语言和工程类型；113项不等于已验证113套运行环境。具体顺序只在PROJECT_SPEC第8节维护。


### U29 固定题包与源码下载

`public_sources`通过固定上游revision下载113份instruction/task.toml/environment/tests，校验仓库和base SHA与索引相符；不解包solution。题包存public-sources，目标源码以固定SHA导入baselines；重用校验过的同仓库/提交，已有或已归档题不覆盖。失败逐题保留，重启标记下载中断。源码已下载、环境unverified、verifier downloaded-not-integrated分开记录；不得给出官方reward。隐藏tests不进入开发目录，目标仓库自带的公开测试保留。

生成DeepSWE工作区时复制全部已冻结源码与选定Harness，建立main分支和一个本地初始提交，无remote/未来历史。该提交用于本地diff，不冒充上游SHA；上游SHA仍在来源元数据中。原题说明原样保留，不加入隐藏测试和参考解。现有50MB/5000文件/8MB单文件及链接限制继续适用，超限显示未准备；源码就绪计数不等于环境可运行数量。

### U30 Tengo Windows适配

支持固定revision的tengo-callable-instance-isolation、tengo-destructuring-bindings和yaegi-go-embed-directives，分别使用固定选择器/白名单。官方Go 1.26.8 Windows x64 ZIP按SHA-256核对，解包至toolchains；不改系统PATH。故障起点须满足f2p=0、p2p=1才创建ready-windows题目新版本；已有Run冻结版本不重写。该题无第三方Go依赖，验收关闭GOPROXY/GOSUMDB和网络；候选go.mod变化不支持，保留未知而非猜分。

## U46–U47：低预算、可区分能力的题集设计（方向已批准）

用户目标不是“手动打开 113 个文件夹看通过数”。题集需要同时覆盖**真实工程、模糊需求、前端、长期协作、逻辑与效率**。题的数量不是可用性：可运行起点、可观察目标、验收器、样本难度、额度上限、正负例和重复价值均须列清楚。当前已验证的是五份现有回收的 DeepSWE Linux 上游验收及少量 Windows 适配题；下表的开放项目题型是**候选设计**，没有凭空宣称题包已做完。

|层级与候选题型|主要区分什么|必要产物与验收|预算/准备策略|
|---|---|---|---|
|烟测：一题短 SWE 修复或功能|配置是否导致明显工程退步；代码和回归|固定仓库/提交、原生测试、目标功能与回归分列|自动按题准备，缓存源码/镜像；只跑选择的一题|
|烟测：一题小型开放业务需求|能否切中模糊但常见的用户目标|需求条目、真实运行场景、异常/持久化证据|限制范围和时间，不预写唯一实现|
|烟测：一题可运行前端|UI 功能、视觉、键盘与反馈|浏览器实际操作、截图、可访问性/窄屏检查和人工视觉复核|固定设计约束与资源；不能仅靠源码截图|
|核心集：工程新功能/跨文件改动|规格理解、架构与程序正确性|DeepSWE 或原创固定源码；失败起点、参考通过、语义目标映射|选题即准备；“来源 113 条”不等于“113 条可跑”|
|核心集：已有系统修复/可靠性|根因定位、保留旧行为和边界|隐藏/独立测试、回归、失败诊断|与功能题分开统计，不让大量相似 Bug 垄断总分|
|核心集：前后端产品交付|业务流程、交互、数据持久化、视觉质量|真实浏览器主路径、后端/API、重启恢复、人工使用观察|需新建经过负例/参考解验证的完整题包；当前未完成|

|核心集：需求澄清/变更|是否问对问题、避免越权扩张、后续执行一致|冻结最初目标、允许澄清点、用户答复、变更事件、最终成果|阶段数不能自动当额外题数；人工体验可盲评|
|重点案例：长项目连续推进|跨轮上下文、阶段回归、返工、交接|里程碑产物、每阶段状态与证据、最终完整验收和复盘|少量题、明确小时级上限；不是每天全量回归|
|可选专项：逻辑/视觉/文档/安全|特定能力短板|该领域原题答案、交互或专家验收|作为独立专项，不拿数学/医学分替代软件质量|

**建议工作集**：3–5 道低成本烟测用于验证系统和筛掉明显退步；8–12 道固定、跨类型的核心题作为日常配置比较；约两道长期项目案例用于深度观察；113 道 DeepSWE 全库仅为用户自愿的高预算专项。数量是待审预算层级，不是通过率阈值或当前已准备题数。要判断小差异，优先在同题做 A/B 配对和少量独立重复，而不是新增几十道只给 0/1 的相似题；费用不够时只报告观察值和“不足以判断”，不假装一位小数很可靠。抽样不能看完模型结果后专挑对某配置有利的题；固定核心集与探索集标记分开。

**题目入池门槛**：

1. 原始需求、用户可见提示词、独立评分依据及版权/许可分别封存；隐藏测试与参考解不进入被测工作区或模型提示词。原创题要有失败起点和至少一份参考正确实现，证明验收器会辨别结果；开放项目还要有可接受实现的多样性检查，不能将某一种架构偷偷规定为唯一答案。
2. 明确 `prepareStatus`（题面/源码/依赖/验收器）、平台、版本哈希、预估耗时/资源、可运行入口、正负例回执。没有 Docker 或浏览器时选题前说明能否跑，能修的系统问题由应用准备/重试；不要耗费模型额度后才暴露验收器缺失。
3. 模糊需求保留故意未知的部分，同时写下**评测者自己的目标/禁止动作/合理澄清范围**，和模型可能提出的问题分开。必要问题没有答复时按预先定义的流程处理；不能让评测者事后随好恶改成功标准。开放项目的评分卡先定目标组和可接受证据，再看产物。
4. 长项目保存初始要求、各次确认与需求变更、里程碑、回收、修复次数、最终回归、实际用量和外部介入。阶段诊断不代替最终分；同一项目的一连串消息和快照不是独立试次。要测试长期稳定性，需独立重新开始同题或可比题，而非把同一会话切碎。
5. 批量创建每题一个已有 helper 管理的独立 `runs/<run>/<trial>/workspace`，共同固定源码可校验复用，不共享可写目录；每次由用户点击打开一道未请求的桌面草稿，处理 Codex 目录信任与预填后才能继续下一道，取消后可在对应试次重试。打开不自动发送、不切换宿主全局配置或确认信任；如需全局配置，用户在配置步骤或试次执行区显式点击“应用到 Codex”。用户只选题集/配置/预算，不需要手动添加百余文件夹。缓存、工作区、结果分别计数并可回收。

**当前实装与缺口**：任务分类现在是来源、题型、能力标签三条独立轴：`taskFamily` 覆盖 SWE 修复/功能、网页交互、全栈、业务流程、数据分析、长期项目、架构、协作、安全可靠性、性能；`capabilityTags` 用于多能力检索，旧题按冻结元信息补显示分类，不改原题面。准备页和题库均可按细分类别筛选。五道已跑 DeepSWE 有目标语义组评分卡；新增两道原创题的参考实现通过独立验收，故障起点不通过。网页题为真实浏览器功能取证，不等同于人工视觉审美分。仍未完成：自动挑选并冻结完整低成本核心集、可实际运行的全栈后端/前端一体项目题、长期项目过程自动评分、Windows 原生浏览器取证、其余 DeepSWE 语义评分卡与所有依赖/上游镜像适配。不能用未准备的题面数或脚本数量替代这些门槛。
