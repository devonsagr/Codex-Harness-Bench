## 如何区分事实、要求和提案

- **用户已定**：U07/U08/U10 或 D15 条目能直接支持的要求。
- **现有实现**：在当前代码中找到入口和行为；基准及交付版本见当前交接和历史；不等于所有情况已实测。
- **已验证**：有具体测试或操作回执，并明确验证范围。
- **目标合同**：依据用户要求补齐的设计；尚未编码的字段和接口必须写“拟新增”。
- **待审设计**：需要用户以后裁决的产品取舍；默认建议和影响写在所属模块，不把沉默当作批准。
- **未验证/不支持**：没有依据时直接这样写，不用“预留”包装为完成。

本轮补接固定契约与逐项验收功能，没有产生新的正式桌面模型成绩。Gemini 原目录只读；完整对话原文、配置和实验产物留在 `.local/`。公开文档保存相关要求的整理和必要短引，不复制完整日记。

## 审查时值得先看的四个例子

1. 项目题有“刷新后数据仍在”这一要求：它应从选题、提示词一路进入验收明细；当前已接入并有软件链路验收，仍不等于正式桌面整题通过。见任务合同 T-AC1。
2. 配置要求每阶段等确认：等待应算遵守要求，不能自动扣效率分。见执行合同 E-AC3 与用量合同 M-AC2。
3. AI 说某文件缺少功能：路径与引用存在只证明引用正确，不能证明意见正确；需允许人工驳回并保留记录。见评分合同 S-AC5。
4. 两套配置只差一条规则：要看实际条件、任务版本和重复结果，单次高两分不构成可靠收益。见用量合同 M-AC4。
