# Codex Harness Bench：总架构与唯一实施路线

依据用户当前裁决U27：本项目独立定义产品与后端，Gemini仅为初始前端来源。正式评测以Codex桌面为固定产品底座，研究模型与个人可配置Harness对真实任务交付的共同影响。本文第8节是唯一实施路线，模块文档保存接口与细则。

## 1. 项目要解决的问题

公开模型成绩来自特定任务、运行框架和评测条件，不能直接回答“我的日常Codex配置是否更有效”。本项目把问题缩到用户真实使用的桌面场景：固定Codex桌面这一既有Harness，记录模型与推理档位，改变可配置层，观察交付、用量及约束遵守的差异。

评测对象分三层：

|层次|具体对象|实验角色|
|---|---|---|
|桌面底座|Codex桌面的执行循环、工具、上下文管理和产品行为|记录版本/平台/宿主条件；不重写它的Agent Loop|
|模型条件|模型、推理档位、可用额度及实际调用记录|配置A/B尽量固定；改变时解释为组合对比|
|个人配置|AGENTS、Skills、交互约定、支持的原生设置及已有工具开关|主要比较变量，冻结版本并记录实际应用证据|

核心问题：规则改动是否更切中需求？技能是否带来可验证的帮助？相同交付需要多少资源与人工介入？需要覆盖项目构建、修复、重构与已有项目扩展，不以一类任务代表全部能力。

默认一套配置、一道题、完整需求，不限定真实对话轮数；对比与分阶段由用户主动选择。判断微小收益需要同题同条件重复样本，当前仅保存可追溯记录和有条件分组，不自动宣布统计胜者。详见[产品模型](architecture/PRODUCT_MODEL.md)与[用量比较](architecture/MEASUREMENT_AND_COMPARISON.md)。

## 2. 产品依据与实施原则

1. 用户当前目标和可核实的实现是依据；前端原型提供界面起点，不定义题库数量、评分算法或后端边界。
2. 正式执行仍在Codex桌面；题库接入借用外部任务与验收方法，不偷换成CLI模型榜。独立CLI裁判只承担回收后的验收。
3. 题目必须说明需求、起点、运行依赖和判分依据。需要已有工程的任务自动准备固定源码；题面链接不算环境已就绪。
4. 评分以机器为主、人工按项修正；原生程序验收指标与开放质量量表分开，证据缺失不编分。
5. 工作区冻结题目/配置/策略，回收生成新快照。宿主全局继承、版本变化和人工介入作为实验条件记录，不宣称天然完全隔离。
6. 对用户的说明只讲当前定位、操作和限制。原型承接、旧算法及历次修补属于历史记录，不作为首页产品叙事。

当前已实现配置管理/显式应用、独立工作区、回收、独立机器评分和人工修正、用量与历史。内置5套带独立功能验收的源码题；51道原创开放网页题共用空白起点与基础烟检，不能算51套独立验收；U54再增12道各有不同文件起点的业务、数据、工程、长期与协作开放题，但它们还没有独立程序验收。工作台默认的32题跨类型精选仅控制浏览顺序，不是已冻结的统计题集。U69补入8道社区机制项目、77个功能核心用例和页面连接检查，另有163道HumanEval+固定扩展测试用于短任务对照，默认不混入项目随机组卷。DeepSWE113条来源可按题选择与准备，少量题已接原生/上游验收；另外四类公开基准目前仅完成来源与适配门槛研究，没有可选题包。U45对五份既有回收完成上游Linux验收，U47为这五题接入本地连续分。**外部基准完整接入、创意题逐题验收/盲评、12道新开放题程序验收、长期项目真实整题及完整环境指纹仍未完成。**状态与数量细账见[U54题集审计](research/task-portfolio-audit-20260927.md)。

## 3. 产品对象与完整操作流

|对象|含义|版本/归属|
|---|---|---|
|Config|规则、技能、模型/档位、交互与个人约束|命名ID+revision；运行保存全文|
|Task|项目/修复需求、契约、阶段、起点、验收、来源|独立版本；不能后改旧Run|
|Run|一次冻结的配置/题目选择与策略|可含多个Trial，不代表自动批跑|
|Trial|一个配置×一道题的独立工作区|多轮仍是一题|
|Capture|一次回收的文件证据|所属阶段、hash、差异、检查|
|Review|针对回收的人工评价或AI意见|证据类型分开、追加版本|
|Comparison|有条件的结果与差异解释|不把不同题类/策略混成总榜|

```mermaid
  C[保存配置版本] --> P[选择题目与验收策略]
  T[需求/项目契约/起点/阶段] --> P
  P --> F[冻结输入并准备独立工作区]
  F --> D[桌面核对设置并手动发送本轮提示词]
  D --> W[执行/澄清/等待确认]
  W --> S[停止写入后回收新快照]
  S --> O[客观检查]
  S --> A[机器裁判取证并评分]
  A --> H[按需人工修正]
  O --> E[证据与评分版本]
  A --> E
  H --> E
  E --> N{是否还有阶段}
  N -->|用户确认| D
  N -->|最后交付| R[记录结束与历史]
  R --> X[复用配置/导出/有条件比较]
```

图表示完整操作方向。当前已接固定结构化契约与逐项人工验收；候选Spec的用户确认、配置矩阵和按历史完整重建仍待补。

用户实际步骤是：选择 → 准备 → 打开新桌面任务草稿 → 核对模型/档位并发送 → 自动读取执行日志 → 本轮完成后回收 → 机器评分/人工修正 → 确认下一轮或结束。打开桌面不等于已发消息；开始状态从匹配会话的原生日志自动同步，手动记录只作后备。完整动作说明见 [执行合同](architecture/EXECUTION_AND_EVIDENCE.md)。

```mermaid
flowchart TB
  UI[React/Vite本地界面] -->|同源HTTP与令牌| HTTP[Python HTTP入口]
  HTTP --> App[配置/题目/阶段应用服务]

  App --> FS[起点/技能/工作区/回收快照]

  App --> Checks[Docker客观检查]

  App --> Score[验收/评分/比较派生]
  Legacy[旧CLI实验] --> Old[runs独立历史]
```

|模块|现有落点|负责|边界|
|---|---|---|---|
|界面|frontend/src/workbench|表单、操作、材料、历史|不造结果，localStorage不存业务事实|
|HTTP|src/chb/webapp.py|静态资源、Host/Origin/Token、路由|仅127.0.0.1，无任意宿主shell/文件接口|
|应用|arena/api.py、service.py|校验、版本、准备、阶段、恢复|显式应用可备份写入宿主；不代发桌面提示词|
|契约|arena/contracts.py、task_import.py|结构校验、兼容转换、冻结提示词、事务题包导入|不改旧Run，不从题面猜测已通过|
|数据|arena/database.py|records/revisions事务|Trial等目前内嵌Run JSON，非独立SQL表|
|文件|arena/files.py|限定路径、快照、hash、差异|不跟随链接，不吞超限或变化错误|
|后台|arena/jobs.py|拥有的检查与本机/Harbor审查|只停止本工具工作，机器分与人工修正分开保存|
|评分|arena/scoring.py|公式、适用项、证据齐备性|未知不填默认高分|
|用量|arena/telemetry.py|明确日志归属、累计值|不扫描全部会话，不猜费用|
|旧实验|cli/adapter/results/analysis|CLI执行与只读历史分析|不混入桌面正式成绩|

### 4.1 配置装载

准备时复制题目起点，合并起点根规则和本次配置为AGENTS.override.md，复制选定技能到.agents/skills，初始化独立Git并冻结baseline。**这是工作区叠加，不是完整全局隔离。**

桌面仍继承宿主全局规则、技能、插件和设置。当前宿主指纹只有AGENTS.md、AGENTS.override.md、config.toml。回收比较工作区规则/技能/.codex变化，只能提供部分条件证据。文件存在不能证明模型已遵守或技能已触发。详细能力表和冲突规则见 [配置合同](architecture/CONFIGURATION.md)。

2026-09-15已有本机codex app帮助与官方规则/技能文档核对记录；本轮沿用其证据，不宣称重新验证全部当前模型组合。旧CLI能力说明在codex-capabilities.md，不可套成桌面支持表。

### 4.2 客观检查与AI审查

客观检查采用image+argv+weight+timeout+可选stageIndex，镜像需预先准备，执行固定内容ID。只读挂载本次冻结文件并复制到容器/app；网络关闭、无宿主home/Docker socket，资源与权限受限。退出码、输出、时间真实记录；超时/取消/环境错误不当作题目失败。

AI裁判标cli-review-only，可选固定本机 Codex 原生沙箱或 Harbor 容器。新机器方案页面默认 gpt-6-luna/max；模型目录不等于账号权限，缺少本机能力或账号调用失败均不能静默换成 Sol/medium，用户可明确选择其他可用模型。本机时间预算默认1小时、最高8小时，准备清理另计。本机模式按PATH查找官方 Codex CLI（可用 `CHB_CODEX_BIN` 指定路径），不会打包、安装或登录 CLI；复制冻结快照、使用独立临时 CODEX_HOME，关闭宿主规则加载，不运行 Docker 脚本；使用本机工具并允许安装依赖，环境不能视为跨机器一致。容器模式使用machine-v1镜像及已有Harbor。每次裁判是新的 `codex exec --ephemeral` 进程，不续接前次会话；两者均保存命令/输出并核对引用，缺运行证据不生成UX/性能分，不自动重试或换模型。本站 AI 质量评价使用版本化项目提示词，公开题的上游验证器另算；模型评分可能波动，单次报告不构成准确性保证。

工作区继续变化不影响旧快照。前轮补验检查的是旧版本，不是最终回归；新契约可用runOnFinal明确声明最终快照回归；未勾选的旧阶段检查不会自动重跑。详情见执行和评分合同。

## 5. 数据、状态与证据约束

本地业务根.local/arena，包含arena.sqlite3、skills、baselines、runs；每个Trial含workspace、baseline、captures、traces、reviews。原生日记、配置、轨迹、产物只本地保存，不进入Git；Obsidian镜像none。

主要约束：

- Config/Task编辑创建revision，旧版不覆盖；Run冻结完整输入和策略。
- Capture文件不可改写；检查尝试和人工复审有历史，新回收不继承旧人工分。
- 评分和导出核对目标快照hash；hash不是第三方签名或防恶意编辑系统。
- 快照单文件8 MB、总50 MB、5000文件；凭据/依赖/Git元数据排除，链接和回收期间变化报错。
- ZIP最大200 MB，含私有规则与产物，不含认证/原生完整日志；当前没有ZIP导入恢复功能。
- SQLite与文件系统非同一事务；失败残留和恢复仍需B05补强。
- 服务重启保留证据并标记中断。强制结束后Harbor环境清理不能保证，只按精确拥有信息核对，不全局清Docker。

状态主线：prepared → working → captured → completed；修改后可再次capture；显式分步才使用waiting_confirmation；后台checking/judging是有目标快照的临时状态，另有interrupted。completed只表示交付结束，不表示质量通过。

现有HTTP路由、请求/响应、后台动作、错误和拟新增实体完整列于 [数据与API](architecture/DATA_AND_API.md)。它保留了原接口合同，没有把实现细则压缩掉。

## 6. 评分方法与比较边界

三类评价证据是客观、人工、AI；个人约束另有逐项验收结果。版本2题目已将条目与人工操作说明、文件hash和检查回执关联；旧Run保留原评分语义。

新评测默认arena-machine-v1：裁判依据冻结需求和量表检查项目，逐项给0–100分或null；人工可修正单项，不固定占50%。开放项目的适用评分项和必要程序检查齐全后即显示完整单题分；未标记交付结束时明确标为“暂定”，再次回收或修正会重算，且不进入配置正式成绩。缺项只有已评分项均值，不冒充整题分。中间阶段快照不得提前形成整题分。脚本结果独立保存，不重复加权。旧arena-review-v1/v2保留原客观/人工公式和AI辅助意见，不重算历史。详见评分合同。

版本2已提供“必要条目是否满足”的独立验收结论，与连续分数并列。分高不自动等于需求通过，行数少不自动等于切中需求，等待确认不自动等于效率差。详见 [验收与评分](architecture/EVALUATION.md)。

用量读取明确导入的原生日志最终累计，验证cwd/session与模型/档位；缓存属于input，reasoning不盲目重复相加。活动区间不是纯推理时间；费用未知。小幅规则修改可能被随机性和评分误差淹没；没有固定误差、100%正确或单次因果结论。比较方法与未实现部分见 [用量与比较](architecture/MEASUREMENT_AND_COMPARISON.md)。

**当前单题与配置分**：配置成绩以冻结的配置 ID＋revision 为选手，模型、思考档位和速度是条件。五道已验收 DeepSWE 题保留原题 reward 与本地 70/20/10 连续分；其余公开题没有已核对语义卡时本地总分为空。U47–U50 的开放项目使用固定 60/25/15 卡，U51 自定义评测使用冻结的 `project-policy-v1`；U52 起新建评测默认按冻结题型自动选择适用项，当前新评测的开放项目采用 `project-tasktype-v3` 的 60/25/15 三组卡，旧 v2 记录保持原协议。每道题只有一个本地单题分，已配置的程序检查失败限制验证项。最近完整多题批次按不同题等权，同题重复先取均值；归档保留成绩，永久删除整次评测才移除记录和证据。

**U62 证据资格边界**：以上开放项目数值首先是本地 AI 参考分，并不因全部维度有分、引用可定位或通用浏览器烟检通过就取得配置对比资格。当前仅已核对的公开题原生验收，以及项目内五套带正反例的任务专属程序验收中**未改动的单阶段题**，在最新快照有完整结果且检查通过时，才允许题集发布具最低程序证据的本地综合分；多阶段题须待最终快照全项回归后再取得资格。仅有共享网页烟检、无专属检查、专属检查失败或旧记录缺少证据级别时，页面保留逐题原分与批次 AI 参考均值，但配置综合分留空、禁止据此宣布胜负。原始回收、裁判报告及历史数值不改；此资格只是最低程序证据门槛，**综合分中的 AI 质量项尚未校准**，不能因数值差自动宣布配置胜负。下一步要冻结逐题语义验收和独立正反例，再用已知好/坏交付、盲评和同快照重复测试检验裁判排序、误判与弃评率，细则见评分合同。

**配置能力画像（U52 现行）**：配置成绩展开区使用一张六轴雷达：目标兑现、工程实现、网页体验、推理决策、协作沟通、稳健交付。每轴只读取最新冻结回收所对应的程序评分卡或有效 AI／人工修正分项；同题重复先均值，不同题等权。目标组中的规则约束计入单题总分一次，不单列“规则边界”雷达轴；同一已取证分项可用于分析多个能力视角，但不因此在单题综合分重复加权。旧评测的评分项按旧协议读取；公开题的原题 reward 仍独立展示。缺项为未测，不能从题目标签或单题总分推造轴分；三轴以上有分时绘制填充图形。图表不是第二套总分。Token、活动时长、API 等值估算与同题重复分差单列；配置对照只用双方共同题和可匹配协议，顶部完整题集总分不受对照切换影响。

配置展开的题目记录按当前题集、历史、待补分开并以双列卡片分页，避免逐题原始记录铺满整页。六轴右侧的高分证据核查列出 90 分以上题数、独立重复、人工评分记录和程序检查覆盖，并提示同模型裁判及检查的覆盖边界；这些是核查入口，不是新的分数或置信区间。旧分保留原样，尤其单次前端 AI 的 90+ 不能直接解释为需求、交互或审美的已验证通过率。

**下一阶段目标**：将当前按 run 划分的批次提升为具名、固定版本题集，支持跨批次配对重复与自定义题权；扩大已核对语义卡的公开题范围。模糊开放项目与长项目补足澄清、里程碑、最终回归和实际体验证据；网页项仅在网页题适用。微小 Harness 差异通过同题配对、重复和不确定性说明判断，不能凭多显示小数位得出胜负。成本、时间和稳定性与质量分并列。DeepSWE 70/20/10 与 U52 开放项目按题型 60/25/15 已接入；长期项目浏览器取证、盲评和统计校准仍待完成。

## 8. 唯一实施路线与完成标准

本节统一维护工作包状态。B编号是功能交付范围，不是每次对话只做一个按钮。当前状态不以测试数换算百分比，不把本轮文档完成写成其描述的功能已编码。

### 8.15 U55 配置应用与逐题打开草稿

用户在配置选择步骤看不到“一键应用到 Codex”，而独立工作区的项目级 `config.toml` 不能证明桌面新任务实际采用该模型与档位。现将显式应用入口同时放在第2步和准备态试次执行区：前者使用选中的已保存配置，后者使用该试次冻结版本。用户点击后复用原有备份、版本校验、单活动应用和撤销机制；浏览、选题、创建工作区、打开草稿都不自动改宿主配置。同配置多题可复用匹配的活动应用。页面区分“全局文件读回一致”和“Codex 当前任务实际模型”，后者仍需发送前在桌面核对，不能把文件状态当遥测。官方说明[桌面会保留用户手动选过的模型](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)，[新对话深链](https://learn.chatgpt.com/docs/reference/commands)只公开 `prompt`、`path`、`originUrl`，不支持本工具为每个桌面对话直接传模型/档位；因此一次应用全局默认值不能保证覆盖既有手动选择。

原批量入口的服务端循环会连续启动所有 `codex://threads/new` 深链；在目录信任弹窗尚未处理时，后一个深链可能覆盖前一个对话框的预填提示词，`os.startfile` 成功也无法判断用户是否取消。现以 `trialId` 指定单题，每次按钮只请求一个草稿并聚焦该题；成功请求只标 `requested`，仍不算任务开始。页面等待用户处理信任和预填：确认草稿保留才标 `confirmed` 并允许打开下一道；点击“否”或草稿丢失则标 `cancelled`，同题留在待重试队首。该确认是用户反馈，不是能从 Codex 读取的桌面信任状态。并发重复请求受服务端锁与状态检查约束。验收以单次最多一条系统打开调用、失败不标记已请求、取消后同题重试及真实页面入口为准；不依赖桌面自动确认弹窗。

### 8.16 U56 配置版本应用与桌面实际选择的界线

配置库编辑后的草稿和上次已应用的版本必须分别识别：只要草稿有未保存修改，就显示“保存修改并应用到 Codex”，先保存新版本再写入并核对宿主文件；不能因为旧版本仍有活动回执而禁用按钮或显示“已应用”。没有修改时复用已保存版本，不为了应用制造一个内容相同的新 revision。工作台第2步和试次执行区仍只按各自已保存/冻结版本显式应用；它们不能替代配置库对未保存草稿的保存。

应用回执、全局 `config.toml`、项目 `.codex/config.toml` 只能证明**文件值**。Codex 桌面可能保留手动模型选择，新对话深链也没有模型、思考档位和速度参数；应用无法强制切换当前或新对话的实际选择。配置页、批量草稿按钮旁及单题执行按钮前均明确展示这一限制和本题目标模型/档位/速度；发送前若不同须由用户在桌面调整。手动记录开始时确认范围包含速度。未固定的档位或速度标“未固定/沿用”，实际条件缺失或不一致的试次不能当作受控配置比较；原生日志事后并列展示实际记录的模型与档位及其是否匹配，不能把未采集的实际速度编造成已证实。

### 8.17 U57 草稿确认、裁判失败诊断与短时前端空间题

五道前端试次均有回收快照；旧五次 Docker 裁判日志明确返回 `gpt-6-luna` 不支持当时的 ChatGPT 账号，原 `0/5` 是未评而非作品零分。升级裁判镜像 CLI 后，曾使用 `gpt-6-sol`/`medium` 对同一批冻结交付逐题新建独立审查作业，当时五题都有8/8适用项及本地连续参考分，整批显示90.3/100、5/5；最新 Luna/max 复评见 8.19。旧失败日志继续只读保留；家庭能源题的一条空引文经追加重校验剔除，原答未改。其成功作业使用缺中文字形的旧镜像，另四题用补齐 CJK 的新镜像，批次页须提示镜像混用，不能把跨题的小数差当成能力差。账号权限只由真实调用验证，不由模型目录推定；每次重试都保留为独立作业。

批量打开深链只知道 Windows 收到了打开请求，不知道 Codex 信任弹窗中是否点击“是”、工作区是否加入或预填草稿是否保留。每次只请求一道，状态先为 `requested`；页面显式确认保留后才可开下一道。点“否”或草稿丢失时标为 `cancelled`，同题留在待重试队首，不自动跳过。此确认是用户反馈，不是桌面信任状态的自动遥测。

前端创意题新增一件可旋转的短时三维展台，固定精选入口用它替换水獭缆车题；后者仍在全库。精选24道中的 SVG/交互SVG 仅保留一项，其他网页、仪表盘、游戏、工具与表单并列。新题只复用基础浏览器烟检，不能宣称几何正确或审美已有自动验收；它和原50题一样仍需真实浏览器操作、截图及人工复核。一个 AI 裁判可帮助收集证据和给参考分，但单次主观分不是精确真值。新报告要求视觉/原创项至少有裁判保存的本题光栅截图，页面允许人工打开，截图本身仍不能证明 AI 真正看过图像。评分提示词固定版本、SHA-256，并与模型/档位/环境一起记录；同题比较应在同协议下复审，对有争议的视觉项加入人工盲评。DeepSWE 原题程序验收不使用本站 AI 质量评分提示词，二者分开展示。详细失败链与校准边界见[评分合同](architecture/EVALUATION.md)及[当前交接](当前交接.md)。

### 8.18 U58 裁判盲化与额度可见性

U57 的五份有效前端报告是五个独立 Harbor/Codex CLI 作业，用 `gpt-6-sol`/`medium`，并非当前开发对话直接评分。审计发现旧裁判副本仍包含被测工作区的 `.codex/config.toml` 和 AGENTS 指令，故原五分虽会话隔离，却不能标成严格盲评。新 `arena-judge-2026-09-27-blind-v2` 过滤各级 `.codex`、`AGENTS.md` 和 `AGENTS.override.md`，在副本、提示材料与引用映射三处一致；冻结原快照不变，旧报告重校验仍用原协议的可见文件。产物正文、代码风格仍可能暴露身份，新 AI 裁判也不能成为客观真值。来源与未解决项见[评分合同](architecture/EVALUATION.md)和[当前交接](当前交接.md)。

每次新 AI 裁判请求需单次明确同意消耗当前 CLI 登录账号额度，时间预算只限运行时长、不限 Token。模型切换不自动升到 `max`；支持时优先 `medium`，否则不强制档位。裁判事件和中止作业 rollout 的会话累计 Token 在过程页显示，新报告保留各自输入/缓存输入/输出/推理输出计数；缓存和推理分别是输入/输出的子集，不能相加成额外花费，不表示实际订阅扣额或账单。五次成功审查日志累计约184万输入、3.9万输出 Token，另一次超时作业底层记录约27.8万输入、0.67万输出；重复工具检查和多轮上下文是主要可见来源，单次初始提示词从7404缩至4628字符不足以控制整段作业开销。本轮不新增模型调用，也不将旧成绩重写为新协议成绩。

提示词影响评分可靠性和用量，须分别验证。现有版本/SHA、引用校验和证据分层只使报告可追溯，**没有完成**同快照提示词 A/B、人工盲评对照、重复波动或“AI 真正看图”的验证。未来校准应预冻结样本、评分卡、模型/档位、镜像/浏览器/字体、预算和候选提示词，随机交换顺序，在已知好/坏/边界样本上比较逐项分布、未评比例、人工一致度、Token/时间与失败；只有结果可重复且成本可接受才替换版本。任何单次小数分差仍只供参考。

### 8.19 U59 Luna/max 默认与报告容错边界

新裁判默认恢复为 `gpt-6-luna`/`max`，仅改变评分页初选，不覆盖旧 Sol/medium 报告，也不触发模型调用。两份实际 Luna/max 报告分别因浏览器命令输出的美化 JSON 与单行引文排版不同、完整报告末尾多一个 `}` 而被旧校验拒绝；现分别在**完整 JSON、同一对象、原序连续键值**和**恰好一个多余尾括号**的窄条件下接受。原始报告不改，命令与引用仍逐项核对，其余异常和伪造引用仍拒绝。相同冻结快照上仅追加无模型调用的重校验记录，救援艇和金门大桥恢复为 92.7 与 92.6 分，批次现显示 5/5、约 93.6 分。另一条无效引文仍显示警告；引用存在不保证主观分正确。分数偏高的判断须依据截图、交互和人工校准，不能自动调低或据单次不同裁判分差作能力结论。详见[评分合同](architecture/EVALUATION.md)与[当前交接 U59](当前交接.md)。

### 8.20 U60 均衡随机选题、评分可靠性与故障恢复

工作台提供一次选择 SWE 仓库题与短/中型网页题各 1–5 道的按钮，交替组成最多十题的同配置待办队列；SWE 只从已接入固定验收协议的公开题及有检查器的内置题抽取，网页从可创建且有浏览器检查的前端题抽取，抽样先分散来源/交付机制。可预览、调整并返回三步；随机种子不构成正式榜单题集或可复现抽样协议，创建后每题仍有独立工作区、回收、验收和分数。桌面草稿逐题请求并等待用户确认，不能连续覆盖提示词，也不能自动替用户信任目录、配置当前桌面模型或完成多题执行。

裁判启动前把冻结题面、适用评分卡和候选文件名写入任务环境 JSON，CLI 指令只给路径，不再将大量文件/浏览器配置路径内联进 Windows 命令。生成的 Chromium profile 文件不进入候选/行号映射；原始快照、原始裁判日志不改。Harbor 的异常原因传至失败诊断，明确区分启动命令超长与模型无结果；它们都不记零分。新报告记录指令与材料各自 SHA 及协议版本。现有失败作业不会在用户未再次确认额度时后台重评。

新自动评分卡 `project-tasktype-v3` 在工程/网页等开放题的目标组显式要求有证据的“逻辑取舍”细项，总权重仍为 60/25/15；v2 试次和当前 93.6 的五题批次按冻结版本只读，缺失的推理轴仍显示“未测”。新版要求可见决策证据，不推断私有思维链。网页共用检查器增加真实交互后的页面变化、键盘触发、表单标签、SVG 结构、四档窄屏溢出、运行异常和离线依赖等检查，并在已知内置镜像旧版本时自动准备新版；这仍不是题意/审美/几何的逐题真值。配置成绩对仅一次的网页 AI 高分直接说明未校准；不人为调低旧分。部署与验证边界见[当前交接 U60](当前交接.md)。

### 8.21 U65 Harness收益与成本的配对实验

将用户要验证的冗余Harness作为实验变量，固定模型/思考/速度、题目和验收。配置页提供A/B与精简副本、1–5次重复、活动/Token预算；最多60个独立试次。交错AB/BA、冻结哈希、进度恢复、逐题执行与导出贯通。结果页首位显示两组验收成功/失败/未知、超预算、含失败的资源及配对差；不再将两组AI分平均。

验收通过率读取当前快照原生程序结果或已有正负例保护的专属程序检查，独立于AI报告。统一AI协议仍辅助诊断；修复本机JSON schema与提示词冲突。全部计划尝试保留；条件、实际速度或完整验收缺失时显示观测数据与缺口，不能宣布收益。详情见MEASUREMENT_AND_COMPARISON的U65合同。真实桌面A/B尚未跑完、视觉裁判尚未校准，B02/B06/B08不标全项目完成。
