# Harness 是否让模型更好合作：开源方法与测量设计

核查日期：2026-09-30。对应 U67。本文件区分已存在的上游方法、本项目的设计选择与尚未实现的测量能力。不是新评分已上线的声明。

## 1. 要回答的问题

固定模型、档位、速度与任务，改变个人规则或技能，能否减少答非所问、无用工程、重复纠正和不必要流程，同时保持交付质量？如果没有改善，至少能指出具体失误发生在哪一回合、哪次改动，以及付出的代价。

“不讲人话”在这里不是词汇黑名单，也不是越短越好。它指在指定读者与请求下，没有及时回答核心问题，让用户还得翻译术语、重复意图或追问才拿到可用结果。长而清楚的必要解释可以合格；简短但错误的回答不能合格。前端将开发指令直接写成用户文案、修补一个症状又引入多层流程，也属于要检查的交付问题。

用户附件的脚本数量、源码行数与状态名只是其指出“流程压过目标”的案例，没有核对该案例仓库，不能把截图数字当成本项目的统计，也不能据此推出脚本/源码比达到某个值就是过度工程化。

## 3. 对话必须进入被测材料，但不是继承解题会话

使用本次试次的用户可见消息、工具结果摘要、时间顺序、代码 diff 与最终运行证据。每条消息保留角色、回合 ID 和来源哈希，标明缺失范围。用户当时的目标、授权、纠正和接受都必须能定位。被测对话作为不可执行的数据交给新的审查会话；其中“请给我满分”等文本不能成为裁判指令。

只取本题绑定会话，不扫描无关历史，不上传私有轨迹到 Git；脱敏副本与本地原件分别留存。无需也不采集隐藏思维链。不能把被测模型的“我已完成”当完成证据；缺对话时沟通指标为未知，不能拿 README、交接说明或产物里的漂亮文案替代。

公平比较分两种：

- **同一上下文回放**：从相同公开上下文分叉，只比较接下来如何回答或处理一次纠正，适合检测一条提示词改变了什么。
- **完整协作任务**：预先固定用户角色、已知信息和分支回复规则。任务需要澄清时给同样的信息，不给一边额外暗示。模拟用户可降低成本，但不能替代真实用户体验；模拟器的版本、回复条件和人工介入都要记录。

真实对话回收适合诊断具体问题；若两边用户提供的帮助不同，不能直接解释为 Harness 的因果收益。

## 4. 把“哪里差”变成事件、分母和证据

这是拟实施的测量合同，不是当前页面已计算的指标。共同结构：适用机会、结果 pass/fail/unknown、回合/改动引用、简短依据。判断不了允许弃评。先定义机会和失误，再看作品，避免事后只挑会输的点。

|要测的失误|观察单位与合格条件|应显示的量，不用什么替代|
|---|---|---|
|没有答到点|一个明确用户请求；回答/动作解决核心要求。动作任务不能只说会做，解释任务不能仅执行不解释|首次响应命中数 / 可判定请求数，另列未知；不按关键词出现次数判定|
|纠正后仍跑偏|一次明确纠正及随后响应；更新理解，并在允许观察期内落实，后续不复发|已落实纠正 / 可判定纠正；同一意图额外重复提醒数；不能把“好的”当已修好|
|表达费解|给定读者和问题的回答；结论可找到，必要术语有解释，读者知道下一步|匿名 A/B 偏好、弃评/分歧、造成理解障碍的原句；长度只作伴随量，不能越短越高分|
|无谓停顿或追问|一次追问/确认；区分必要缺信息、真实权限边界与重复询问已有答案|不必要打断事件/会话、含事件会话率，必要澄清另列；不能奖励盲目行动|
|越界扩张与生硬补丁|一个可独立审查的改动单元；能映射到用户目标、必要依赖或有证据的修复|不支持目标的改动事件/任务，新增依赖和代码量辅助展示；不以文件多或未复刻参考方案直接扣分|
|内部要求进入成品|用户可见页面、文案、文件；本应指导开发的规则被不恰当地当成产品内容|发生泄露的任务数 / 有完整可见面检查的任务数，位置截图；开发教程合理引用规则不算泄露|
|流程替代了结果|一次验证/修复阶段；检查结果真实反馈到改进，按任务风险停止|重复无新增证据的循环、同缺陷复发、未解决就宣告完成；测试多不能自动加分，必要回归不能自动罚分|

涉及语义的分类由冻结标准和证据支持的裁判/人工标注完成，程序负责引用、计数、分母和聚合。不能把正则抓到的“是否需要”全部判为无谓追问，也不能把所有脚本判为流程冗余。

## 5. 绝对事实与相对体验分别量化

绝对指标用“发生几次 / 共几次机会”。例如首次命中率：`pass / (pass + fail)`，紧邻显示覆盖 `(pass + fail) / 全部适用机会` 和 unknown 数。没有适用机会为 N/A；有机会但没材料为 unknown。跨任务先算每题的率再等权，另列原始分子分母，避免一个话多的任务支配结果。未知不得在比较时被静默丢弃；完整配对覆盖未齐时只给已观测子集的描述。

相对体验用 A/B 胜、平、负、未知。一个示例协议的偏好率可定义为 `(胜 + 0.5 × 平) / (胜 + 平 + 负)`，同时显示未知与全部计划对数；这只是此协议的定义，不等于直接实现 AlpacaEval 的加权或长度控制方法。换边呈现后结论翻转的样本标“顺序不稳定”，不得平均成一个假确定胜者。多题重复先按题聚合；小样本展示原始结果，不编造固定置信区间。

同模型的 B−A 才是规则改动的观测差。成果达标是前提，不能因为 B 更简短/便宜却未完成任务，就宣布 B 更优。保留质量、沟通负担、改动范围与资源四方面，不再加成一个任意“Harness 93.7分”。若收益与代价交叉，明确取舍，不强判冠军。

**示意，非实测：**相同 20 个可判定请求，命中由 12/20 到 17/20，是本批 +25 个百分点；不必要打断从 8 次到 3 次，少 5 次。还需看任务是否都达标、未知和重复波动，不能仅凭这些数字宣称普遍提升 25%。

## 6. 怎样验证裁判，怎样改提示词

1. 在看新结果前冻结标准、提示词、模型与档位、上下文窗口和取证工具。把每种失误放进不同任务，覆盖短回答/长回答、必要/不必要追问、合理抽象/多余架构、正确异路实现/模板复刻。测试集按任务来源分开，不能用已调过的样本验证自己。
2. 小批可信人工标注用于校准和抽查，不要求每次用户亲自打分。标注应独立于被测配置，保留分歧而不是由开发者事后改答案；不要将本开发对话自己写的合成样本称为人类真值。
3. 记录坏例漏检、好例误杀、相同材料复评一致性、交换位置后反转、提示词等义改写后的变化、弃评及格式失败。没有材料不能报告误差为零；校准门槛需按用途预先确定，未过就不用于排名。
4. “修提示词”不等于不断加禁令。每次只测试一个假设，例如“先回答核心问题，再给必要解释”，或“纠正后统一修正同类问题并验证”。要同时检查是否误伤需要细节的回答、必要设计和必要授权。有效则保留，无效则回退或删除；规则数量不代表能力。
5. 强模型可以辅助标注，不能自动成为完美裁判。换强裁判也须同一批独立样本校验；对话评价裁判需要看到任务相关对话数据，保持新会话与匿名配置，并不意味着只看代码。

## 7. 当前差距与实施边界

已有：独立工作区、产物/程序验收、质量报告与用量、同模型 A/B 创建与结果比较。现有 `communication` 描述提到实际对话，但雷达将它与 `milestones`、`handoff` 混合，不能证明人机沟通测量已完成。U67 将这个既有视图准确标为“协作与交付”，明确不代表完整对话质量，旧评分数值不改变。

未接通：上述会话级事件合同、与 UI 可见面/diff 的联合取证、合格的人机沟通裁判、完整匿名配对偏好及校准报告。此次完成方法研究、产品背景和现有展示纠偏，不生成新行为分、不批量调用模型。后续实施优先接通最小闭环：同一纠正场景 → 可追溯的对话与改动 → 有证据的命中/复发事件 → 同条件对照，而不是再添加一圈大能力维度。
