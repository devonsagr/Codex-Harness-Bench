# Harness 对照的依据与落地 · 2026-09-29

## 用户真正要测的东西

“冗余Harness”是一个实验假设：额外规则、技能或流程消耗更多资源，却没有改善需求完成/回归/体验，甚至扩大范围或损害结果。只测困难知识题或一次作品的AI绝对分，无法把模型能力和Harness影响分开。本项目固定同一模型、思考和速度，以具体配置差异作处理变量。

强模型的作品可加入后续盲评作为参考样本，但不是无条件正确，也不能定义成100分后按比例折算Luna。困难度饱和或全部失败的题都可能缺乏区分力；应同时观察成功率与包括失败的资源，对冻结题集重复验证。高分的正确处置是审查验收覆盖和裁判校准，不是按模型名预先压分。

## 发布方方法核对

- [Terminal-Bench 4.0发布说明](https://www.tbench.ai/news/terminal-bench-4-0)：校准CPU/内存/时间资源、修复题目、移除饱和等问题任务；资源或题集变化需重新运行，验收器变化另分版本。其8小时上限面向该榜单，不能直接当作本项目短时交付的默认预算。本项目借鉴固定环境、版本化和成功/成本并列，不把TB任务索引说成已接入。
- [FrontierCode 1.1](https://cognition.com/blog/frontier-code-1.1)：真实工程criteria及blocker仍需要审计，发布方修正过75项过严blocker；它还区分正常查文档与寻找现成答案。这说明验收器本身也必须验证，主观审查不是只加一段“严格客观”提示词便可靠。本项目保留引用与反例检查，尚未实现同等规模独立校准。
- [Cursor的模型比较方法](https://cursor.com/blog/cursorbench)：任务和实际产品Agent设置共同影响测量。借鉴点是用与用户工作对应的任务和执行条件，不能把另一套Agent下的模型榜单名次直接迁移为本机Harness结论。

以上是方法借鉴，不复制其榜单数字、私有题或官方认证。截图中的全部指标仍需各自单位与版本；本次实施不把不同榜单百分比、rating或Elo相加。

## 实施结果与尚欠实证

已实现harness-paired-v1：相同题目/模型，冻结A/B计划、AB/BA顺序、重复、预算、独立workspace、原生用量绑定、程序验收与AI参考分分离、失败/未知保留、报告和ZIP导出。精简副本帮助直接检验附加规则是否有用，不替换宿主底座。

发现并修复了一个具体评分工程错误：本机CLI输出schema仍要求旧score字段，与新等级提示词不一致。新schema根据同一冻结合同生成，无需改默认裁判模型；旧材料仍用旧格式。此缺陷不是所有历史Docker失败的统一解释。

代码与页面验收覆盖实施行为，不是模型效度实验。尚未得到真实同模型A/B桌面样本、人工/专家锚点保留集、视觉误差或提示词扰动数据。不能把“已实现对照流程”写成“已证实某套Harness更好”或“主观高分已消除”。后续真实实验应保持协议冻结并留出新样本检验，而非看结果后调验收门槛。
